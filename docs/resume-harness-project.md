### Claude Code 기반 백엔드 개발 하네스 구축 및 효과 검증
개인 | 2026.07 ~ 2026.10 · github.com/urban6/my-harness

- 설계·구현·검증·테스트 단계를 나눈 에이전트 팀과 Spring Boot 관례 스킬을 구성
- 일반·스킬·에이전트 팀 방식을 비교하기 위해, 주문 결제 API를 과제로 숨긴 인수 테스트(결제 장애 주입, 동시 결제·재고 경합, 멱등성, 결제 만료 검증)와 채점 파이프라인을 AI 에이전트를 활용해 설계·검증
- 실험 5회·약 35회 실행 결과 명세가 상세하면 모델(Opus~Haiku)·과제 유형(신규 기능·기존 코드 수정·멀티테넌시 전환)과 무관하게 단일 세션이 만점이었고, 에이전트 팀은 정확도 차이 없이 비용 2.6~6.3배를 소모해 단일 세션 + 스킬을 기본 개발 방식으로 채택
- 실험 중 채점기 버그 2건과 테스트 편향 1건을 찾아 수정하고 전 실행 재채점

본문에 넣지 않고 면접에서 꺼낼 수치: 시간 2.8~5.1배, 스킬 관례 준수율 71% → 95%(비용 +7~22%, 실행 3회씩, 스킬 체크리스트 기준이라 순환 측정 — 스킬 밖 일반 품질 14항목으로는 79% vs 83%로 차이 없음), 인수 테스트 92케이스·견고성 25항목, 채점기 돌연변이 검증 13종(5차 8종은 실패 예상을 채점 전에 기록). 5차는 단일 세션이 실패하는 과제를 먼저 걸러 내는 정지 조건을 둬, 걸러 내기 $3.5로 예상 $100~220의 본 실행을 생략.

> Claude Code 에이전트 팀과 Spring Boot 스킬을 만들고, 주문 결제 API 숨긴 인수 테스트(PG 장애 주입·동시성·멱등성·테넌트 격리)로 개발 방식을 비교 — 에이전트 팀은 정확도 차이 없이 비용 2.6~6.3배여서 단일 세션 + 스킬을 기본값으로 채택

## 면접 예상 질문 (백엔드 관점)

- **숨긴 테스트를 어떻게 믿나?** — 빈 스타터 0점, 정답 구현 2회 연속 만점, 정답에 결함을 넣은 돌연변이 5종이 해당 항목만 실패하는지 확인. 짧은 명세용 2종(입력 검증·상품 행 잠금·주문 행 잠금 제거 / 잠금 순서 정렬·쿠폰 행 잠금 제거), 상세 명세용 3종(상품·쿠폰 행 잠금 제거 / 멱등 키 지문 검사 제거 / 할인 상한 무시 + PG 멱등 키를 매번 새로 생성). 상세 명세용은 실패할 항목을 채점 전에 기록해 두고 대조했다. 이 과정에서 테스트 허점 2건(엔드포인트가 없어 나는 404를 거절로 셈, 같은 상품 주문이라 상품 잠금이 쿠폰 경합을 가림)을 찾아 고침. 5차는 변경 요청 과제용 8종(환불 안분 계산, 카드·포인트 환불 순서, PG 환불 키, 상태 전이 / PG 키 테넌트 접두어, 목록·잠금 조회·쿠폰 검사의 테넌트 조건)을 실패 예상을 먼저 적고 돌려 8종 모두 예상한 케이스만 실패했다.
- **동시성 테스트의 비결정성은?** — 경합 케이스는 Barrier로 동시에 출발시키고 5회 반복, 정답 구현에서 연속 통과 확인. 교차 주문은 `[P,Q]`·`[Q,P]`를 섞어 교착 시 5xx가 나는지 확인 — 잠금 순서 정렬을 뺀 구현에서 실제로 5xx 발생.
- **멱등성·중복 청구는 어떻게 검증했나?** — PG 스텁이 받은 요청을 관리 API로 노출하고, 멱등키 재전송으로 저장된 결과를 돌려준 호출을 빼고 "실제 청구 횟수"를 셈. 같은 주문 동시 결제 5건에서 청구 1회인지 확인.
- **명세가 짧으면 상태코드를 어떻게 채점하나?** — 상태코드를 특정하지 않고 "4xx로 거절 + 재고·쿠폰·주문 상태 불변"으로 판정. 명세가 비운 판단(PG 장애 시 대기 유지 vs 실패 처리)은 일관되면 모두 인정.
- **편향을 발견한 사례는?** — 테스트가 "결제 시 재고 차감"을 단언했는데, 짧은 명세에 없는 규칙이었다. 에이전트 팀이 설계 문서에 "출고 시 차감"을 명시해 실패하면서 발견, 가용 재고(stock − reserved)로 판정을 바꾸고 전체 재채점.
- **한계는?** — 단일 기능(주문 도메인)·단일 스택(Spring Boot)·사람 개입 없는 실행, 반복 2~3회로 통계 검정은 하지 않음. 여러 모듈에 걸친 대형 작업이나 대화형 사용에서의 가치는 검증하지 않음. 실험 후 독립 검토로 추가 한계도 찾았다: 짧은 명세 테스트 일부가 상세 명세의 규칙에서 왔다(제외하고 재계산해도 결론 동일), 컨벤션 판정이 스킬 체크리스트 기준이라 순환 측정이다(보충 측정으로 보완), 전역 플러그인이 모든 군에 로드돼 있었다(5차에서 `--setting-sources project,local`과 하네스 커밋 사본으로 해결). 5차는 걸러 내기 단계에서 마감해 A·C를 돌리지 않았고, 시작 코드가 깔끔한 정답 구현이라 낡은 실무 코드 수정보다 쉬웠을 수 있다.
- **컨벤션 수치는 스킬에 유리하지 않나?** — 맞다. 점검 기준을 스킬에서 뽑았으니 "지시한 관례를 실제로 지키는가"를 확인한 것이다. 그래서 스킬이 다루지 않는 일반 리뷰 항목 14개(긴 메서드·중복·죽은 코드·예외 삼킴·시각 주입·상태 전이 응집 등)로 같은 방식의 블라인드 판정을 다시 했고, 일반 품질은 A 79% · B 83%로 구별되지 않았다. 결론은 "스킬은 지시한 관례를 지키게 하지만 코드 품질 전반을 올리지는 않고, 떨어뜨리지도 않는다"이다. 에이전트 팀은 64%로 가장 낮았는데(긴 메서드·죽은 코드), 구현 워커가 Sonnet이라 모델 차이와 분리할 수 없다.
- **단일 세션이 실패하는 과제에서는 에이전트 팀이 낫지 않나?** — 그걸 재려고 5차를 설계했다. 기존 코드에 포인트·부분 환불을 넣는 변경(T3)과 단일 테넌트를 멀티테넌시로 바꾸는 교차 관심사 변경(T4)을 만들고, 단일 세션 통과율이 40~85%인 과제만 본 실행에 쓰기로 미리 정했다. Sonnet은 물론 Haiku 단일 세션도 두 과제를 모두 만점(125/125, 110/110)으로 통과해 채택할 과제가 없었고, 정지 조건대로 본 실행 없이 마감했다. 명세가 상세하면 이 규모(변경 파일 12~16개)는 단일 세션이 해낸다 — 남은 후보는 한 세션 컨텍스트를 넘는 대형 작업뿐이고 검증하지 않았다.
- **짧은 명세에서도 스킬이 기본값이 맞나?** — 보충으로 스킬 군을 2회 더 돌렸더니 견고성·실패 항목이 일반 방식과 같았고 비용은 +22%, 에이전트 팀의 약 1/5이었다. 명세에 없는 기대(0원 거절, 쿠폰 1인 1회)는 어느 방식도 채우지 못했다 — 방식보다 명세가 큰 변수다.

- **테스트 코드를 직접 짰나?** — 테스트·스크립트·정답 구현은 대부분 AI 에이전트가 작성했고, 나는 검증 항목과 판정 규칙을 정하고 스타터·정답·돌연변이로 테스트가 맞는지 확인하고 편향을 찾아 고쳤다. 아래 코드 목록은 직접 설명할 수 있어야 한다.
