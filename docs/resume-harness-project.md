## 이력서 항목 (사이드 프로젝트 맨 위)

### Claude Code 기반 백엔드 개발 하네스 구축 및 효과 검증
개인 | 2026.07 ~ 2026.10 · github.com/urban6/my-harness

**배경**
- AI 코딩 도구로 백엔드 기능을 개발할 때 세션마다 설계 기준과 코드 관례가 달라지고, 결과물을 검증할 기준이 없는 문제
- 설계·구현·검증·테스트를 나눈 에이전트 팀이 단일 세션보다 나은지, 늘어나는 비용과 시간만큼 가치가 있는지 수치로 확인 필요

**해결 1: 단계별 에이전트 팀과 스킬 구성**
- 오케스트레이터가 요구를 분해하고 프로젝트 스택을 확정해 설계, 구현, 경계 검증, 테스트 에이전트에 전달하도록 구성
- API와 DB 설계를 한 에이전트가 함께 작성해, 요청 필드와 테이블 컬럼, 제약 위반과 HTTP 상태코드가 어긋나지 않도록 구성
- Spring Boot 관례(레이어 경계, Bean Validation, RFC 9457 에러 응답, 트랜잭션 경계)를 스킬로 정리

**해결 2: 에이전트가 볼 수 없는 인수 테스트로 채점 파이프라인 구축**
- 쿠폰, 재고 예약, 외부 PG 결제가 얽힌 주문 결제 API를 과제로, 블랙박스 HTTP 인수 테스트 92케이스(규칙 48개)와 견고성 테스트 25항목 작성
- 외부 PG를 거절, 500, 지연, 연결 끊김, 환불 실패를 주입하는 스텁으로 대체하고, 멱등키 재전송, 동시 결제 중복 청구, 재고·쿠폰 경합, 교차 주문 교착, 결제 만료를 검증
- 빈 스타터는 0점, 정답 구현은 2회 연속 만점, 결함을 주입한 구현은 의도한 항목만 실패하는지 확인해 채점기 자체를 검증
- 실행마다 독립 저장소와 DB 컨테이너를 쓰고, 세션 로그로 채점 자산 접근과 사용 모델을 자동 검사해 위반 실행 폐기

**해결 3: 방식별 비교 실험과 누락 원인 추적**
- 일반, 스킬, 에이전트 팀 세 방식을 같은 과제로 각 2~3회 실행(실험 4차례, 약 30회)하고, 명세 상세도와 모델을 바꿔 결과 차이의 원인 분리
- 자체 테스트의 요구 검증 범위와 코드 관례 준수는 실행 이름을 가린 LLM 판정 3회 다수결로 채점
- 짧은 명세에서 놓친 요구를 설계 문서, 코드, 테스트 순으로 거슬러 올라가 어느 단계에서 빠졌는지 분류
- 실험 중 발견한 채점기 버그 2건(chunked 요청 본문 미처리, keep-alive 연결 오염)과 테스트 편향 1건을 수정하고 전체 재채점

**결과**
- 에이전트 팀은 기능 정확도 차이 없이 비용 2.6~6.3배, 시간 2.8~5.1배 소모 — 상세 명세에서는 세 방식 모두 인수 테스트 만점
- 짧은 명세에서 에이전트 팀이 놓친 요구는 모두 설계 단계에서 사람 확인 없이 내린 가정(0원 상품 허용, 쿠폰 사용 제한 없음 등)으로 확인
- Spring Boot 스킬 적용 시 비용 약 7% 증가로 코드 관례 준수율 71%에서 95%로 상승
- 단일 세션과 스킬을 기본 개발 방식으로 정하고, 에이전트 팀은 대형 작업에만 쓰도록 운영 기준 정리

## 짧은 버전 (한 줄 요약이 필요할 때)

> Claude Code 에이전트 팀과 Spring Boot 스킬을 직접 만들고, 주문 결제 API 숨긴 인수 테스트(92케이스, PG 장애 주입)로 개발 방식을 비교 — 에이전트 팀은 정확도 차이 없이 비용 2.6~6.3배, 스킬은 비용 +7%로 코드 관례 준수율 71%→95%를 확인해 단일 세션 + 스킬을 기본값으로 채택

## 자기소개 문단 수정안

현재 문장:
> 개발에는 Claude Code를 주로 사용하며, 설계, 구현, 검증 단계를 나눈 에이전트 하니스를 직접 만들어 쓰고 있습니다. AI가 만든 결과물도 숨긴 인수 테스트와 평가로 채점해, 어떤 개발 방식이 실제로 나은지 수치로 확인하고 있습니다.

수정안:

## 면접 예상 질문 (백엔드 관점)

- **숨긴 테스트를 어떻게 믿나?** — 빈 스타터 0점, 정답 구현 2회 연속 만점, 정답에 결함 5종을 두 묶음으로 넣어(입력 검증·상품 행 잠금·주문 행 잠금 제거 / 잠금 순서 정렬·쿠폰 행 잠금 제거) 해당 항목만 실패하는지 확인. 이 과정에서 테스트 허점 2건(엔드포인트가 없어 나는 404를 거절로 셈, 같은 상품 주문이라 상품 잠금이 쿠폰 경합을 가림)을 찾아 고침.
- **동시성 테스트의 비결정성은?** — 경합 케이스는 Barrier로 동시에 출발시키고 5회 반복, 정답 구현에서 연속 통과 확인. 교차 주문은 `[P,Q]`·`[Q,P]`를 섞어 교착 시 5xx가 나는지 확인 — 잠금 순서 정렬을 뺀 구현에서 실제로 5xx 발생.
- **멱등성·중복 청구는 어떻게 검증했나?** — PG 스텁이 받은 요청을 관리 API로 노출하고, 멱등키 재전송으로 저장된 결과를 돌려준 호출을 빼고 "실제 청구 횟수"를 셈. 같은 주문 동시 결제 5건에서 청구 1회인지 확인.
- **명세가 짧으면 상태코드를 어떻게 채점하나?** — 상태코드를 특정하지 않고 "4xx로 거절 + 재고·쿠폰·주문 상태 불변"으로 판정. 명세가 비운 판단(PG 장애 시 대기 유지 vs 실패 처리)은 일관되면 모두 인정.
- **편향을 발견한 사례는?** — 테스트가 "결제 시 재고 차감"을 단언했는데, 짧은 명세에 없는 규칙이었다. 에이전트 팀이 설계 문서에 "출고 시 차감"을 명시해 실패하면서 발견, 가용 재고(stock − reserved)로 판정을 바꾸고 전체 재채점.
- **한계는?** — 단일 기능(주문 도메인)·단일 스택(Spring Boot)·사람 개입 없는 실행, 반복 2~3회. 여러 모듈에 걸친 대형 작업이나 대화형 사용에서의 가치는 검증하지 않음.
