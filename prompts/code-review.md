# 코드 리뷰

커밋이나 배포 전에 변경 코드를 여러 관점으로 점검할 때 쓰는 프롬프트입니다. 아래 템플릿을 복사해 `{빈칸}`만 채운 뒤 붙여넣습니다.

## 빈칸 작성 팁

- `{대상 범위}`는 경로나 "최근 커밋 N개", "현재 diff"처럼 구체적으로 적습니다. 범위가 넓으면 리뷰가 얕아집니다.
- `{레이어·의존성 규칙}`은 지켜야 할 방향을 한 줄로 적습니다. 예: web → service → repository 단방향.
- `{경계 밖으로 새면 안 되는 타입}`은 엔티티, 내부 DTO처럼 API 응답에 노출되면 안 되는 타입을 적습니다.
- `{스킬명}`과 `{문서}`는 프로젝트 스택에 맞는 스킬의 참고 문서를 적습니다. 해당 스킬이 없으면 3번 줄을 지웁니다.
- 진단만 하라는 문장은 지우지 않습니다. 이 문장이 없으면 리뷰 중에 코드를 고치기 시작합니다.

## 템플릿

```text
{대상 범위 — 경로나 최근 변경}를 {커밋 전 / 배포 전}에 점검해줘.

1) architecture-expert로 {레이어·의존성 규칙}이 깨진 곳,
   {경계 밖으로 새면 안 되는 타입}이 노출된 곳을 찾아줘.
2) security-auditor로 인증·인가·민감 데이터 노출을 심각도와 함께 점검.
3) {스킬명} 스킬의 references/{문서}.md 체크리스트로 {점검 항목}을 항목별로.
4) code-reviewer로 가독성·네이밍·에러 핸들링·중복을 마무리 점검.

넷 다 진단만 하고 수정은 하지 마 — 고칠지는 내가 정할게.
발견 항목은 file:line 근거와 함께 심각도 순으로 정리해줘.
```
