# 기능 개발

새 백엔드 기능을 구현할 때 쓰는 프롬프트입니다. 설계부터 맡길 수도 있고, 정해 둔 설계대로 작은 단위만 구현시킬 수도 있습니다. 아래 템플릿을 복사해 `{빈칸}`만 채운 뒤 붙여넣습니다.

## 어떤 템플릿을 고를까

- **A**: `feature-pm`에게 전체를 맡깁니다. 요구 분해, 스택 주입, 설계·구현·검증·테스트를 Phase 단위로 자동 진행합니다. 기능이 크거나 검증 단계까지 챙기고 싶을 때 씁니다.
- **B**: 단계와 담당 에이전트·스킬을 직접 지정합니다. 흐름을 내가 통제하고 싶거나 일부 단계만 돌릴 때 씁니다.
- **C**: 설계가 이미 정해진 작은 단위 하나를 구현합니다. 메서드나 클래스 하나처럼 범위가 좁고, 무엇을 어떻게 만들지 내가 결정했을 때 씁니다. 추측할 여지가 가장 적어 결과가 가장 안정적입니다.

## 빈칸 작성 팁

- `{기능명}`은 도메인 이름 하나로 씁니다. 산출물 디렉터리 이름이 됩니다.
- `{스택}`은 언어·프레임워크·영속성·DB까지 적습니다. 비워 두면 매니페스트로 판별하지만, 적어 두는 편이 확실합니다.
- `{포함 / 제외}`는 둘 다 적습니다. 제외 항목이 없으면 AI가 범위를 넓힙니다.
- `{테스트 명령}`은 실제 실행 명령 그대로 적습니다. 결과를 "그대로" 보여 달라고 해야 통과 여부를 요약으로 뭉개지 않습니다.

## 템플릿 A — feature-pm 오케스트레이션

```text
feature-pm 에이전트로 {기능명} 기능을 개발해줘.
스택은 {스택}이고, 범위는 {포함 / 제외}야.

Phase 0에서 스택을 확정해 모든 워커에 주입하고,
설계(backend-designer) → 구현·검증(backend-impl·boundary-verifier) → 테스트(test-writer) 순으로 진행해줘.
각 Phase 산출물 경로와 마지막에 {테스트 명령} 결과를 그대로 보여줘.
```

산출물은 `_workspace/features/{기능명}/`에 `00_requirements.json` → `01_api_design.md`·`02_db_design.md` → `03_integration_summary.md` 순으로 쌓이고, 진행 상태는 같은 디렉터리의 `progress.md`에 기록됩니다.

## 템플릿 B — 단계 직접 지정

```text
{기능명} 기능을 설계부터 구현까지 진행해줘.
스택은 {스택}, {범위}야.

1) backend-designer로 엔드포인트·요청/응답 스키마·에러 응답과
   테이블·인덱스·제약을 한 번에 정리. 정합 요약표까지 남겨줘.
2) 그 산출물을 입력으로 {구현 스킬 또는 backend-impl}로 구현
3) architecture-expert로 {레이어·의존성 규칙}이 지켜졌는지 점검

각 단계 산출물 경로를 알려주고, 마지막에 {테스트 명령} 결과를 그대로 보여줘.
```

## 채워 넣은 예시 — Spring Boot (템플릿 B)

```text
주문(Order) API를 설계부터 구현까지 진행해줘.
스택은 Spring Boot 3.x + JPA + PostgreSQL이야.

1) backend-designer로 엔드포인트·요청/응답 스키마·에러 응답(RFC 9457)과
   테이블·인덱스·제약을 한 번에 정리. JPA 엔티티 + Flyway SQL 기준으로.
2) 그 산출물을 입력으로 spring-boot 스킬을 따라 컨트롤러·서비스·리포지토리 구현
3) architecture-expert로 web → service → repository 단방향이 지켜졌는지 점검

각 단계 산출물 경로를 알려주고, 마지막에 ./gradlew test 결과를 그대로 보여줘.
```

## 템플릿 C — 설계 확정 후 단일 작업

```text
## 작업
{구현 대상 — 클래스·메서드 단위}만 구현해줘.

## 설계 (내가 정한 것)
- {핵심 방식 — 어떤 기술·알고리즘으로}
- {실패·예외 시 동작}
- {시그니처·반환값}
- {이번 범위 밖인 것}

## 제약
- {스택·라이브러리}
- {반드시 지켜야 할 규칙}

## 범위
- 수정 가능: {수정해도 되는 파일}
- 생성 가능: {새로 만들어도 되는 파일 — 예외·테스트 등}
- 금지: 그 외 기존 파일 수정

## 완료 조건
- {통과해야 할 테스트 — 결과로 판정할 수 있는 문장}
- {테스트 환경·명령} 결과를 그대로 보여줘.
```

빈칸 작성 팁:

- **설계**에는 AI가 고르면 안 되는 결정만 적습니다. 여기가 비면 AI가 임의로 정합니다.
- **범위**는 수정과 생성을 나눠 적습니다. "다른 파일은 건드리지 마"만 쓰면 예외 클래스나 테스트 파일이 필요할 때 AI가 규칙을 어기거나 한 파일에 몰아넣습니다.
- **완료 조건**은 테스트 통과 여부로 판정되는 문장으로 씁니다. "잘 동작하게"처럼 판정할 수 없는 말은 쓰지 않습니다.
- 둘 이상이 협력하는 기능이면 연결 고리를 설계에 적습니다. 예를 들어 락을 풀 때 토큰이 필요하면 누가 토큰을 반환하는지 적습니다.

## 채워 넣은 예시 — Spring Boot (템플릿 C)

```text
## 작업
OrderService.reserveSeat()만 구현해줘.

## 설계 (내가 정한 것)
- Redis SETNX + TTL 180초로 좌석 선점
- 키는 seat:{showId}:{seatId}, 값은 요청마다 새로 만든 UUID 토큰
- 선점 성공 시 토큰을 반환, 실패 시 SeatAlreadyHeldException
- DB 확정은 이 메서드 범위 밖

## 제약
- Spring Boot 3, Lettuce 사용
- 락 해제는 본인 토큰일 때만 (Lua 스크립트)

## 범위
- 수정 가능: OrderService
- 생성 가능: SeatAlreadyHeldException, 해제용 Lua 스크립트, OrderService 테스트
- 금지: 그 외 기존 파일 수정

## 완료 조건
- 동시 요청 100개 중 정확히 1개만 성공하는 테스트 포함
- Testcontainers Redis로 ./gradlew test 실행 결과를 그대로 보여줘.
```
