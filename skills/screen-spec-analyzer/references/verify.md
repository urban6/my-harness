# 4-B. verify 모드

기준은 3단계 데이터 구조 명세뿐이다.

## 절차

1. API 찾기: 코드라면 라우트 매핑(예: `@GetMapping`, `@RequestMapping`, `@Get()`, `@Post()`, 라우터 등록부)을 검색 → 핸들러 → 서비스 → 매퍼 → 응답 DTO → 엔티티/쿼리까지 추적한다. 응답 DTO 선언만 보고 판단하지 않는다. 매퍼/쿼리에서 실제로 값을 채우는지 확인한다.
2. 필드 대조: 3-1의 모든 path에 대해 존재·타입·nullable·포맷·enum 값·네이밍을 비교한다.
3. 액션 대조: 3-2의 각 액션에 대해 엔드포인트 존재, 입력 검증, 선행 조건 검사, 실패 시 응답 코드를 확인한다.
4. 규칙 대조: 3-3의 "서버 필수" 규칙이 서버에서 강제되는지(쿼리·서비스·직렬화 레벨) 확인한다.
5. 비기능: N+1(목록 + 작성자 + 조회자별 좋아요 여부), 인증 적용, 페이지네이션, 타임존 직렬화, 트랜잭션 경계(결합 액션), 동시성(중복 투표 유니크 제약 등).

## 판정 표

| # | 대상 | 화면 기대 | 현재 구현 | 판정 | 심각도 | 근거 | 조치 |
|---|---|---|---|---|---|---|---|

- 판정: ✅ 일치 / ⚠️ 불일치(타입·네이밍·nullable·포맷) / ❌ 누락 / ➕ 초과(화면에 없는 필드 — 민감 정보 노출 여부 확인) / ❓ 판단 불가(근거 부족)
- 심각도: BLOCKER(화면 동작 불가, 보안·규칙 위반) / MAJOR(잘못된 값, 수정 필요) / MINOR(네이밍·포맷)
- 근거: `파일경로:라인` 또는 응답 JSON 경로. 근거 없는 ✅는 금지한다.
- 코드만 보고 실행하지 않았으면 "정적 검증"이라고 명시한다. 실제 호출이 가능한 환경이면 GET만 호출하고, 쓰기 API는 사용자 승인 후에만 호출한다.

## 보고 순서

결론 한 줄(그대로 사용 가능 / 수정 후 사용 / 재구현 필요) → BLOCKER 목록 → 전체 판정 표 → 3-4 질문 중 판정에 영향을 준 것.
