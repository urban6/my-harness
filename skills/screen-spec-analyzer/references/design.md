# design 모드

입력은 추출한 필드 표다. 범위는 **API 계약과 DTO까지**이고, DB 스키마는 다루지 않는다. 요청 스키마가 필요한 쓰기 액션(버튼·입력)은 화면에서 다시 뽑는다.

## 스택 판별

매니페스트로 판별한다. 예: `build.gradle(.kts)`/`pom.xml` → Spring Boot, `package.json`의 `@nestjs/*` → NestJS. 코드베이스가 없고 스택이 불명확하면 OpenAPI 스니펫까지만 만들고 스택을 묻는다. 임의로 고르지 않는다.

## 산출물

1. 엔드포인트 표: 메서드, 경로, 인증 필요 여부, 멱등성, 대응하는 화면 요소
2. OpenAPI 3.0 스니펫(요청·응답·에러 스키마)
3. DTO: **프로젝트의 기존 DTO 관례를 최우선으로 따른다**(선언 방식, 검증 방식, 날짜 타입, enum 표현). 관례가 없을 때의 예시는 다음과 같다.
   - Spring: Java record + Bean Validation, 날짜는 `OffsetDateTime`/`LocalDate`, enum은 별도 타입
   - NestJS: class-validator + class-transformer + `@nestjs/swagger` 데코레이터
4. 에러 코드 표: 400/401/403/404/409(중복 행위)/422 또는 프로젝트 컨벤션의 비즈니스 에러 코드, 발생 조건 포함. 에러 바디 포맷은 프로젝트 컨벤션을 따르고, 없으면 RFC 9457(`application/problem+json`)을 쓴다.
5. 영속성 힌트(한 줄씩): 화면 규칙 중 저장소 제약이 필요한 것(예: 중복 투표 방지 → 사용자·대상 유니크). 스키마 설계는 하지 않는다.

## 설계 원칙 (벗어나면 이유를 적는다)

- 조회자별 값은 `viewer`(또는 `me`) 하위 객체로 분리한다. 공통 부분 캐싱과 권한 로직 분리를 위해서다.
- 계산 값은 원천 값(예: `voteEndAt`)을 내려주고 표시용 문자열 계산은 클라이언트가 한다. 단 서버 시각에 의존하는 상태(진행중/종료)는 서버가 `status`로 확정한다.
- 규칙상 비공개 데이터는 응답에서 제외한다. UI에서 숨기는 방식으로 처리하지 않는다.
- 개수가 늘어나는 하위 목록(댓글 등)은 별도 엔드포인트 + 페이지네이션. 상세 응답에 첫 N건을 임베드할지는 트레이드오프(요청 수 vs 응답 크기·캐시)를 표로 제시하고 선택한다.
- 서비스·리포지토리 구현 코드는 사용자가 요청할 때만 작성한다.
