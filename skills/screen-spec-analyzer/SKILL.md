# 화면정의서 → 데이터 구조 명세 → API 설계/검증

## 0. 모드 결정

| 모드 | 수행 단계 | 자동 선택 조건 |
|---|---|---|
| analyze (기본) | 1~3 | 아래 두 조건에 해당하지 않을 때 |
| design | 1~3 + 4-A | "개발", "구현", "API 만들어", "DTO" 등 요청 |
| verify | 1~3 + 4-B | 기존 API 근거(코드/Swagger/응답 JSON)가 함께 주어지거나 "검증", "맞는지", "확인" 요청 |

모드를 선택했으면 응답 첫 줄에 어떤 모드로 진행하는지 밝힌다.

## 입력

- 필수: 화면 캡처 1장 이상. Figma 커넥터가 연결돼 있고 프레임 URL이 주어지면 캡처 대신 커넥터로 디자인 컨텍스트·스크린샷·레이어 텍스트를 직접 가져온다(텍스트 판독 오류가 없음).
- 권장: 화면정의서의 번호별 설명(Description) 텍스트. 캡처에 설명 패널이 없으면 "설명 없이 화면만으로 추론한 항목"임을 명시한다.
- verify 근거(신뢰도 순): 1) 실제 응답 샘플 JSON 2) OpenAPI/Swagger 3) 소스코드(Controller → Service → Mapper → DTO/Entity/Query). 여러 개면 교차 확인.
- 프로젝트 컨벤션: 코드베이스가 있으면 기존 컨트롤러·DTO 1~2개를 먼저 읽고 네이밍(camelCase/snake_case), 날짜 포맷, 공통 응답 래퍼, 페이지네이션 방식, 에러 포맷을 따른다.

## 1단계: 영역 인벤토리

캡처의 번호 마커(01, 02…) 단위로 정리한다. 마커가 없으면 위→아래로 A, B…를 부여한다. 마커 박스가 요소와 어긋나 있으면 박스 위치보다 의미상 가장 가까운 요소를 기준으로 하고 그렇게 판단했다고 적는다.

모든 표시 요소를 다음으로 분류한다.

| 분류 | 의미 | 예 |
|---|---|---|
| DATA | 서버가 내려줘야 하는 원천 값 | 제목, 작성자, 작성일 |
| DERIVED | 원천 값에서 계산되는 값. 계산 주체(서버/클라) 결정 필요 | D-7, 상태 배지, 댓글 수 |
| USER_CTX | 조회자에 따라 달라지는 값 | 내 투표 여부, 내가 좋아요 눌렀는지, 버튼 활성 여부 |
| ACTION | 서버 쓰기를 유발하는 인터랙션 | 투표, 좋아요, 답글, 등록 |
| NAV | 화면 이동만 | 목록으로, 탭 이동 |
| STATIC | 고정 문구 | 안내 문구, 섹션 타이틀 |
| RULE | 문구·상태로부터 도출되는 서버 강제 규칙 | "종료 전 결과 비공개" → 집계 비노출 |

STATIC 문구라도 비즈니스 규칙을 암시하면 RULE로도 등록한다.

출력 형식:

| 영역 | 요소 | 캡처 표시값 | 분류 | 비고 |
|---|---|---|---|---|

해상도 때문에 읽을 수 없는 글자는 추측하지 말고 `[판독불가]`로 적는다.

## 2단계: 숨은 요구사항 점검 (생략 금지)

캡처는 한 시점·한 상태·한 사용자 관점만 보여준다. 아래 항목을 전부 점검하고, 캡처로 판단할 수 없는 것은 3-4 질문 목록으로 보낸다.

- 상태 전이: 같은 화면이 다른 상태(종료, 반려, 반영 등)일 때 바뀌는 영역과 필드
- 빈 상태·0건·긴 텍스트·최대 개수
- 표시 개수 vs 총 개수 불일치 → 페이지네이션/더보기/접힘 필요
- 계층 구조: 답글·대댓글 depth, 삭제된 부모 처리
- 권한: 비로그인 / 일반 / 작성자 본인 / 관리자별 노출·활성 조건
- 중복 행위: 재투표·투표 변경·취소, 좋아요 토글, 중복 제출
- 시간 기반 값: 서버 시각 기준, 타임존(KST/UTC), D-day 경계(D-0, 마감 직후, 기간 시작 전)
- 같은 라벨 버튼이 여러 곳에 있으면 같은 액션인지, 노출 조건이 다른지
- 결합 액션: 버튼 하나가 여러 쓰기(예: 투표 + 의견)를 하면 원자성, 부분 입력 허용 여부, 부분 실패 처리
- 목업 데이터 모순: 날짜 선후, 합계·개수 불일치 → 목업 오류인지 스펙인지 질문
- 탭·필터가 목록 필터인지 현재 항목의 상태 표시인지

## 3단계: 데이터 구조 명세 (다음 단계의 유일한 입력)

design/verify는 이 명세만을 기준으로 삼는다. 형식을 바꾸지 않는다. 채워진 형태는 `references/example.md`를 본다.

### 3-1. 리소스 트리

```yaml
screen: <화면명 또는 ID>
resources:
  - name: <리소스명>
    source: <메서드 경로 | TBD>
    fields:
      - path: title
        type: string
        nullable: false
        category: DATA
        example: "<캡처 표시값>"
        evidence: "02"
        confidence: high
      - path: comments[].likeCount
        type: integer
        nullable: false
        category: DATA
        example: 12
        evidence: "05"
        confidence: high
```

- type: string | integer | long | boolean | decimal | date(YYYY-MM-DD) | datetime(ISO-8601, offset 포함) | enum(값 나열) | object | array<T>
- enum은 화면에 보이는 값만 `values`에, 존재할 것으로 추정되는 값은 `inferred`에 분리한다.
- 화면 근거는 없지만 구현상 필요한 필드(id, 커서, 버전 등)는 `category: TECHNICAL`.
- 근거 없는 필드를 만들지 않는다. confidence가 low인 필드는 반드시 3-4에 질문으로 올린다.

### 3-2. 액션 목록

| 액션 | 트리거(영역) | 요청 데이터 | 선행 조건 | 성공 후 화면 변화 | 실패 케이스 |
|---|---|---|---|---|---|

### 3-3. 규칙(RULE)

| 규칙 | 근거 | 강제 위치(서버 필수 / UI 표시만) |
|---|---|---|

접근 제어·데이터 비공개·기간 제한·중복 방지는 항상 "서버 필수"다.

### 3-4. 확인 필요 질문

번호를 매기고, 각 질문마다 "답에 따라 바뀌는 것"(필드/엔드포인트/규칙)을 한 줄로 붙인다. 질문이 남아 있어도 작업을 멈추지 않고, 가장 합리적인 가정을 명시한 채 진행한다.

## 4단계: 모드별 후속 작업

- design 모드 → `references/design.md`를 읽고 4-A를 수행한다.
- verify 모드 → `references/verify.md`를 읽고 4-B를 수행한다.

## 출력 규칙

- 결론을 먼저, 근거를 뒤에 쓴다.
- 기초 개념 설명은 하지 않는다.
- 파일 쓰기가 가능한 코드베이스 환경이면 3단계 명세를 `docs/screen-specs/<screen-id>.md`로 저장할지 묻고, 이미 있으면 읽어서 변경분만 갱신한다.
- 한 번에 여러 화면이 주어지면 화면별로 1~3단계를 하고, 공통 리소스(작성자, 댓글 등)는 마지막에 통합 스키마로 정리한다.
