# PRD — 2차 실험: 어려운 기능에서의 방식별 결과 점수화

> 상태: 확정 · 2026-10-09 · 1차 결과: [`../REPORT.md`](../REPORT.md)

## 1. 목적

1차와 같은 세 방식(A 일반 · B 스킬 · C 오케스트레이션)을 **점수가 갈릴 만큼 어려운 기능**에 적용해 다시 점수화한다. 1차와 마찬가지로 우열 판정은 하지 않고, 점수와 참고 지표를 한 표에 나란히 놓는다.

### 1차에서 배운 것 → 2차에서 바꾸는 것

| 1차 관찰 | 2차 변경 |
|---|---|
| 정확도 9/9 만점 — 기능이 쉬워 천장 효과 | 상태 전이·멱등성·외부 연동·시간 만료·다중 동시성이 얽힌 기능으로 교체 (§3) |
| 숨긴 테스트 34케이스가 정상 경로·단일 규칙 위주 | 규칙 조합·경계값·장애 주입 케이스 포함 약 80케이스 |
| 요구사항 단위 커버(R1~R8)가 27건 만장일치 — 변별력 없음 | **규칙 단위** 커버로 세분화 — `feature.md` 규칙에 번호를 붙여 48개 |
| 분기 커버리지는 비율이라 단순한 코드가 유리 | 배점 축소, 분기 수를 함께 표기 (§5) |
| C의 verifier가 숨긴 테스트 밖 결함(오버플로)을 잡았지만 점수 미반영 | 경계값을 명세에 명시해 숨긴 테스트가 정당하게 검증 |

| 군 | 정의 | 군별 실행 옵션 |

## 3. 기능 — 주문 결제 (쿠폰 · 재고 예약 · 외부 PG)

1차 기능(주문 + 재고 차감)을 확장한다. 스택·스타터는 1차와 같다(Spring Boot 3.5 + JPA + PostgreSQL + Flyway + Testcontainers).

| ID | 기능 | 어려운 점 |
|---|---|---|
| R1 | 상품 등록·조회 — `stock`, `reserved`, `available` 노출 | 예약 재고와 가용 재고 구분 |
| R2 | 쿠폰 등록·조회 — 정액/정률, 최소 주문 금액, 총 발행 수량, 유효 기간 | 할인 계산 규칙(정률 내림, 최대 할인액, 할인 ≤ 총액) |
| R3 | 주문 생성 — `X-User-Id`, 항목, 선택 쿠폰 → `PENDING_PAYMENT`, 재고 **예약** | 예약·쿠폰 사용이 원자적, 오류 우선순위 |
| R4 | 멱등성 — 주문 생성·결제에 `Idempotency-Key` 필수 | 같은 키+같은 본문 → 같은 응답, 다른 본문 → 422, 동시 같은 키 → 1건만 생성 |
| R5 | 결제 — `POST /orders/{id}/pay {cardToken}` → 외부 PG 호출 | 승인 → `PAID`(예약 → 차감 확정), 거절 → `PAYMENT_FAILED`(예약·쿠폰 복원), PG 5xx·2초 타임아웃 → 503 + 상태 유지 + 재시도 시 같은 PG 멱등 키 |
| R6 | 결제 만료 — `ORDER_PAYMENT_TTL`(환경 변수) 경과 시 `EXPIRED` | 시간 의존, 예약·쿠폰 복원, 만료 후 결제 409 |
| R7 | 취소·환불 — 미결제 취소 → `CANCELLED`, 결제 후 취소 → PG 환불 → `REFUNDED` | 환불 실패 시 상태 유지, 배송 후 취소 불가 |
| R8 | 배송 상태 — `PAID → SHIPPED → DELIVERED` | 허용되지 않은 전이 409 |
| R9 | 주문 목록 — 커서 페이지네이션 + `status`·`userId` 필터 | 정렬 안정성, 페이지 사이 삽입에도 중복·누락 없음 |
| R10 | 동시성 | 재고 경합, 쿠폰 수량 경합, 사용자당 1회 쿠폰 경합, **역순 항목 주문의 교착**(5xx 금지) |
| R11 | 에러 포맷 — RFC 9457 + 오류별 `code` 필드 | 모든 오류 경로에서 일관성 |

- **외부 PG**: 채점 측이 스텁 서버를 띄우고 `PAYMENT_GATEWAY_URL`로 주입한다. 스텁 동작은 `cardToken`으로 정해진다(`tok_ok` 승인 · `tok_decline` 거절 · `tok_error` 500 · `tok_slow` 5초 지연 · `tok_refund_fail` 승인 후 환불 500). PG API 계약은 `feature.md`에 적고, 스텁 자체는 숨긴다 — 에이전트는 자체 테스트에서 직접 목을 만들어야 한다.
- **명세 원칙**: 경로·상태코드·규칙·경계값은 적고, 테이블·락 방식·스케줄러 방식은 적지 않는다(1차와 같음). 만료는 "TTL 경과 후 2초 안에 조회 결과에 반영"처럼 관찰 가능한 계약으로만 적는다.
- 규칙마다 번호(`R5.3` 등)를 붙인다 — 숨긴 테스트·규칙 커버 판정의 공통 기준.

## 5. 채점 (100점)

| 항목 | 1차 | 2차 | 측정 |
|---|---|---|---|
| 기능 정확도 | 60 | **60** | 숨긴 인수 테스트, **요구사항별 통과율의 평균** × 60 (케이스 수가 많은 요구사항이 점수를 독점하지 않게) |
| 테스트 품질 | 30 | **30** | 규칙 커버(48개 중 n) × **20** + 분기 커버리지 × **10** |
| 완료성 | 10 | **10** | `assemble` 5 + 자체 `test` 통과 5 |

- 규칙 커버: 1차 `map_coverage.py` 방식(블라인드 라벨, opus 3회 다수결)을 규칙 단위로 확장.
- 참고 열(점수 미반영): 비용, 시간, 자체 테스트 수, 분기 수, 압축 횟수, C의 FIX·REDO·BLOCKED, 인수 테스트 실패 유형.

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| 기능이 너무 커서 A·B가 컨텍스트 압축·중도 포기 | 그 자체가 측정 대상. 종료 상태·압축 횟수를 기록하고, 시간 초과 시 그 시점 결과로 채점 |
