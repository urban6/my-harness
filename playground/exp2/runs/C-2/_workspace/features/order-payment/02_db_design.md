# 02. DB 설계 — order-payment

- DB: PostgreSQL(테스트 `postgres:16-alpine`) / 마이그레이션: Flyway / ORM: JPA(Hibernate 6, Spring Boot 3.5)
- API 계약: [`01_api_design.md`](./01_api_design.md)
- **필드 ↔ 컬럼 대응표와 제약 ↔ 상태코드 매핑표는 [`01_api_design.md` §16 정합 요약](./01_api_design.md#16-정합-요약-구현검증의-기준표)에만 있다.** 이 문서는 그 표를 복제하지 않는다. 구현·검증은 그 표를 기준으로 삼는다.
- 표기: `[DECISION]` = 설계에서 확정한 것.

---

## 1. 공통 원칙

| 항목 | 규칙 | 근거 |
|---|---|---|
| 금액 | `BIGINT` (Java `long`) | C1 — int 범위 초과 가능 |
| 수량·재고 | `INTEGER` (Java `int`) | 상한 1,000,000 / 1,000 |
| 쿠폰 수량 | `BIGINT` (`total_quantity`, `used_count`) | 상한이 정의되지 않음 |
| 시각 | `TIMESTAMPTZ` (Java `Instant`), µs 정밀도 | C2. 앱이 `truncatedTo(MICROS)` 후 저장 |
| 열거형 | `VARCHAR` + `CHECK (... IN ...)`, JPA `@Enumerated(EnumType.STRING)` | PG native enum은 Hibernate 매핑·마이그레이션 비용이 커서 쓰지 않음 `[DECISION]` |
| PK | `BIGINT GENERATED BY DEFAULT AS IDENTITY`, JPA `GenerationType.IDENTITY` | PostgreSQL 관용. 배치 INSERT 손실은 무시 가능한 규모 |
| 제약 이름 | 모두 명시(`pk_`, `uk_`, `ux_`, `fk_`, `ck_`, `ix_`) | 예외 핸들러가 제약명으로 409를 매핑(01 §11.2) |
| 시간 기준 | DB `now()`를 쓰지 않고 앱 `Clock`이 값을 바인딩 | 01 §1.2 — 컨테이너·앱 시계 차이 회피 |

## 2. 테이블

### 2.1 `products`
| 컬럼 | 타입 | NULL | 기본 | 제약 |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | N | | `pk_products` |
| `name` | VARCHAR(100) | N | | `ck_products_name_not_blank`: `length(btrim(name)) > 0` |
| `price` | BIGINT | N | | `ck_products_price_range`: 1..10,000,000 |
| `stock` | INTEGER | N | | `ck_products_stock_nonneg`: ≥ 0 (상한 1,000,000은 등록 시 입력 검증. 이후 판매·환불로 원래 값을 넘지 않음) |
| `reserved` | INTEGER | N | 0 | `ck_products_reserved_range`: 0 ≤ reserved ≤ stock — R10.1 최종 안전망 |
| `created_at` | TIMESTAMPTZ | N | | |

- `available`은 저장하지 않는다(`stock − reserved` 계산). 중복 저장이 낳는 불일치를 원천 차단한다.

### 2.2 `coupons`
| 컬럼 | 타입 | NULL | 기본 | 제약 |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | N | | `pk_coupons` |
| `code` | VARCHAR(20) | N | | `uk_coupons_code` UNIQUE (→ 409 DUPLICATE_COUPON_CODE), `ck_coupons_code_format`: `^[A-Z0-9]{4,20}$` |
| `discount_type` | VARCHAR(10) | N | | `ck_coupons_discount_type`: FIXED/RATE |
| `discount_value` | BIGINT | N | | `ck_coupons_discount_value`: ≥ 1, RATE면 ≤ 100 |
| `min_order_amount` | BIGINT | N | 0 | `ck_coupons_min_order_amount`: ≥ 0 |
| `max_discount_amount` | BIGINT | **Y** | | `ck_coupons_max_discount_amount`: NULL 또는 ≥ 1 (NULL = 무제한) |
| `total_quantity` | BIGINT | N | | `ck_coupons_total_quantity`: ≥ 1 |
| `used_count` | BIGINT | N | 0 | `ck_coupons_used_count`: 0 ≤ used_count ≤ total_quantity — R10.2 최종 안전망 |
| `valid_from` | TIMESTAMPTZ | N | | |
| `valid_until` | TIMESTAMPTZ | N | | `ck_coupons_validity`: valid_from < valid_until |
| `created_at` | TIMESTAMPTZ | N | | |

- `[DECISION]` API 필드 `type`/`value`를 `discount_type`/`discount_value` 컬럼에 매핑한다. `value`·`type`은 SQL 키워드여서 방언·도구에 따라 따옴표가 필요할 수 있으므로 피한다.
- `[DECISION]` PK는 대리키 `id`이고, `code`는 UNIQUE 자연키다. 주문은 `code`로 FK를 건다(코드는 수정이 범위 밖이라 불변). 그래서 주문 응답의 `couponCode`를 조인 없이 바로 낼 수 있다.

### 2.3 `orders`
| 컬럼 | 타입 | NULL | 기본 | 제약 |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | N | | `pk_orders` |
| `user_id` | VARCHAR(50) | N | | `ck_orders_user_id_not_blank` |
| `status` | VARCHAR(20) | N | | `ck_orders_status`: 8개 상태 |
| `coupon_code` | VARCHAR(20) | **Y** | | `fk_orders_coupon_code` → `coupons(code)` |
| `subtotal` | BIGINT | N | | `ck_orders_amounts` |
| `discount` | BIGINT | N | | `ck_orders_amounts`, `ck_orders_discount_requires_coupon` |
| `total_price` | BIGINT | N | | `ck_orders_amounts`: = subtotal − discount |
| `payment_id` | VARCHAR(255) | Y | | PG `paymentId`(승인·거절 시 저장, 환불에 사용). totalPrice=0 결제면 NULL |
| `created_at` | TIMESTAMPTZ | N | | 불변 — 목록 커서 키 |
| `expires_at` | TIMESTAMPTZ | N | | `ck_orders_expires_after_created`: > created_at |
| `paid_at` | TIMESTAMPTZ | Y | | `ck_orders_paid_at`: PAID·SHIPPED·DELIVERED·REFUNDED ⇔ NOT NULL |
| `updated_at` | TIMESTAMPTZ | N | | 전이마다 갱신 |

**활성 쿠폰 사용 = `status IN ('PENDING_PAYMENT','PAID','SHIPPED','DELIVERED')`** (R2.6에서 복원되는 4개 상태의 여집합).

### 2.4 `order_items`
| 컬럼 | 타입 | NULL | 제약 |
|---|---|---|---|
| `order_id` | BIGINT | N | `fk_order_items_order` → orders(id) |
| `line_no` | INTEGER | N | 0-based 요청 순서. `ck_order_items_line_no`: 0..19 |
| `product_id` | BIGINT | N | `fk_order_items_product` → products(id) |
| `quantity` | INTEGER | N | `ck_order_items_quantity`: 1..1000 |
| `unit_price` | BIGINT | N | `ck_order_items_unit_price`: ≥ 1 (주문 시점 가격 복사) |
- PK `pk_order_items (order_id, line_no)`, UNIQUE `uk_order_items_order_product (order_id, product_id)`.

### 2.5 `idempotency_records`
| 컬럼 | 타입 | NULL | 제약 |
|---|---|---|---|
| `id` | BIGINT IDENTITY | N | `pk_idempotency_records` |
| `scope` | VARCHAR(20) | N | `ck_idempotency_scope`: ORDER_CREATE / ORDER_PAY |
| `idempotency_key` | VARCHAR(64) | N | `uk_idempotency_scope_key (scope, idempotency_key)` — `ON CONFLICT` 대상 |
| `request_fingerprint` | VARCHAR(64) | N | SHA-256 hex (01 §6.3) |
| `status` | VARCHAR(20) | N | `ck_idempotency_status`: IN_PROGRESS / COMPLETED |
| `response_status` | INTEGER | Y | `ck_idempotency_response_status`: NULL 또는 200..299 (2xx만 저장 — R4.4) |
| `response_body` | TEXT | Y | 직렬화된 JSON 원문(재생 시 그대로 출력). JSONB는 키 순서를 바꾸므로 쓰지 않음 |
| `response_location` | VARCHAR(255) | Y | Location 경로(E5만, 예 `/api/orders/42`) |
| `created_at` | TIMESTAMPTZ | N | |
| `completed_at` | TIMESTAMPTZ | Y | |
- `ck_idempotency_completed`: `(status = 'COMPLETED') = (response_status IS NOT NULL AND response_body IS NOT NULL AND completed_at IS NOT NULL)`.
- 만료·청소는 하지 않는다(멱등 키 만료는 범위 밖).

## 3. 인덱스와 용도

| 인덱스 | 정의 | 용도 |
|---|---|---|
| `ix_orders_created_id` | orders (created_at DESC, id DESC) | 필터 없는 목록, 키셋 커서(R9.4/R9.5) |
| `ix_orders_user_created_id` | orders (user_id, created_at DESC, id DESC) | `userId` 필터 목록 |
| `ix_orders_status_created_id` | orders (status, created_at DESC, id DESC) | `status` 필터 목록 |
| `ix_orders_pending_expires` | orders (expires_at) WHERE status = 'PENDING_PAYMENT' | 만료 스캔(R6) — 대기 주문만 담는 작은 부분 인덱스 |
| `ux_orders_active_coupon_user` | UNIQUE orders (coupon_code, user_id) WHERE coupon_code IS NOT NULL AND status IN (활성 4개) | R2.5 "같은 사용자가 사용 중인 주문 없음"의 DB 보증 + 그 존재 확인 쿼리의 인덱스(R10.3) |
| `ix_order_items_product_id` | order_items (product_id) | FK 역참조 |
| `uk_order_items_order_product` | UNIQUE (order_id, product_id) | 같은 상품 중복 금지(R3.2) |
| `uk_coupons_code` | UNIQUE coupons (code) | R2.2 중복 409 + 코드 조회 |
| `uk_idempotency_scope_key` | UNIQUE (scope, idempotency_key) | R4 키 공간 |

- `ux_orders_active_coupon_user`는 주문이 CANCELLED·EXPIRED·PAYMENT_FAILED·REFUNDED로 바뀌는 순간 인덱스에서 빠진다. 그래서 같은 사용자가 쿠폰을 다시 쓸 수 있다(R2.6). 비활성에서 활성으로 돌아가는 전이는 없다.

## 4. Flyway 마이그레이션

파일: **`src/main/resources/db/migration/V1__init.sql`** (`.gitkeep`이 있는 기존 디렉터리. Flyway 기본 위치 `classpath:db/migration`)

```sql
-- V1__init.sql — order-payment 초기 스키마
-- 금액 BIGINT(C1), 시각 TIMESTAMPTZ(C2). 제약 이름은 예외 매핑(01_api_design.md §11.2)에 쓰이므로 바꾸지 말 것.

-- ---------------------------------------------------------------------------
-- products
-- ---------------------------------------------------------------------------
CREATE TABLE products (
    id          BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    name        VARCHAR(100) NOT NULL,
    price       BIGINT       NOT NULL,
    stock       INTEGER      NOT NULL,
    reserved    INTEGER      NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_products                 PRIMARY KEY (id),
    CONSTRAINT ck_products_name_not_blank  CHECK (length(btrim(name)) > 0),
    CONSTRAINT ck_products_price_range     CHECK (price BETWEEN 1 AND 10000000),
    CONSTRAINT ck_products_stock_nonneg    CHECK (stock >= 0),
    CONSTRAINT ck_products_reserved_range  CHECK (reserved >= 0 AND reserved <= stock)
);

-- ---------------------------------------------------------------------------
-- coupons
-- ---------------------------------------------------------------------------
CREATE TABLE coupons (
    id                   BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    code                 VARCHAR(20)  NOT NULL,
    discount_type        VARCHAR(10)  NOT NULL,
    discount_value       BIGINT       NOT NULL,
    min_order_amount     BIGINT       NOT NULL DEFAULT 0,
    max_discount_amount  BIGINT,
    total_quantity       BIGINT       NOT NULL,
    used_count           BIGINT       NOT NULL DEFAULT 0,
    valid_from           TIMESTAMPTZ  NOT NULL,
    valid_until          TIMESTAMPTZ  NOT NULL,
    created_at           TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_coupons                      PRIMARY KEY (id),
    CONSTRAINT uk_coupons_code                 UNIQUE (code),
    CONSTRAINT ck_coupons_code_format          CHECK (code ~ '^[A-Z0-9]{4,20}$'),
    CONSTRAINT ck_coupons_discount_type        CHECK (discount_type IN ('FIXED', 'RATE')),
    CONSTRAINT ck_coupons_discount_value       CHECK (discount_value >= 1
                                                      AND (discount_type <> 'RATE' OR discount_value <= 100)),
    CONSTRAINT ck_coupons_min_order_amount     CHECK (min_order_amount >= 0),
    CONSTRAINT ck_coupons_max_discount_amount  CHECK (max_discount_amount IS NULL OR max_discount_amount >= 1),
    CONSTRAINT ck_coupons_total_quantity       CHECK (total_quantity >= 1),
    CONSTRAINT ck_coupons_used_count           CHECK (used_count >= 0 AND used_count <= total_quantity),
    CONSTRAINT ck_coupons_validity             CHECK (valid_from < valid_until)
);

-- ---------------------------------------------------------------------------
-- orders
-- ---------------------------------------------------------------------------
CREATE TABLE orders (
    id           BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    user_id      VARCHAR(50)  NOT NULL,
    status       VARCHAR(20)  NOT NULL,
    coupon_code  VARCHAR(20),
    subtotal     BIGINT       NOT NULL,
    discount     BIGINT       NOT NULL,
    total_price  BIGINT       NOT NULL,
    payment_id   VARCHAR(255),
    created_at   TIMESTAMPTZ  NOT NULL,
    expires_at   TIMESTAMPTZ  NOT NULL,
    paid_at      TIMESTAMPTZ,
    updated_at   TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_orders                          PRIMARY KEY (id),
    CONSTRAINT fk_orders_coupon_code              FOREIGN KEY (coupon_code) REFERENCES coupons (code),
    CONSTRAINT ck_orders_user_id_not_blank        CHECK (length(btrim(user_id)) > 0),
    CONSTRAINT ck_orders_status                   CHECK (status IN ('PENDING_PAYMENT', 'PAID', 'PAYMENT_FAILED',
                                                                    'EXPIRED', 'CANCELLED', 'SHIPPED',
                                                                    'DELIVERED', 'REFUNDED')),
    CONSTRAINT ck_orders_amounts                  CHECK (subtotal >= 1
                                                         AND discount >= 0
                                                         AND discount <= subtotal
                                                         AND total_price = subtotal - discount),
    CONSTRAINT ck_orders_discount_requires_coupon CHECK (coupon_code IS NOT NULL OR discount = 0),
    CONSTRAINT ck_orders_expires_after_created    CHECK (expires_at > created_at),
    CONSTRAINT ck_orders_paid_at                  CHECK ((paid_at IS NOT NULL)
                                                         = (status IN ('PAID', 'SHIPPED', 'DELIVERED', 'REFUNDED')))
);

-- 목록 키셋 정렬 (R9.4 / R9.5)
CREATE INDEX ix_orders_created_id        ON orders (created_at DESC, id DESC);
CREATE INDEX ix_orders_user_created_id   ON orders (user_id, created_at DESC, id DESC);
CREATE INDEX ix_orders_status_created_id ON orders (status, created_at DESC, id DESC);

-- 만료 스캔 (R6)
CREATE INDEX ix_orders_pending_expires   ON orders (expires_at)
    WHERE status = 'PENDING_PAYMENT';

-- 사용자별 쿠폰 활성 사용 유일성 (R2.5 / R2.6 / R10.3)
CREATE UNIQUE INDEX ux_orders_active_coupon_user ON orders (coupon_code, user_id)
    WHERE coupon_code IS NOT NULL
      AND status IN ('PENDING_PAYMENT', 'PAID', 'SHIPPED', 'DELIVERED');

-- ---------------------------------------------------------------------------
-- order_items
-- ---------------------------------------------------------------------------
CREATE TABLE order_items (
    order_id    BIGINT   NOT NULL,
    line_no     INTEGER  NOT NULL,
    product_id  BIGINT   NOT NULL,
    quantity    INTEGER  NOT NULL,
    unit_price  BIGINT   NOT NULL,
    CONSTRAINT pk_order_items                PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_items_order          FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product        FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT uk_order_items_order_product  UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_line_no        CHECK (line_no BETWEEN 0 AND 19),
    CONSTRAINT ck_order_items_quantity       CHECK (quantity BETWEEN 1 AND 1000),
    CONSTRAINT ck_order_items_unit_price     CHECK (unit_price >= 1)
);

CREATE INDEX ix_order_items_product_id ON order_items (product_id);

-- ---------------------------------------------------------------------------
-- idempotency_records (R4)
-- ---------------------------------------------------------------------------
CREATE TABLE idempotency_records (
    id                   BIGINT        GENERATED BY DEFAULT AS IDENTITY,
    scope                VARCHAR(20)   NOT NULL,
    idempotency_key      VARCHAR(64)   NOT NULL,
    request_fingerprint  VARCHAR(64)   NOT NULL,
    status               VARCHAR(20)   NOT NULL,
    response_status      INTEGER,
    response_body        TEXT,
    response_location    VARCHAR(255),
    created_at           TIMESTAMPTZ   NOT NULL,
    completed_at         TIMESTAMPTZ,
    CONSTRAINT pk_idempotency_records          PRIMARY KEY (id),
    CONSTRAINT uk_idempotency_scope_key        UNIQUE (scope, idempotency_key),
    CONSTRAINT ck_idempotency_scope            CHECK (scope IN ('ORDER_CREATE', 'ORDER_PAY')),
    CONSTRAINT ck_idempotency_status           CHECK (status IN ('IN_PROGRESS', 'COMPLETED')),
    CONSTRAINT ck_idempotency_response_status  CHECK (response_status IS NULL OR response_status BETWEEN 200 AND 299),
    CONSTRAINT ck_idempotency_completed        CHECK ((status = 'COMPLETED')
                                                      = (response_status IS NOT NULL
                                                         AND response_body IS NOT NULL
                                                         AND completed_at IS NOT NULL))
);
```

- 이후 스키마 변경은 `V2__….sql`로 추가한다. 적용된 V1은 고치지 않는다(Flyway 체크섬).
- Testcontainers DB는 테스트 시작 때마다 비어 있으므로 V1이 매번 적용된다. 테스트 간 데이터 격리는 테스트 쪽 책임이다(각 테스트가 고유한 상품·쿠폰 코드·사용자·멱등 키를 만들어 쓰는 방식을 권장한다. 스케줄러가 돌고 있으므로 `TRUNCATE`는 피한다).

## 5. 엔티티 매핑 지침

공통: `jakarta.persistence.*`, `protected` 기본 생성자, setter 대신 의도를 드러내는 도메인 메서드, `ddl-auto: validate` 통과(아래 Java 타입 ↔ DB 타입을 정확히 맞출 것).

### 5.1 `Product` (`@Table(name = "products")`)
| 필드 | Java | 매핑 |
|---|---|---|
| id | `Long` | `@Id @GeneratedValue(strategy = IDENTITY)` |
| name | `String` | `@Column(nullable=false, length=100)` |
| price | `long` | |
| stock | `int` | |
| reserved | `int` | |
| createdAt | `Instant` | `@Column(nullable=false, updatable=false)` |

도메인 메서드: `available()`, `reserve(q)`(available 부족이면 예외), `releaseReservation(q)`, `confirmSale(q)`(stock −q, reserved −q), `restock(q)`(stock +q).

### 5.2 `Coupon` (`@Table(name = "coupons")`)
| 필드 | Java | 매핑 |
|---|---|---|
| id | `Long` | IDENTITY |
| code | `String` | `@Column(nullable=false, unique=true, length=20, updatable=false)` |
| type | `CouponType` | `@Enumerated(STRING) @Column(name="discount_type", length=10)` |
| value | `long` | `@Column(name="discount_value")` |
| minOrderAmount | `long` | |
| maxDiscountAmount | `Long` | nullable |
| totalQuantity | `long` | |
| usedCount | `long` | |
| validFrom / validUntil / createdAt | `Instant` | |

도메인 메서드: `isValidAt(Instant now)`(`!now.isBefore(validFrom) && now.isBefore(validUntil)`), `calculateDiscount(long subtotal)`(01 §5), `isExhausted()`, `use()`, `release()`.

### 5.3 `Order` (`@Table(name = "orders")` — `order`는 예약어이므로 테이블 이름을 반드시 명시)
| 필드 | Java | 매핑 |
|---|---|---|
| id | `Long` | IDENTITY |
| userId | `String` | `length=50, updatable=false` |
| status | `OrderStatus` | `@Enumerated(STRING) length=20` |
| couponCode | `String` | nullable, `updatable=false`. **연관관계 없이 문자열로 둔다** — 쿠폰 행 락은 리포지토리로 따로 잡는다 |
| subtotal / discount / totalPrice | `long` | `updatable=false` |
| paymentId | `String` | nullable |
| createdAt / expiresAt | `Instant` | `updatable=false` (R9.5 불변 보장) |
| paidAt | `Instant` | nullable |
| updatedAt | `Instant` | 전이 메서드에서 갱신 |
| items | `List<OrderLine>` | `@ElementCollection(fetch = LAZY) @CollectionTable(name="order_items", joinColumns=@JoinColumn(name="order_id")) @OrderColumn(name="line_no")` |

`OrderLine`은 `@Embeddable`(`productId: Long` → `product_id`, `quantity: int`, `unitPrice: long` → `unit_price`)이고 불변이다(생성 후 컬렉션을 수정하지 않는다. 수정하면 Hibernate가 삭제 후 재삽입할 수 있다). 상품은 연관관계 없이 id로만 참조한다.
전이 메서드: `markPaid(now, paymentId)`, `markPaymentFailed(paymentId)`, `expire(now)`, `cancel(now)`, `refund(now)`, `ship(now)`, `deliver(now)`. 허용되지 않는 전이는 `InvalidOrderStateException`이다(01 §13 표가 기준).

### 5.4 `IdempotencyRecord`
- `[DECISION]` JPA 엔티티로 만들지 않고 `JdbcTemplate` 기반 `IdempotencyRepository`로 다룬다. `INSERT … ON CONFLICT DO NOTHING RETURNING id`와 조건부 `UPDATE/DELETE … WHERE status='IN_PROGRESS'`를 SQL 그대로 드러내기 위해서다.
- JPA 트랜잭션(`JpaTransactionManager`) 안에서 `JdbcTemplate`을 호출하면 같은 커넥션·트랜잭션에 참여한다(COMPLETED 갱신이 비즈니스 반영과 원자적 — 01 §6.4 ②).
- 엔티티가 없으므로 `ddl-auto: validate` 대상이 아니다.

### 5.5 락 전략 (비관적 락 전용, `@Version` 없음)
| 리포지토리 메서드 | 쿼리 | 락 |
|---|---|---|
| `ProductRepository.findAllByIdInForUpdate(ids)` | `select p from Product p where p.id in :ids order by p.id` | `@Lock(PESSIMISTIC_WRITE)` → `FOR NO KEY UPDATE`, **id 오름차순** |
| `CouponRepository.findByCodeForUpdate(code)` | `select c from Coupon c where c.code = :code` | `@Lock(PESSIMISTIC_WRITE)` |
| `OrderRepository.findByIdForUpdate(id)` | `select o from Order o where o.id = :id` | `@Lock(PESSIMISTIC_WRITE)` |
| `OrderRepository.findExpiredIds(now, limit)` | `status='PENDING_PAYMENT' and expiresAt <= :now order by expiresAt, id` | 없음 |
| `OrderRepository.lockForExpiration(id)` | native `SELECT * FROM orders WHERE id = :id FOR UPDATE SKIP LOCKED` | SKIP LOCKED (또는 JPA 힌트 `jakarta.persistence.lock.timeout = -2`) |
| `OrderRepository.existsActiveCouponUse(code, userId)` | `exists … where couponCode=:code and userId=:userId and status in (활성 4개)` | 없음(쿠폰 행 락 뒤에 실행 → 최신 커밋을 봄) |

- 전역 락 순서: **orders → products(id 오름차순) → coupons** (01 §10.1).
- 락 조회가 그 트랜잭션에서 해당 엔티티의 **첫 로딩**이어야 한다(1차 캐시의 오래된 상태 방지).
- 격리 수준은 READ COMMITTED(기본) 그대로 둔다.
- `@Version`을 쓰지 않는 이유: 모든 갱신 경로가 비관적 락으로 직렬화되므로 필요 없고, 처리되지 않은 낙관적 락 예외가 5xx가 될 위험만 생긴다(R10.4 "5xx 없이").

### 5.6 시각
- 엔티티는 `Instant`이고, Hibernate 6는 PostgreSQL에서 이를 `timestamp(6) with time zone`으로 매핑한다(validate 통과). `hibernate.jdbc.time_zone: UTC`.
- 생성하는 모든 시각은 `clock.instant().truncatedTo(ChronoUnit.MICROS)`로 만든다(201 응답 값과 DB 값을 같게 하기 위해서 — 01 §1.2).

### 5.7 `ddl-auto: validate` 주의
- `products.stock`/`reserved`, `order_items.quantity`/`line_no`는 `INTEGER`이므로 Java `int`/`Integer`, 금액·쿠폰 수량은 `long`/`Long`이어야 한다. 하나라도 어긋나면 기동 시 스키마 검증이 실패한다.
- 열거형 컬럼은 `VARCHAR`이다. `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`을 쓰지 말 것.
