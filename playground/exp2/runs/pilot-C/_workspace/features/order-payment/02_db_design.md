# 02. DB 설계 — order-payment

- DB: PostgreSQL (Testcontainers `postgres:16-alpine` 권장)
- 마이그레이션: Flyway, `src/main/resources/db/migration/V1__init.sql` (단일 파일)
- 스키마 단일 출처: Flyway. `spring.jpa.hibernate.ddl-auto: none` (01 문서 0.6)
- **응답 필드 ↔ 컬럼 대응, 제약 ↔ HTTP 상태·code 매핑은 [01_api_design.md 7장 정합 요약](./01_api_design.md#7-정합-요약-구현검증-기준표)이 유일한 기준이다.** 이 문서는 복제하지 않는다.

---

## 1. 타입 관례

| 대상 | SQL | Java |
|---|---|---|
| 대리키 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `Long` + `@GeneratedValue(strategy = IDENTITY)` |
| 금액 (C1), 쿠폰 수량 | `BIGINT` | `long` / `Long`(nullable) |
| 재고·주문 수량 | `INTEGER` | `int` |
| 시각 (C2) | `TIMESTAMPTZ` (μs 정밀도) | `OffsetDateTime` — 저장 전 UTC 변환 + `truncatedTo(MICROS)` |
| enum | `VARCHAR` + CHECK | `@Enumerated(EnumType.STRING)` |
| 긴 텍스트 | `TEXT` | `String` + `@Column(columnDefinition = "text")` (`@Lob` 금지 — PG에서 OID가 됨) |

- `hibernate.jdbc.time_zone: UTC` 설정.
- 엔티티 클래스명: `Product`, `Coupon`, `OrderEntity`(`@Table(name = "orders")` — JPQL 예약어 `Order` 회피), `OrderItem`. `idempotency_keys`는 `JdbcTemplate`로만 접근(엔티티 불필요).

## 2. 테이블

### 2.1 `products`
| 컬럼 | 타입 | null | 기본 | 설명 |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | N | | PK |
| `name` | VARCHAR(100) | N | | |
| `price` | BIGINT | N | | 1 ~ 10,000,000 |
| `stock` | INTEGER | N | | 판매되지 않은 보유 수량 (생성 시 0 ~ 1,000,000) |
| `reserved` | INTEGER | N | 0 | 결제 대기 예약 수량 |
| `created_at` | TIMESTAMPTZ | N | | |

`available`은 저장하지 않는다(`stock - reserved`).

### 2.2 `coupons`

|---|---|---|---|---|
| `id` | BIGINT IDENTITY | N | | PK (대리키 — 할당 키 `code`를 `@Id`로 쓰면 `save()`가 merge로 동작해 중복 insert를 덮어쓰므로 회피) |

| `discount_type` | VARCHAR(10) | N | | `FIXED` \| `RATE` |
| `discount_value` | BIGINT | N | | FIXED: 원(≥1), RATE: 1~100 |
| `min_order_amount` | BIGINT | N | 0 | ≥ 0 |
| `max_discount_amount` | BIGINT | Y | | NULL = 상한 없음, 있으면 ≥ 1 |
| `total_quantity` | BIGINT | N | | ≥ 1 |
| `used_count` | BIGINT | N | 0 | 사용 중 주문 수, 0 ≤ used_count ≤ total_quantity |
| `valid_from` | TIMESTAMPTZ | N | | |
| `valid_until` | TIMESTAMPTZ | N | | valid_from < valid_until |
| `created_at` | TIMESTAMPTZ | N | | |

### 2.3 `orders`
| 컬럼 | 타입 | null | 기본 | 설명 |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | N | | PK |
| `user_id` | VARCHAR(50) | N | | `X-User-Id` |
| `status` | VARCHAR(20) | N | | 8개 상태 |
| `coupon_code` | VARCHAR(20) | Y | | FK → `coupons(code)` |
| `subtotal` | BIGINT | N | | |
| `discount` | BIGINT | N | | |
| `total_price` | BIGINT | N | | = subtotal − discount |
| `payment_id` | VARCHAR(255) | Y | | PG paymentId (환불용, 응답 미노출). 0원 결제면 NULL |
| `created_at` | TIMESTAMPTZ | N | | 커서 키 |
| `expires_at` | TIMESTAMPTZ | N | | created_at + TTL |
| `paid_at` | TIMESTAMPTZ | Y | | 승인 시각 |

"쿠폰 사용 중" 상태 집합 = `PENDING_PAYMENT`, `PAID`, `SHIPPED`, `DELIVERED` (R2.6의 복원 상태 4개의 여집합).

### 2.4 `order_items`
| 컬럼 | 타입 | null | 설명 |
|---|---|---|---|
| `id` | BIGINT IDENTITY | N | PK |
| `order_id` | BIGINT | N | FK → `orders(id)` |
| `line_no` | INTEGER | N | 요청 내 순서 0..n-1 (응답 items 순서) |
| `product_id` | BIGINT | N | FK → `products(id)` |
| `quantity` | INTEGER | N | 1 ~ 1,000 |
| `unit_price` | BIGINT | N | 주문 시점 상품 가격 |

JPA: `OrderEntity.items` = `@OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true) @OrderBy("lineNo ASC")`, `OrderItem.order` = `@ManyToOne(fetch = LAZY) @JoinColumn(name = "order_id")`. `product_id`는 연관관계 없이 `long productId` 스칼라로 매핑(상품 락은 별도 쿼리로 획득).

### 2.5 `idempotency_keys`
| 컬럼 | 타입 | null | 설명 |
|---|---|---|---|
| `id` | BIGINT IDENTITY | N | PK |
| `scope` | VARCHAR(20) | N | `CREATE_ORDER` \| `PAY_ORDER` (엔드포인트별 독립 키 공간) |
| `idem_key` | VARCHAR(64) | N | 클라이언트 `Idempotency-Key` |
| `request_hash` | VARCHAR(64) | N | 요청 지문 SHA-256 소문자 hex (01 문서 4.2) |
| `status` | VARCHAR(20) | N | `IN_PROGRESS` \| `COMPLETED` |
| `response_status` | INTEGER | Y | COMPLETED일 때 2xx |
| `response_body` | TEXT | Y | COMPLETED일 때 응답 JSON |
| `response_location` | VARCHAR(255) | Y | 201의 Location |
| `created_at` | TIMESTAMPTZ | N | |
| `completed_at` | TIMESTAMPTZ | Y | |

유니크 `uk_idempotency_scope_key (scope, idem_key)` — `INSERT ... ON CONFLICT (scope, idem_key) DO NOTHING RETURNING id`로 IN_PROGRESS 선점. 오류 종료 시 행 DELETE(선점 해제), 2xx 시 COMPLETED로 UPDATE.

## 3. 인덱스와 용도

| 이름 | 정의 | 용도 |
|---|---|---|
| `uk_coupons_code` | UNIQUE (code) | 쿠폰 조회·중복 방지·FK 대상 |
| `uk_orders_coupon_user_active` | UNIQUE (coupon_code, user_id) WHERE coupon_code IS NOT NULL AND status IN (사용 중 4개) | R2.5/R10.3 "같은 사용자 사용 중 주문 없음"을 DB 수준에서 보장(안전망) + 사전 검사 exists 쿼리 인덱스 |
| `ix_orders_created_id` | (created_at DESC, id DESC) | R9 무필터 키셋 |
| `ix_orders_user_created_id` | (user_id, created_at DESC, id DESC) | R9 userId 필터 |
| `ix_orders_status_created_id` | (status, created_at DESC, id DESC) | R9 status 필터 |
| `ix_orders_pending_expires` | (expires_at) WHERE status = 'PENDING_PAYMENT' | R6 만료 스윕 후보 조회 |
| `uk_order_items_order_line` | UNIQUE (order_id, line_no) | 순서 보존·조회 |
| `uk_order_items_order_product` | UNIQUE (order_id, product_id) | 같은 productId 중복 방지(안전망) |
| `uk_idempotency_scope_key` | UNIQUE (scope, idem_key) | 멱등 선점 |

## 4. 락 규약 (동시성 R10)

| 대상 | 획득 방법 | 순서 |
|---|---|---|
| 주문 행 | `@Lock(PESSIMISTIC_WRITE)` 단건 조회 (스윕은 네이티브 `FOR UPDATE SKIP LOCKED`) | 1 |
| 상품 행 | `@Lock(PESSIMISTIC_WRITE) select p from Product p where p.id in :ids order by p.id asc` — PG는 Sort 후 LockRows이므로 **id 오름차순으로 락** | 2 |
| 쿠폰 행 | `@Lock(PESSIMISTIC_WRITE) select c from Coupon c where c.code = :code` | 3 |

- 전역 순서: 주문 → 상품(오름차순) → 쿠폰. 한 트랜잭션에서 여러 주문의 상품을 섞어 잠그지 않는다(스윕은 주문당 트랜잭션 1개).
- Hibernate 6의 PG `PESSIMISTIC_WRITE`는 `FOR NO KEY UPDATE`로 나갈 수 있다. 행 간 상호 배제는 동일하므로 문제없음.
- 격리 수준: 기본 READ COMMITTED. 쿠폰 락 획득 후 실행하는 "같은 사용자 사용 중" exists 쿼리는 새 문장 스냅샷이라 선행 커밋을 본다.
- `uk_orders_coupon_user_active`는 사전 검사가 정상이면 위반되지 않는다. 위반 시 409 COUPON_NOT_APPLICABLE로 매핑(01 문서 6.3).
- CHECK 제약(`ck_products_reserved`, `ck_coupons_used_count` 등)은 최종 방어선이다. 정상 흐름에서 위반되면 사전 검사 누락 버그다.

### 4.1 주요 쿼리
```sql
-- 쿠폰 사용 중 검사 (쿠폰 락 획득 후)
SELECT EXISTS (
  SELECT 1 FROM orders
  WHERE coupon_code = :code AND user_id = :userId
    AND status IN ('PENDING_PAYMENT','PAID','SHIPPED','DELIVERED'));

-- 만료 스윕 후보 (락 없음)
SELECT id FROM orders
WHERE status = 'PENDING_PAYMENT' AND expires_at <= :now
ORDER BY expires_at, id LIMIT 100;

-- 만료 스윕 주문 단건 락 (주문당 트랜잭션)
SELECT * FROM orders
WHERE id = :id AND status = 'PENDING_PAYMENT' AND expires_at <= :now
FOR UPDATE SKIP LOCKED;

-- 멱등 선점
INSERT INTO idempotency_keys (scope, idem_key, request_hash, status, created_at)
VALUES (:scope, :key, :hash, 'IN_PROGRESS', :now)
ON CONFLICT (scope, idem_key) DO NOTHING
RETURNING id;
```

## 5. Flyway 마이그레이션

파일: `src/main/resources/db/migration/V1__init.sql` (기존 `.gitkeep`은 두어도 무방)

```sql
-- V1__init.sql : order-payment 초기 스키마

CREATE TABLE products (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    price       BIGINT       NOT NULL,
    stock       INTEGER      NOT NULL,
    reserved    INTEGER      NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ  NOT NULL,
    CONSTRAINT ck_products_price    CHECK (price BETWEEN 1 AND 10000000),
    CONSTRAINT ck_products_stock    CHECK (stock >= 0),
    CONSTRAINT ck_products_reserved CHECK (reserved >= 0 AND reserved <= stock)
);

CREATE TABLE coupons (
    id                   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code                 VARCHAR(20)  NOT NULL,
    discount_type        VARCHAR(10)  NOT NULL,
    discount_value       BIGINT       NOT NULL,
    min_order_amount     BIGINT       NOT NULL DEFAULT 0,
    max_discount_amount  BIGINT,
    total_quantity       BIGINT       NOT NULL,
    used_count           BIGINT       NOT NULL DEFAULT 0,
    valid_from           TIMESTAMPTZ  NOT NULL,
    valid_until          TIMESTAMPTZ  NOT NULL,
    created_at           TIMESTAMPTZ  NOT NULL,
    CONSTRAINT uk_coupons_code           UNIQUE (code),
    CONSTRAINT ck_coupons_code           CHECK (code ~ '^[A-Z0-9]{4,20}$'),
    CONSTRAINT ck_coupons_type           CHECK (discount_type IN ('FIXED', 'RATE')),
    CONSTRAINT ck_coupons_value          CHECK (discount_value >= 1
                                                AND (discount_type <> 'RATE' OR discount_value <= 100)),
    CONSTRAINT ck_coupons_min_order      CHECK (min_order_amount >= 0),
    CONSTRAINT ck_coupons_max_discount   CHECK (max_discount_amount IS NULL OR max_discount_amount >= 1),
    CONSTRAINT ck_coupons_total_quantity CHECK (total_quantity >= 1),
    CONSTRAINT ck_coupons_used_count     CHECK (used_count >= 0 AND used_count <= total_quantity),
    CONSTRAINT ck_coupons_valid_range    CHECK (valid_from < valid_until)
);

CREATE TABLE orders (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id      VARCHAR(50)  NOT NULL,
    status       VARCHAR(20)  NOT NULL,
    coupon_code  VARCHAR(20),
    subtotal     BIGINT       NOT NULL,
    discount     BIGINT       NOT NULL,
    total_price  BIGINT       NOT NULL,
    payment_id   VARCHAR(255),
    created_at   TIMESTAMPTZ  NOT NULL,
    expires_at   TIMESTAMPTZ  NOT NULL,
    paid_at      TIMESTAMPTZ,
    CONSTRAINT fk_orders_coupon_code FOREIGN KEY (coupon_code) REFERENCES coupons (code),
    CONSTRAINT ck_orders_status CHECK (status IN (
        'PENDING_PAYMENT', 'PAID', 'PAYMENT_FAILED', 'EXPIRED',
        'CANCELLED', 'REFUNDED', 'SHIPPED', 'DELIVERED')),
    CONSTRAINT ck_orders_amounts CHECK (
        subtotal >= 0 AND discount >= 0 AND discount <= subtotal
        AND total_price = subtotal - discount),
    CONSTRAINT ck_orders_expires CHECK (expires_at >= created_at)
);

CREATE UNIQUE INDEX uk_orders_coupon_user_active
    ON orders (coupon_code, user_id)
    WHERE coupon_code IS NOT NULL
      AND status IN ('PENDING_PAYMENT', 'PAID', 'SHIPPED', 'DELIVERED');

CREATE INDEX ix_orders_created_id        ON orders (created_at DESC, id DESC);
CREATE INDEX ix_orders_user_created_id   ON orders (user_id, created_at DESC, id DESC);
CREATE INDEX ix_orders_status_created_id ON orders (status, created_at DESC, id DESC);
CREATE INDEX ix_orders_pending_expires   ON orders (expires_at) WHERE status = 'PENDING_PAYMENT';

CREATE TABLE order_items (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id    BIGINT  NOT NULL,
    line_no     INTEGER NOT NULL,
    product_id  BIGINT  NOT NULL,
    quantity    INTEGER NOT NULL,
    unit_price  BIGINT  NOT NULL,
    CONSTRAINT fk_order_items_order   FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT uk_order_items_order_line    UNIQUE (order_id, line_no),
    CONSTRAINT uk_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_line_no    CHECK (line_no >= 0),
    CONSTRAINT ck_order_items_quantity   CHECK (quantity BETWEEN 1 AND 1000),
    CONSTRAINT ck_order_items_unit_price CHECK (unit_price >= 1)
);

CREATE TABLE idempotency_keys (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scope              VARCHAR(20)  NOT NULL,
    idem_key           VARCHAR(64)  NOT NULL,
    request_hash       VARCHAR(64)  NOT NULL,
    status             VARCHAR(20)  NOT NULL,
    response_status    INTEGER,
    response_body      TEXT,
    response_location  VARCHAR(255),
    created_at         TIMESTAMPTZ  NOT NULL,
    completed_at       TIMESTAMPTZ,
    CONSTRAINT uk_idempotency_scope_key UNIQUE (scope, idem_key),
    CONSTRAINT ck_idempotency_scope  CHECK (scope IN ('CREATE_ORDER', 'PAY_ORDER')),
    CONSTRAINT ck_idempotency_status CHECK (status IN ('IN_PROGRESS', 'COMPLETED')),
    CONSTRAINT ck_idempotency_completed CHECK (
        status <> 'COMPLETED'
        OR (response_status BETWEEN 200 AND 299 AND response_body IS NOT NULL))
);
```

## 6. 구현 메모 (엔티티 ↔ DDL)

- 컬럼명은 위 DDL과 **정확히 일치**시킨다(Boot 기본 `CamelCaseToUnderscoresNamingStrategy`로 `discountType` → `discount_type` 등 자동 대응되지만, 예약어 회피 컬럼(`discount_type`, `discount_value`, `idem_key`)은 필드명을 그대로 두거나 `@Column(name=...)`를 명시).
- `ddl-auto: none`이므로 매핑 오류는 기동 시 잡히지 않는다. 각 엔티티를 저장·재조회하는 통합 테스트(저장 후 GET)로 컬럼 정합을 확인한다.
- 시각 필드 setter/팩토리에서 UTC·μs 정규화를 강제한다(01 문서 0.1).
- 테스트: Testcontainers PostgreSQL 컨테이너는 **JVM당 1개 싱글턴**(static 시작 + `@DynamicPropertySource` 또는 `@ServiceConnection`)으로 공유. 테스트 간 데이터 격리는 고유 code/userId 사용 또는 `TRUNCATE ... RESTART IDENTITY CASCADE`(스윕 스케줄러와 경합하지 않도록 주의).
