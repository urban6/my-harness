# 02. DB 설계 — order-payment

- DB: PostgreSQL · 마이그레이션: Flyway `src/main/resources/db/migration/V1__init.sql`
- JPA: Hibernate 6 (`ddl-auto: validate`, `hibernate.jdbc.time_zone: UTC`)
- **필드 ↔ 컬럼 대응표와 제약 ↔ 상태코드 매핑표는 [01_api_design.md §12 정합 요약](./01_api_design.md#12-정합-요약)이 유일한 기준이다.** 여기에는 복제하지 않는다.

---

## 1. 테이블 개요

| 테이블 | 엔티티 (패키지) | 역할 |
|---|---|---|
| products | `Product` (`com.example.order.product`) | 상품·재고·예약 수량 |
| coupons | `Coupon` (`com.example.order.coupon`) | 쿠폰 정책·사용 수 |
| orders | `Order` (`com.example.order.order`, `@Table(name="orders")`) | 주문 헤더·금액·상태·PG 결제 ID |
| order_items | `OrderItem` (`com.example.order.order`) | 주문 항목(주문 시점 단가) |
| idempotency_records | `IdempotencyRecord` (`com.example.order.idempotency`) | 멱등 키 클레임·응답 저장 |

## 2. 타입 규칙

- 금액 → `BIGINT` / Java `long`(C1). 수량·재고·카운트 → `INTEGER` / `int`.
- 시각 → `TIMESTAMPTZ` / `Instant`. **모든 시각은 저장 전 `truncatedTo(ChronoUnit.MICROS)`** (01 §0.1). Hibernate 6은 `Instant`를 `timestamp(6) with time zone`으로 매핑한다.
- enum → `VARCHAR` + `@Enumerated(EnumType.STRING)` + CHECK 제약.
- PK → `BIGINT GENERATED BY DEFAULT AS IDENTITY` / `@GeneratedValue(strategy = IDENTITY)`.
- 문자열은 `VARCHAR(n)`(`CHAR` 금지 — `validate`에서 bpchar 불일치). 큰 문자열은 `TEXT` + `@Column(columnDefinition = "text")`.
- `stock`/`reserved`/`used_count`는 엔티티 필드를 직접 증감한다(락으로 보호되므로 원자적 UPDATE 불필요). 낙관적 락 `@Version`은 쓰지 않는다.

## 3. 테이블 상세

### products
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| name | VARCHAR(100) | NOT NULL |
| price | BIGINT | NOT NULL, `1..10,000,000` |
| stock | INTEGER | NOT NULL, `≥ 0` |
| reserved | INTEGER | NOT NULL DEFAULT 0, `0 ≤ reserved ≤ stock` |

stock 상한 1,000,000은 등록 시 DTO에서만 검증(환불로 stock이 늘어도 최초 등록값을 넘지 않음).

### coupons
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK (비노출) |
| code | VARCHAR(20) | NOT NULL, UNIQUE `uk_coupons_code`, `^[A-Z0-9]{4,20}$` |
| discount_type | VARCHAR(10) | NOT NULL, `FIXED`/`RATE` |
| discount_value | BIGINT | NOT NULL, `≥ 1`, RATE면 `≤ 100` |
| min_order_amount | BIGINT | NOT NULL DEFAULT 0, `≥ 0` |
| max_discount_amount | BIGINT | NULL(제한 없음), 있으면 `≥ 1` |
| total_quantity | INTEGER | NOT NULL, `≥ 1` |
| used_count | INTEGER | NOT NULL DEFAULT 0, `0 ≤ used_count ≤ total_quantity` |
| valid_from | TIMESTAMPTZ | NOT NULL |
| valid_until | TIMESTAMPTZ | NOT NULL, `valid_from < valid_until` |

`value`·`type` 대신 `discount_value`·`discount_type`을 컬럼명으로 쓴다(키워드 회피). JSON 이름은 `value`·`type` 그대로.

### orders
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| user_id | VARCHAR(50) | NOT NULL |
| status | VARCHAR(20) | NOT NULL, 8개 상태 CHECK |
| coupon_code | VARCHAR(20) | NULL, FK → coupons(code) |
| subtotal | BIGINT | NOT NULL, `≥ 0` |
| discount | BIGINT | NOT NULL, `0 ≤ discount ≤ subtotal` |
| total_price | BIGINT | NOT NULL, `= subtotal − discount` |
| pg_payment_id | VARCHAR(100) | NULL. PG 결제 ID(환불용, 비노출). totalPrice=0 결제는 NULL |
| created_at | TIMESTAMPTZ | NOT NULL |
| expires_at | TIMESTAMPTZ | NOT NULL (`created_at + TTL`) |
| paid_at | TIMESTAMPTZ | NULL |

- 엔티티: `couponCode`는 `String` 컬럼(연관관계 매핑 안 함). `items`는 `@OneToMany(mappedBy="order", cascade=ALL) @OrderBy("lineNo ASC") List<OrderItem>`.
- 인덱스
  - `ix_orders_created_id (created_at DESC, id DESC)` — 필터 없는 목록 키셋
  - `ix_orders_user_created_id (user_id, created_at DESC, id DESC)` — userId 필터
  - `ix_orders_status_created_id (status, created_at DESC, id DESC)` — status 필터
  - `ix_orders_pending_expires (expires_at) WHERE status='PENDING_PAYMENT'` — 만료 스윕
  - `ux_orders_user_coupon_active UNIQUE (user_id, coupon_code) WHERE coupon_code IS NOT NULL AND status IN ('PENDING_PAYMENT','PAID','SHIPPED','DELIVERED')` — "같은 사용자가 이 쿠폰을 사용 중인 주문은 최대 1건"(R2.5, R10.3)의 DB 차원 방어선. 1차 판정은 쿠폰 행 락 하의 조회.

### order_items
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK (비노출) |
| order_id | BIGINT | NOT NULL, FK → orders(id) |
| line_no | INTEGER | NOT NULL, `≥ 0` (요청 순서) |
| product_id | BIGINT | NOT NULL, FK → products(id) |
| quantity | INTEGER | NOT NULL, `1..1000` |
| unit_price | BIGINT | NOT NULL, `≥ 1` |

UNIQUE `(order_id, line_no)`, UNIQUE `(order_id, product_id)`(중복 상품 금지 방어). 인덱스 `ix_order_items_order (order_id)`는 유니크 인덱스가 겸한다.

### idempotency_records
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| scope | VARCHAR(20) | NOT NULL, `CREATE_ORDER`/`PAY_ORDER` |
| idem_key | VARCHAR(64) | NOT NULL |
| fingerprint | VARCHAR(64) | NOT NULL (SHA-256 hex) |
| status | VARCHAR(20) | NOT NULL, `IN_PROGRESS`/`COMPLETED` |
| response_status | INTEGER | NULL (COMPLETED면 NOT NULL) |
| response_body | TEXT | NULL (COMPLETED면 NOT NULL). 최초 2xx 응답 JSON 원문 |
| response_location | VARCHAR(255) | NULL (201일 때 `/api/orders/{id}`) |
| created_at | TIMESTAMPTZ | NOT NULL |
| completed_at | TIMESTAMPTZ | NULL |

UNIQUE `uk_idem_scope_key (scope, idem_key)` — scope별 독립 키 공간(R4.1)과 동시 클레임 직렬화(R4.5)의 근거. `cardToken` 평문은 저장하지 않는다(지문 해시에만 사용). `response_body`는 jsonb가 아니라 TEXT — 키 순서·서식 그대로 재생.

## 4. 동시성·락 프로토콜

### 4.1 전역 락 순서 (데드락 방지, R10.4)
**`orders` 행(1건) → `products` 행들(id 오름차순, 1건씩) → `coupons` 행(1건)**. 모든 쓰기 트랜잭션이 이 순서의 부분열만 사용한다.
- 주문 생성: products(asc) → coupon
- 결제: order → (PG 호출) → products(asc) → [거절 시] coupon
- 취소/환불, 만료: order → products(asc) → coupon
- ship/deliver: order
- 한 트랜잭션에서 **주문은 최대 1건만** 락한다(만료 스윕도 주문당 트랜잭션 1개). 여러 주문을 한 트랜잭션에서 잡으면 상품 락 순서가 깨질 수 있다.
- 멱등 클레임 INSERT는 비즈니스 트랜잭션 이전의 별도 트랜잭션에서 커밋되므로 이 순서에 참여하지 않는다.

### 4.2 리포지토리 락 메서드
```java
// ProductRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Optional<Product> findByIdForUpdate(@Param("id") Long id);

// CouponRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select c from Coupon c where c.code = :code")
Optional<Coupon> findByCodeForUpdate(@Param("code") String code);
boolean existsByCode(String code);

// OrderRepository (JpaSpecificationExecutor<Order> 포함)
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select o from Order o where o.id = :id")
Optional<Order> findByIdForUpdate(@Param("id") Long id);

@Query(value = "SELECT id FROM orders WHERE status = 'PENDING_PAYMENT' AND expires_at <= :now ORDER BY expires_at, id LIMIT :limit", nativeQuery = true)
List<Long> findExpirableIds(@Param("now") Instant now, @Param("limit") int limit);

@Query(value = "SELECT * FROM orders WHERE id = :id AND status = 'PENDING_PAYMENT' AND expires_at <= :now FOR UPDATE SKIP LOCKED", nativeQuery = true)
Optional<Order> lockExpirable(@Param("id") Long id, @Param("now") Instant now);

@Query("select count(o) > 0 from Order o where o.userId = :userId and o.couponCode = :code and o.status in :active")
boolean existsActiveCouponUse(String userId, String code, Collection<OrderStatus> active);

// IdempotencyRecordRepository
@Modifying
@Query(value = "INSERT INTO idempotency_records (scope, idem_key, fingerprint, status, created_at) VALUES (:scope, :key, :fp, 'IN_PROGRESS', :now) ON CONFLICT (scope, idem_key) DO NOTHING", nativeQuery = true)
int tryClaim(String scope, String key, String fp, Instant now);
Optional<IdempotencyRecord> findByScopeAndIdemKey(IdempotencyScope scope, String idemKey);
@Modifying
@Query("delete from IdempotencyRecord r where r.id = :id and r.status = com.example.order.idempotency.IdempotencyStatus.IN_PROGRESS")
int releaseInProgress(Long id);
```
- 락 대상 행은 그 트랜잭션에서 **처음 로딩할 때 락 쿼리로** 읽는다(락 없이 먼저 읽어 1차 캐시에 올려 두면 이후 락 쿼리가 오래된 값을 돌려줄 수 있음).
- 같은 트랜잭션에서 여러 상품을 잡을 때는 `items`의 productId를 정렬(`TreeSet`)해 순서대로 `findByIdForUpdate` 호출.

### 4.3 재고 예약 (R10.1, R10.4) — 비관적 락 방식 채택
조건부 UPDATE 대신 `SELECT ... FOR UPDATE`(id 오름차순)를 쓴다. 이유: C3 순서(404 → 재고 409 → 쿠폰 409)를 지키려면 모든 상품·쿠폰 존재 확인과 재고 판정을 반영 전에 끝내야 하고, 락을 쥔 상태라 판정과 `reserved += q`가 원자적이다. `ck_products_reserved`는 최후 방어선.

### 4.4 쿠폰 (R10.2, R10.3)
쿠폰 행 `FOR UPDATE`가 같은 쿠폰을 쓰는 모든 주문 생성/복원을 직렬화한다. READ COMMITTED에서 락 획득 후의 `existsActiveCouponUse` 조회는 앞선 트랜잭션의 커밋된 주문을 본다 → 같은 사용자 동시 5건 중 1건만 통과. `used_count`도 락 하에서 판정·증가 → 정확히 `total_quantity`건 통과. `ux_orders_user_coupon_active`·`ck_coupons_used_count`는 방어선.

### 4.5 결제 (R10.5)
주문 행 `FOR UPDATE`를 쥔 채 PG 호출(최대 2초) — 같은 주문의 다른 결제는 락 대기 후 상태가 `PAID`라 409. 503은 예외 롤백으로 주문·재고·쿠폰 불변. 상세는 01 §6.

### 4.6 만료 (R6)
주문 1건씩 `FOR UPDATE SKIP LOCKED`로 잡아 처리 → 결제 진행 중(락 보유) 주문은 건너뛴다. 상세는 01 §9.

### 4.7 멱등 (R4.5)
`INSERT ... ON CONFLICT (scope, idem_key) DO NOTHING`. 동시 같은 키 요청 중 하나만 INSERT 성공(소유), 나머지는 기존 행을 읽어 422/409/재생. 오류 종료 시 `releaseInProgress`(별도 트랜잭션)로 삭제 → 같은 요청 재시도 가능(R4.4).

## 5. Flyway 마이그레이션 — `src/main/resources/db/migration/V1__init.sql`

```sql
-- V1__init.sql : order-payment 초기 스키마

CREATE TABLE products (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      VARCHAR(100) NOT NULL,
    price     BIGINT       NOT NULL,
    stock     INTEGER      NOT NULL,
    reserved  INTEGER      NOT NULL DEFAULT 0,
    CONSTRAINT ck_products_price    CHECK (price BETWEEN 1 AND 10000000),
    CONSTRAINT ck_products_stock    CHECK (stock >= 0),
    CONSTRAINT ck_products_reserved CHECK (reserved >= 0 AND reserved <= stock)
);

CREATE TABLE coupons (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code                VARCHAR(20)  NOT NULL,
    discount_type       VARCHAR(10)  NOT NULL,
    discount_value      BIGINT       NOT NULL,
    min_order_amount    BIGINT       NOT NULL DEFAULT 0,
    max_discount_amount BIGINT       NULL,
    total_quantity      INTEGER      NOT NULL,
    used_count          INTEGER      NOT NULL DEFAULT 0,
    valid_from          TIMESTAMPTZ  NOT NULL,
    valid_until         TIMESTAMPTZ  NOT NULL,
    CONSTRAINT uk_coupons_code           UNIQUE (code),
    CONSTRAINT ck_coupons_code           CHECK (code ~ '^[A-Z0-9]{4,20}$'),
    CONSTRAINT ck_coupons_type           CHECK (discount_type IN ('FIXED', 'RATE')),
    CONSTRAINT ck_coupons_value          CHECK (discount_value >= 1 AND (discount_type <> 'RATE' OR discount_value <= 100)),
    CONSTRAINT ck_coupons_min_order      CHECK (min_order_amount >= 0),
    CONSTRAINT ck_coupons_max_discount   CHECK (max_discount_amount IS NULL OR max_discount_amount >= 1),
    CONSTRAINT ck_coupons_total_quantity CHECK (total_quantity >= 1),
    CONSTRAINT ck_coupons_used_count     CHECK (used_count >= 0 AND used_count <= total_quantity),
    CONSTRAINT ck_coupons_period         CHECK (valid_from < valid_until)
);

CREATE TABLE orders (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id       VARCHAR(50)  NOT NULL,
    status        VARCHAR(20)  NOT NULL,
    coupon_code   VARCHAR(20)  NULL,
    subtotal      BIGINT       NOT NULL,
    discount      BIGINT       NOT NULL,
    total_price   BIGINT       NOT NULL,
    pg_payment_id VARCHAR(100) NULL,
    created_at    TIMESTAMPTZ  NOT NULL,
    expires_at    TIMESTAMPTZ  NOT NULL,
    paid_at       TIMESTAMPTZ  NULL,
    CONSTRAINT fk_orders_coupon     FOREIGN KEY (coupon_code) REFERENCES coupons (code),
    CONSTRAINT ck_orders_status     CHECK (status IN ('PENDING_PAYMENT', 'PAID', 'PAYMENT_FAILED', 'EXPIRED',
                                                      'CANCELLED', 'SHIPPED', 'DELIVERED', 'REFUNDED')),
    CONSTRAINT ck_orders_subtotal   CHECK (subtotal >= 0),
    CONSTRAINT ck_orders_discount   CHECK (discount >= 0 AND discount <= subtotal),
    CONSTRAINT ck_orders_total      CHECK (total_price = subtotal - discount)
);

CREATE INDEX ix_orders_created_id        ON orders (created_at DESC, id DESC);
CREATE INDEX ix_orders_user_created_id   ON orders (user_id, created_at DESC, id DESC);
CREATE INDEX ix_orders_status_created_id ON orders (status, created_at DESC, id DESC);
CREATE INDEX ix_orders_pending_expires   ON orders (expires_at) WHERE status = 'PENDING_PAYMENT';
CREATE UNIQUE INDEX ux_orders_user_coupon_active
    ON orders (user_id, coupon_code)
    WHERE coupon_code IS NOT NULL
      AND status IN ('PENDING_PAYMENT', 'PAID', 'SHIPPED', 'DELIVERED');

CREATE TABLE order_items (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id   BIGINT  NOT NULL,
    line_no    INTEGER NOT NULL,
    product_id BIGINT  NOT NULL,
    quantity   INTEGER NOT NULL,
    unit_price BIGINT  NOT NULL,
    CONSTRAINT fk_order_items_order   FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT uk_order_items_line    UNIQUE (order_id, line_no),
    CONSTRAINT uk_order_items_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_line_no  CHECK (line_no >= 0),
    CONSTRAINT ck_order_items_quantity CHECK (quantity BETWEEN 1 AND 1000),
    CONSTRAINT ck_order_items_price    CHECK (unit_price >= 1)
);

CREATE INDEX ix_order_items_product ON order_items (product_id);

CREATE TABLE idempotency_records (
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scope             VARCHAR(20)  NOT NULL,
    idem_key          VARCHAR(64)  NOT NULL,
    fingerprint       VARCHAR(64)  NOT NULL,
    status            VARCHAR(20)  NOT NULL,
    response_status   INTEGER      NULL,
    response_body     TEXT         NULL,
    response_location VARCHAR(255) NULL,
    created_at        TIMESTAMPTZ  NOT NULL,
    completed_at      TIMESTAMPTZ  NULL,
    CONSTRAINT uk_idem_scope_key   UNIQUE (scope, idem_key),
    CONSTRAINT ck_idem_scope       CHECK (scope IN ('CREATE_ORDER', 'PAY_ORDER')),
    CONSTRAINT ck_idem_status      CHECK (status IN ('IN_PROGRESS', 'COMPLETED')),
    CONSTRAINT ck_idem_completed   CHECK (status <> 'COMPLETED'
                                          OR (response_status IS NOT NULL AND response_body IS NOT NULL))
);
```

## 6. JPA 매핑 메모

- 엔티티는 `protected` 기본 생성자 + 정적 팩토리/도메인 메서드(`reserve(q)`, `release(q)`, `commitSale(q)`, `restock(q)`, `use()`, `restore()`, `markPaid(...)` 등). setter 노출 최소화.
- `Order`의 상태 전이 메서드는 허용되지 않은 전이에서 `InvalidStateException`을 던진다(01 §10 표 그대로).
- 테스트 간 데이터 격리: 통합 테스트는 `TRUNCATE order_items, orders, idempotency_records, coupons, products RESTART IDENTITY CASCADE` 등으로 정리(테스트 단계 재량).
