# 02. DB 설계 — order (주문 + 재고 차감)

- DB: PostgreSQL (테스트: Testcontainers PostgreSQL, 권장 이미지 `postgres:16-alpine`)
- 마이그레이션: Flyway (`src/main/resources/db/migration/`), 스키마 관리는 Flyway가 전담하고 Hibernate는 `ddl-auto=validate`만 한다
- 짝 문서: [01_api_design.md](./01_api_design.md)
- **필드 ↔ 컬럼 대응표, 제약 ↔ 상태코드 매핑표는 [01_api_design.md §7 정합 요약](./01_api_design.md#7-정합-요약-구현검증-기준표)을 단일 기준으로 한다.** 이 문서에는 복제하지 않는다.

---

## 1. 테이블 개요

```
products 1 ──< order_items >── 1 orders
```

| 테이블 | 용도 | 행 변경 경로 |
|---|---|---|
| `products` | 상품, 현재 재고 | INSERT(R1), `stock`만 UPDATE(R3 차감, R5 복원). 수정/삭제 API 없음 |
| `orders` | 주문 헤더 | INSERT(R3), `status`만 UPDATE(R5). 삭제 없음 |
| `order_items` | 주문 항목, 주문 시점 단가 스냅샷 | INSERT(R3)만. 이후 불변 |

## 2. 컬럼 정의

### products
| 컬럼 | 타입 | NULL | 기본값/생성 | 제약 |
|---|---|---|---|---|
| `id` | `BIGINT` | NOT NULL | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `name` | `TEXT` | NOT NULL | — | `ck_products_name_not_blank`: `length(btrim(name)) > 0` |
| `price` | `BIGINT` | NOT NULL | — | `ck_products_price_positive`: `price > 0` |
| `stock` | `INTEGER` | NOT NULL | — | `ck_products_stock_non_negative`: `stock >= 0` |

### orders
| 컬럼 | 타입 | NULL | 기본값/생성 | 제약 |
|---|---|---|---|---|
| `id` | `BIGINT` | NOT NULL | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `status` | `VARCHAR(20)` | NOT NULL | — | `ck_orders_status`: `status IN ('ORDERED','CANCELLED')` |
| `total_price` | `BIGINT` | NOT NULL | — | `ck_orders_total_price_positive`: `total_price > 0` |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | 앱이 설정(마이크로초 절삭 `Instant`) | — |

### order_items
| 컬럼 | 타입 | NULL | 기본값/생성 | 제약 |
|---|---|---|---|---|
| `id` | `BIGINT` | NOT NULL | `GENERATED BY DEFAULT AS IDENTITY` | PK (항목 순서 = 삽입 순서) |
| `order_id` | `BIGINT` | NOT NULL | — | `fk_order_items_order` → `orders(id)` |
| `product_id` | `BIGINT` | NOT NULL | — | `fk_order_items_product` → `products(id)` |
| `quantity` | `INTEGER` | NOT NULL | — | `ck_order_items_quantity_positive`: `quantity >= 1` |
| `unit_price` | `BIGINT` | NOT NULL | — | `ck_order_items_unit_price_positive`: `unit_price > 0` |
| | | | | `uq_order_items_order_product`: `UNIQUE (order_id, product_id)` |

타입 선택 근거:
- 금액은 `BIGINT`(Java `long`)를 쓴다. 원 단위 정수라서 소수가 필요 없고, `INTEGER` 상한(약 21억 원)은 금액 합계에 좁다.
- 재고·수량은 `INTEGER`(Java `int`)를 쓴다. 요청 DTO가 `Integer`이므로 범위를 넘으면 역직렬화 단계에서 400이 된다.
- `name`은 `TEXT`다. 계약에 길이 상한이 없으므로 `VARCHAR(n)` 초과로 생기는 500 경로를 만들지 않는다.
- `total_price`는 비정규화 컬럼이다. 항목이 생성 뒤 불변이라 갱신 이상이 없고, 목록(R6)에서 합계를 다시 계산하지 않아도 된다. 불변식 `total_price = Σ(unit_price × quantity)`는 생성 시 서비스가 보장한다.
- `created_at`은 `TIMESTAMPTZ`(UTC 기준 시점)다. Java `Instant`와 의미가 일치한다.

## 3. 인덱스

| 이름 | 정의 | 목적 |
|---|---|---|
| `orders_pkey` | PK `(id)` | 단건 조회 R4/R5 |
| `ix_orders_created_at_id` | `orders (created_at DESC, id DESC)` | R6 정렬 `ORDER BY created_at DESC, id DESC LIMIT/OFFSET`을 정렬 없이 인덱스 순서대로 읽기 |
| `uq_order_items_order_product` | UNIQUE `(order_id, product_id)` | 중복 방지 + `order_id` 선두 컬럼이므로 항목 로딩(`WHERE order_id IN (...)`)용 인덱스를 겸함 |
| `ix_order_items_product_id` | `order_items (product_id)` | FK 참조 측 인덱스(향후 상품별 조회·상품 삭제 시 FK 검사 대비). 현재 요구에는 필수 아님, 비용이 작아 포함 |

## 4. 주문 생성(R3) 원자성과 동시성(R7) 전략

### 4.1 결정: 조건부 UPDATE (원자적 검사 후 차감)

```sql
UPDATE products SET stock = stock - :quantity WHERE id = :id AND stock >= :quantity
```
영향 행 수가 1이면 차감 성공이고, 0이면 재고 부족이다 → `InsufficientStockException`(409) → `@Transactional` 롤백.

### 4.2 서비스 흐름 (`OrderService.create`, `@Transactional`, 격리 수준은 기본 READ COMMITTED)

1. `productRepository.findAllById(ids)` → 누락 id가 있으면 `ProductNotFoundException`(404). 이 단계는 **읽기만** 한다(락 없음). 여기서 읽은 `price`가 `unitPrice`가 된다.
2. 요청 항목을 **productId 오름차순으로 정렬**해 항목마다 `productRepository.decreaseStock(id, qty)`를 호출한다. 반환값이 0이면 즉시 `InsufficientStockException`을 던진다.
3. `totalPrice`를 계산한다(`Math.multiplyExact`/`addExact`).
4. `Order`(+ `OrderItem` 목록, 요청 순서대로)를 `save`한다(cascade). 이어서 DTO로 변환해 반환한다.
5. 예외가 하나라도 나면(모두 `RuntimeException`) 트랜잭션 전체가 롤백된다. 2단계에서 이미 차감한 항목도 원복된다 → "전부 차감 또는 전혀 차감 안 됨"(R3).

### 4.3 이 방식이 R7을 만족하는 이유
- PostgreSQL에서 `UPDATE`는 대상 행에 행 락을 잡는다. 동시 트랜잭션의 같은 행 `UPDATE`는 앞 트랜잭션이 커밋/롤백할 때까지 대기한다. READ COMMITTED에서 대기가 풀리면 PG는 **최신 커밋 버전으로 `WHERE stock >= :q`를 다시 평가**한다(EvalPlanQual). 따라서 검사와 차감 사이에 다른 트랜잭션이 끼어들 틈이 없다.
- 재고 10, 수량 1 주문 20건: 행 락 때문에 차감이 직렬화된다. 앞의 10건은 영향 행 1(재고 10→0)이 되고, 나머지 10건은 재평가 시 `stock >= 1`이 거짓이라 영향 행 0 → 409. 결과는 **정확히 201 × 10, 409 × 10, 최종 재고 0**이다. 재시도 루프가 필요 없다.
- `ck_products_stock_non_negative`(CHECK `stock >= 0`)는 최후 방어선이다. 조건부 UPDATE가 음수 재고를 만들지 않으므로 정상 경로에서는 발동하지 않는다.
- 커넥션 풀: Hikari 기본 `maximum-pool-size=10`이면 20건 동시 요청 중 일부는 커넥션을 기다린다(기본 `connection-timeout` 30초). 트랜잭션이 짧아 문제없다. 풀 크기는 바꾸지 않는다.

### 4.4 데드락 방지
- 한 트랜잭션이 여러 상품 행을 잠그는 순서를 **productId 오름차순으로 통일**한다. 주문 A가 [1,2], 주문 B가 [2,1]이어도 둘 다 1→2 순으로 잠그므로 순환 대기가 생기지 않는다.
- `order_items` INSERT의 FK 검사는 `products` 행에 `FOR KEY SHARE`를 잡는다. 이는 `stock`(키가 아닌 컬럼) UPDATE가 잡는 `FOR NO KEY UPDATE`와 충돌하지 않으므로 새 대기 관계가 생기지 않는다.

### 4.5 대안과 기각 근거
| 대안 | 판단 |
|---|---|
| 비관적 락 `SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE` 후 앱에서 검사·차감 | **정확성은 동등**하다(1순위 대안). 다만 JPA `@Lock(PESSIMISTIC_WRITE)` 쿼리, 더티 체킹 차감, 잠금 순서 보장을 위한 `ORDER BY`를 모두 갖춰야 한다. 조건부 UPDATE는 검사와 차감이 SQL 한 문장에 묶여 있어 실수 여지가 더 적다. 위 전략이 테스트에서 실패하면 이 방식으로 전환한다 |
| 낙관적 락(`@Version`) | **기각.** 동시 20건이 같은 버전을 읽으면 1건만 커밋되고 나머지는 재고가 남아 있어도 충돌 실패한다. 재시도 없이는 "정확히 10건 성공"을 보장할 수 없고, 재시도를 붙이면 횟수·백오프 튜닝에 결과가 좌우된다 |
| `SERIALIZABLE` 격리 | **기각.** 직렬화 실패(`40001`)가 나므로 재시도가 필요하고, 실패를 409로 오인할 위험이 있다 |
| JVM `synchronized`/락 | **기각.** 다중 인스턴스에서 무효이고, 트랜잭션 커밋 시점과 락 해제 시점이 어긋난다 |

### 4.6 영속성 컨텍스트 주의 (구현자 필독)
- 1단계에서 로드한 `Product` 엔티티는 영속 상태이지만, 2단계의 네이티브 UPDATE는 영속성 컨텍스트를 거치지 않는다. 그래서 엔티티의 `stock` 필드는 낡은 값이다.
- **이 경로에서 `Product.stock`을 읽거나 수정하지 않는다.** 수정하지 않으면 더티 체킹이 아무것도 플러시하지 않으므로 DB 값이 덮어써지지 않는다. `Product`에 `stock` setter를 두지 않는다.
- `Product`에 `@Version`을 두지 않는다.

## 5. 주문 취소(R5) — 재고 복원과 중복 취소 경합

### 5.1 서비스 흐름 (`OrderService.cancel`, `@Transactional`)
1. `orderRepository.existsById(id)`가 false면 `OrderNotFoundException`(404). 주문은 삭제되지 않으므로 이 판정은 경합 없이 유효하다.
2. 상태 전이를 조건부 UPDATE로 한다:
   ```sql
   UPDATE orders SET status = 'CANCELLED' WHERE id = :id AND status = 'ORDERED'
   ```
   영향 행이 0이면 `OrderAlreadyCancelledException`(409).
3. `orderRepository.findWithItemsById(id)`로 주문과 항목을 로드한다. 2단계 쿼리에 `clearAutomatically = true`를 주어, 다시 읽은 엔티티에 `status=CANCELLED`가 반영되게 한다.
4. 항목을 **productId 오름차순**으로 `productRepository.increaseStock(productId, quantity)`:
   ```sql
   UPDATE products SET stock = stock + :quantity WHERE id = :id
   ```
5. DTO로 변환해 반환한다(200).

### 5.2 중복 취소 경합
- 같은 주문을 동시에 두 번 취소하면, 두 번째 트랜잭션의 2단계 UPDATE는 첫 번째가 잡은 `orders` 행 락에서 대기한다. 첫 번째가 커밋하면 PG가 `status = 'ORDERED'`를 최신 버전으로 재평가해 거짓이 되므로 영향 행 0 → 409. **재고 복원은 정확히 한 번만** 일어난다.
- 첫 번째 트랜잭션이 4단계 이후 실패해 롤백되면, 대기하던 두 번째는 원래 행(`ORDERED`)으로 재평가돼 정상 취소된다. 이것도 일관된다.

### 5.3 생성·취소 간 데드락 검토
- 생성: `products` 행(오름차순) → 새 `orders`/`order_items` 행 INSERT. 기존 `orders` 행은 기다리지 않는다.
- 취소: `orders` 행 1개 → `products` 행(오름차순).
- 생성은 `orders` 락을 기다리지 않고, 취소끼리는 서로 다른 주문 행과 같은 순서의 상품 락을 쓰므로 순환 대기가 없다.
- 복원 오버플로: 재고는 주문으로만 줄고 취소로만 되돌아온다(상품 수정 API 없음). 따라서 `stock + quantity`는 최초 등록 재고를 넘지 않아 `INTEGER` 범위 안에 머문다.

## 6. Flyway 마이그레이션

파일: `src/main/resources/db/migration/V1__create_products_and_orders.sql` (기존 `.gitkeep` 옆에 둔다)

```sql
-- V1: products, orders, order_items

CREATE TABLE products (
    id     BIGINT  GENERATED BY DEFAULT AS IDENTITY,
    name   TEXT    NOT NULL,
    price  BIGINT  NOT NULL,
    stock  INTEGER NOT NULL,
    CONSTRAINT pk_products PRIMARY KEY (id),
    CONSTRAINT ck_products_name_not_blank     CHECK (length(btrim(name)) > 0),
    CONSTRAINT ck_products_price_positive     CHECK (price > 0),
    CONSTRAINT ck_products_stock_non_negative CHECK (stock >= 0)
);

CREATE TABLE orders (
    id          BIGINT      GENERATED BY DEFAULT AS IDENTITY,
    status      VARCHAR(20) NOT NULL,
    total_price BIGINT      NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    CONSTRAINT pk_orders PRIMARY KEY (id),
    CONSTRAINT ck_orders_status               CHECK (status IN ('ORDERED', 'CANCELLED')),
    CONSTRAINT ck_orders_total_price_positive CHECK (total_price > 0)
);

CREATE INDEX ix_orders_created_at_id ON orders (created_at DESC, id DESC);

CREATE TABLE order_items (
    id         BIGINT  GENERATED BY DEFAULT AS IDENTITY,
    order_id   BIGINT  NOT NULL,
    product_id BIGINT  NOT NULL,
    quantity   INTEGER NOT NULL,
    unit_price BIGINT  NOT NULL,
    CONSTRAINT pk_order_items PRIMARY KEY (id),
    CONSTRAINT fk_order_items_order   FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT uq_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_quantity_positive   CHECK (quantity >= 1),
    CONSTRAINT ck_order_items_unit_price_positive CHECK (unit_price > 0)
);

CREATE INDEX ix_order_items_product_id ON order_items (product_id);
```

규약: 적용된 마이그레이션은 수정하지 않는다. 변경은 `V2__...sql`로 추가한다.

## 7. 엔티티 매핑 방침

공통: `jakarta.persistence.*`, `protected` 기본 생성자, `equals/hashCode`는 재정의하지 않는다(식별자 동일성으로 충분). `@GeneratedValue(strategy = GenerationType.IDENTITY)`는 위 `GENERATED BY DEFAULT AS IDENTITY`와 짝을 이룬다.

### Product (`@Table(name = "products")`)
| 필드 | 매핑 |
|---|---|
| `Long id` | `@Id @GeneratedValue(IDENTITY)` |
| `String name` | `@Column(nullable = false, columnDefinition = "text")` |
| `long price` | `@Column(nullable = false)` |
| `int stock` | `@Column(nullable = false)`. setter 없음(§4.6) |

### Order (`@Entity @Table(name = "orders")`)
| 필드 | 매핑 |
|---|---|
| `Long id` | `@Id @GeneratedValue(IDENTITY)` |
| `OrderStatus status` | `@Enumerated(EnumType.STRING) @Column(nullable = false, length = 20, columnDefinition = "varchar(20)")` |
| `long totalPrice` | `@Column(name = "total_price", nullable = false)` |
| `Instant createdAt` | `@Column(name = "created_at", nullable = false, updatable = false, columnDefinition = "timestamptz")`. 생성자에서 `Instant.now().truncatedTo(ChronoUnit.MICROS)` |
| `List<OrderItem> items` | `@OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST) @OrderBy("id ASC")`, `new ArrayList<>()`로 초기화. `addItem(...)`이 양방향을 설정 |

- 클래스명 `Order`는 SQL 예약어라 테이블명은 `orders`로 둔다. 상태 전이는 네이티브 조건부 UPDATE로 하므로(§5) 엔티티에 `cancel()` setter형 메서드를 두지 않는다.

### OrderItem (`@Table(name = "order_items")`)
| 필드 | 매핑 |
|---|---|
| `Long id` | `@Id @GeneratedValue(IDENTITY)` |
| `Order order` | `@ManyToOne(fetch = FetchType.LAZY, optional = false) @JoinColumn(name = "order_id", nullable = false)` |
| `Long productId` | `@Column(name = "product_id", nullable = false)` — `Product` 연관 대신 id 값으로 참조한다(애그리거트 경계를 넘지 않고, 응답에 필요한 것은 id뿐) |
| `int quantity` | `@Column(nullable = false)` |
| `long unitPrice` | `@Column(name = "unit_price", nullable = false)` |

`columnDefinition`을 쓰는 이유: `ddl-auto=validate`가 엔티티 SQL 타입과 DB 메타데이터 타입명을 비교한다. `text`/`timestamptz`/`varchar(20)`을 명시하면 Hibernate 버전별 기본 타입 매핑(`timestamp(6) with time zone` 등)과 JDBC 타입 코드 해석 차이로 생기는 검증 실패를 피할 수 있다.

### 리포지토리
```java
// ProductRepository extends JpaRepository<Product, Long>
@Modifying
@Query(value = "UPDATE products SET stock = stock - :quantity WHERE id = :id AND stock >= :quantity", nativeQuery = true)
int decreaseStock(@Param("id") Long id, @Param("quantity") int quantity);

@Modifying
@Query(value = "UPDATE products SET stock = stock + :quantity WHERE id = :id", nativeQuery = true)
int increaseStock(@Param("id") Long id, @Param("quantity") int quantity);

// OrderRepository extends JpaRepository<Order, Long>
@EntityGraph(attributePaths = "items")
Optional<Order> findWithItemsById(Long id);

Page<Order> findAll(Pageable pageable);   // Sort: createdAt DESC, id DESC (서비스가 PageRequest로 지정)

@Modifying(clearAutomatically = true)
@Query(value = "UPDATE orders SET status = 'CANCELLED' WHERE id = :id AND status = 'ORDERED'", nativeQuery = true)
int cancelIfOrdered(@Param("id") Long id);
```
- 목록(R6)의 항목 로딩은 `hibernate.default_batch_fetch_size: 100`으로 N+1을 막는다(페이지 내 주문들의 items를 `IN` 한 번으로 로드). 페이지네이션과 컬렉션 fetch join을 같이 쓰지 않는다(메모리 페이징 경고 HHH90003004).
- 모든 엔티티→DTO 변환은 `@Transactional(readOnly = true)`(조회) 또는 `@Transactional`(쓰기) 서비스 메서드 안에서 끝낸다.

## 8. application.yml 설정 방침

```yaml
spring:
  application:
    name: order-service
  datasource:
    url: jdbc:postgresql://localhost:5432/order
    username: order
    # password: 기본값을 커밋하지 않는다. 실행 시 SPRING_DATASOURCE_PASSWORD 환경 변수로 주입한다.
  jpa:
    open-in-view: false
    hibernate:
      ddl-auto: validate
    properties:
      hibernate:
        default_batch_fetch_size: 100
  flyway:
    enabled: true            # 기본값, 명시. locations 기본 classpath:db/migration
  jackson:
    serialization:
      write-dates-as-timestamps: false
    deserialization:
      accept-float-as-int: false
    mapper:
      allow-coercion-of-scalars: false

server:
  port: 8080
```

- **표준 속성명만 쓴다.** `${DB_URL}` 같은 자체 변수명을 만들지 않는다. Spring Boot의 relaxed binding으로 OS 환경 변수 `SPRING_DATASOURCE_URL`/`SPRING_DATASOURCE_USERNAME`/`SPRING_DATASOURCE_PASSWORD`/`SERVER_PORT`가 `application.yml` 값보다 우선한다. 따라서 위 기본값은 로컬 개발용이고 실행 환경에서 그대로 덮어쓸 수 있다.
- 비밀번호는 yml에 두지 않는다(스킬 원칙 8).
- 테스트: `@SpringBootTest` + `@Testcontainers` + `@Container @ServiceConnection static PostgreSQLContainer<?>`를 쓴다. `@ServiceConnection`이 datasource url/username/password를 컨테이너 값으로 덮어쓰고, Flyway가 V1을 적용한 뒤 `validate`가 엔티티와 스키마를 대조한다. 테스트 전용 yml로 `ddl-auto`를 바꾸지 않는다(마이그레이션 검증이 무력화된다).
- R7 테스트 힌트: `webEnvironment = RANDOM_PORT` + `TestRestTemplate`(또는 서비스 직접 호출)로 20개 스레드를 `CountDownLatch`로 동시에 출발시키고, 201/409 개수와 최종 `GET /api/products/{id}`의 `stock == 0`을 단언한다.
