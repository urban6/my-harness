# PRD — 오케스트레이션 vs 일반 개발 비교 실험

> 상태: **확정** · 작성 2026-10-09 · 수정 2026-10-09 (계획 검토 반영: B군 스킬 명시 지시, 빌드·테스트 분리, 런타임 계약, 시간 상한, 실행 옵션 고정, 스타터 구성)
> 결정 현황은 §11. 남은 조건부 항목은 파일럿 결과에 따른 C군 워커 수정(§7-1)뿐이다.

## 1. 목적

같은 요구사항 문서(`feature.md`)를 주었을 때 **`feature-pm` 오케스트레이션**(설계 → 구현·검증 → 테스트 파이프라인)이 **일반 단일 세션 개발**보다 결과물 품질이 나은지, 그 대가(비용·시간)는 얼마인지 수치로 확인한다.

| # | 질문 | 판정 근거 |
|---|---|---|
| Q1 | 오케스트레이션이 기능 정확도를 높이는가? | 숨긴 인수 테스트 통과율 |
| Q2 | 설계 ↔ 구현 정합이 더 좋은가? | 계약 위반 수(상태코드·필드·에러 포맷) |
| Q3 | 테스트가 요구사항을 더 넓게 커버하는가? | 요구사항별 테스트 매핑, 커버리지 |
| Q4 | 코드 품질 차이가 있는가? | 블라인드 리뷰 점수, 정적 분석 위반 수 |
| Q5 | 비용·시간 대가는? | 토큰·USD·소요시간·턴 수 |

## 2. 비교군 (확정: A·B·C 3군)

군 간 차이는 **CLI 실행 플래그로만** 만든다. 프롬프트 문구는 모든 군이 같다(§5).

| 군 | 이름 | 사용 자산 | 실행 플래그 |
|---|---|---|---|
| A | Vanilla | 하니스 자산 없음 | `--disable-slash-commands --disallowedTools Agent` (스킬·서브에이전트 차단) |
| B | Skills-only | `spring-boot` 스킬만 | `--disallowedTools Agent --append-system-prompt "Spring Boot 코드는 spring-boot 스킬을 따른다."` (서브에이전트 차단 + 스킬 명시 지시) |
| C | Orchestration | `feature-pm` + 워커 4종 + 스킬 | `--agent feature-pm` (메인 세션 = PM) |

모든 군 공통 옵션: `-p --output-format stream-json --verbose --model claude-opus-5-5 --effort high --permission-mode bypassPermissions --max-budget-usd 40 --strict-mcp-config` (§3).

- A↔B 차이 = 스킬 효과, B↔C 차이 = 오케스트레이션 효과, A↔C 차이 = 하니스 전체 효과.
- **B군에 스킬 명시 지시를 붙이는 이유**: 컨벤션 스킬은 description 자동 트리거가 거의 일어나지 않는다(과거 측정에서 headless 30회 중 0회). 설치만 해 두면 B ≈ A가 되어 스킬 효과를 잴 수 없다. C군도 `feature-pm`이 스킬을 명시 주입하므로, B에도 명시 지시를 줘야 공정하다. 프롬프트 문구가 아닌 실행 옵션이므로 §5의 "프롬프트 동일" 원칙은 유지된다.
- A·B군은 `Agent` 도구 차단으로 Explore·Plan 같은 내장 서브에이전트도 쓰지 못한다. "단일 세션"이라는 군 정의에 맞는 의도된 제약이다.
- **C군 워커의 스킬 접근 (파일럿 후 결정)**: `backend-designer`·`backend-impl`·`test-writer`의 `tools`에 `Skill`이 없어, 스택 주입 블록의 "spring-boot 스킬 레시피를 따른다"를 실제로 이행하지 못할 가능성이 높다. 파일럿에서 확인하고, 접근하지 못하면 **본 실행 전에 하니스 에이전트 정의를 수정**한 뒤 진행한다(§7-1). 수정 내용은 하니스 개선으로 별도 커밋하고 보고서에 기록한다.
- C를 `--agent feature-pm`로 띄우는 이유: `feature-pm`은 "메인 세션에서 직접 호출"을 전제로 한다. 일반 세션에서 "feature-pm 에이전트로 ~"라고 부르면 서브에이전트로 스폰되어 워커를 다시 스폰하지 못할 수 있다(`prompts/feature-development.md` A안의 잠재 이슈 — 파일럿에서 함께 확인).
- `--bare`는 OAuth 인증을 읽지 않으므로 격리 수단으로 쓰지 않는다.

## 3. 통제 변수 (모든 군 동일)

| 항목 | 값 |
|---|---|
| 요구사항 입력 | 동일한 `feature.md`를 실행 디렉터리 루트에 복사 (§4) |
| 프롬프트 | 한 줄 고정 문구 (§5) |
| 스타터 프로젝트 | 미리 만든 동일 스켈레톤(Initializr 산출 + 빈 패키지)을 군마다 복사 |
| 세션 모델 | `--model claude-opus-5-5 --effort high` 명시 (전역 설정 `opus[1m]`·`effortLevel` 의존 제거). C군 워커는 각 정의의 `model`(opus/sonnet)을 따른다 |
| 권한 | `--permission-mode bypassPermissions` (격리된 실행 디렉터리 한정) |
| 예산 상한 | `--max-budget-usd 40` 군마다 동일. 파일럿 실측 후 조정 가능 (§9.2) |
| 실행 방식 | 전 군 헤드리스(`claude -p`), 터미널 CLI. 데스크톱 앱 세션은 쓰지 않으며 군마다 실행 방식을 섞지 않는다 |
| 실행 위치 | `playground/runs/{군}-{회차}/`에서 바로 실행. 각 run은 독립 git 저장소 + 상위 `CLAUDE.md` 차단 설정(§3.2) |
| 시간 상한 | run당 120분, `timeout 120m`으로 강제. 초과 시 그 시점 결과로 채점하고 "시간 초과"로 기록 |
| MCP | `--strict-mcp-config`로 MCP 서버 전부 제외 (모든 군) |
| 사전 준비(warm-up) | 본 실행 전 스타터를 한 번 빌드하고 PostgreSQL 이미지를 받아 둔다 → 첫 run만 다운로드 시간을 떠안는 편향 제거 |
| run 사이 정리 | 남은 java·Gradle 데몬 프로세스와 컨테이너 정리, 8080 포트 비었는지 확인 |
| 사람 개입 | 없음. 질문으로 멈추면 그 시점 결과로 채점하고 "개입 필요"로 기록 |
| 출력 | `--output-format stream-json` 전체 로그 보존 |

**알려진 교란 변수** (통제하지 않고 기록만):
- 전역 설정 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=40`으로 자동 압축이 일찍 걸린다. 컨텍스트를 하나로 쓰는 A·B군이 C군보다 더 자주 걸릴 수 있다. 사용자 실사용 환경이므로 유지하고, run 로그에서 압축 발생 횟수를 기록한다.
- 전역 설정 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`은 유지한다(C군의 워커 간 `SendMessage`가 이에 의존할 수 있음).
- 전역 훅(Orca)은 모든 군에 걸리지만 로컬 서버로 상태만 POST하고 출력이 없어 결과에 영향이 없다.
- C의 워커 모델이 섞여 있다(`backend-impl`·`test-writer` = sonnet, 나머지 = opus). 하니스를 "있는 그대로" 평가하는 것이 목적이므로 바꾸지 않는다.
- 전역 `~/.claude`에 하니스 agents·skills가 심링크돼 있고, 하니스 외 플러그인도 설치돼 있다(모든 군 공통). 각 run의 `stream-json` `system/init` 이벤트에서 로드된 agents·skills·tools 목록을 확인해 **군 설정대로 격리됐는지 검증**한다.

### 3.1 스타터 프로젝트 구성 (확정)

모든 군이 같은 지점에서 출발하도록, 의존성 선택·빌드 셋업 차이를 미리 없앤다. 애플리케이션 코드는 넣지 않는다.

| 항목 | 값 |
|---|---|
| 빌드 | Gradle wrapper 포함, `build.gradle`(Groovy DSL), Java 21 toolchain |
| Spring Boot | 3.5.x — 스타터 생성 시점의 최신 패치로 고정 |
| 의존성 | `spring-boot-starter-web`, `spring-boot-starter-validation`, `spring-boot-starter-data-jpa`, `postgresql`(runtime), `flyway-core` + `flyway-database-postgresql` |
| 테스트 의존성 | `spring-boot-starter-test`, `spring-boot-testcontainers`, `org.testcontainers:junit-jupiter`, `org.testcontainers:postgresql` |
| 코드 | `@SpringBootApplication` 메인 클래스 하나. Initializr 기본 `contextLoads` 테스트는 DB 없이 실패하므로 제거 |
| 설정 | `application.yml`에 애플리케이션 이름만. DB 설정은 각 군이 작성 |
| 기타 | `.gitignore`(build/, .gradle/), 빈 `src/main/resources/db/migration/` |
| 격리 설정 | `.claude/settings.local.json` — 상위 `CLAUDE.md` 차단, 인수 테스트 경로 읽기 차단 (§3.2) |

### 3.2 저장소 안 실행 시 격리

run 디렉터리가 `my_harness` 아래에 있으므로 두 가지를 막는다.

| 문제 | 대응 | 검증 |
|---|---|---|
| 상위 `my_harness/CLAUDE.md`(하니스 저장소 지침)가 자동 로드됨 | 스타터에 `.claude/settings.local.json` → `{"claudeMdExcludes": ["<my_harness 절대경로>/CLAUDE.md"]}` 포함 | 2026-10-09 사전 확인: 독립 git 저장소만으로는 **로드됨**, 위 설정을 넣으면 **로드 안 됨** |
| 에이전트의 git 명령이 `my_harness` 저장소에 적용됨 | run 디렉터리마다 `git init`(독립 저장소) | — |
| 형제 폴더 `playground/acceptance/`(숨긴 인수 테스트)가 가까움 | 같은 settings에 `permissions.deny`로 `../../acceptance/**` 읽기 차단 + 로그에서 `acceptance` 경로 접근 검사, 접근 시 run 폐기 | 파일럿에서 deny 규칙이 우회 모드에서도 적용되는지 확인 |

- run이 끝나면 에이전트의 커밋 이력을 `git-log.txt`로 저장하고 run의 `.git/`을 지운 뒤 `my_harness`에 커밋한다(중첩 저장소가 gitlink로 커밋되는 것 방지).

## 4. 요구사항 문서 `feature.md`

### 4.1 작성 원칙 — "무엇을"만 적고 "어떻게"는 적지 않는다

`feature-pm` 파이프라인의 강점은 요구 분해(Phase 0)와 설계(`backend-designer`)다. 문서에 설계까지 적으면 일반 세션도 설계를 공짜로 받아 비교가 무의미해진다. 반대로 외부 계약이 없으면 같은 인수 테스트를 돌릴 수 없다.

| 적는다 (무엇을) | 적지 않는다 (어떻게) |
|---|---|
| 기능 목적·범위 | 테이블·컬럼·인덱스·마이그레이션 내용 |
| 비즈니스 규칙 (재고 부족 시 실패, 취소 시 복원 등) | 패키지·클래스·레이어 구조 |
| 외부 계약: 경로, 상태코드, 핵심 응답 필드, 에러 포맷 | 락 방식(비관/낙관/원자 UPDATE), 트랜잭션 경계 |
| 스택·테스트 명령 | DTO·엔티티 설계, 라이브러리 선택(스택 외) |
| 완료 조건 | 구현 순서·작업 분해 |

### 4.2 테스트 기능 (확정)

**주문 + 재고 차감 (Spring Boot 3 + JPA + PostgreSQL)**
— 관계(상품·주문·주문항목), 검증, 400/404/409 분기, 트랜잭션·동시성이 있어 설계 ↔ 구현 어긋남이 드러나기 좋다.

### 4.3 `feature.md` (확정)

원본은 [`feature.md`](feature.md)이고 아래는 그 사본이다(수정은 원본에서 하고 사본을 맞춘다). 실행 시 원본을 각 run 디렉터리 루트로 복사한다.

```markdown
# 기능: 주문(Order) + 재고 차감

## 배경
상품을 등록하고, 재고 범위 안에서 주문·취소할 수 있는 백엔드 API가 필요하다.

## 스택
- Java 21, Spring Boot 3.x, JPA, PostgreSQL, Flyway
- 테스트: JUnit 5 + Testcontainers(PostgreSQL)
- 테스트 명령: ./gradlew test

## 범위
- 포함: 상품 등록·조회, 주문 생성·조회·취소·목록
- 제외: 인증·인가, 결제, 상품 수정·삭제

## 공통 규약
- 금액(`price`, `unitPrice`, `totalPrice`)은 정수(원 단위)다.
- 시각(`createdAt`)은 ISO-8601 문자열이다.
- 주문 상태는 `ORDERED`(생성 직후)와 `CANCELLED`(취소 후) 두 가지다.
- 한 요청에 오류가 여럿이면 400 → 404 → 409 순으로 먼저 해당하는 것을 반환한다.
- DB 접속 정보는 표준 Spring 속성(`spring.datasource.url`·`username`·`password`)으로 받으며, 실행 시 환경 변수(`SPRING_DATASOURCE_URL` 등)로 덮어쓸 수 있어야 한다. 서버 포트도 `SERVER_PORT`로 덮어쓸 수 있어야 한다.

## 요구사항
| ID | 기능 | 계약 | 규칙 |
|---|---|---|---|
| R1 | 상품 등록 | POST /api/products {name, price, stock} → 201 + Location, 본문은 R2 응답과 같은 형태 | name 필수(공백만 있는 문자열 불가), price > 0, stock ≥ 0. 위반 시 400 |
| R2 | 상품 조회 | GET /api/products/{id} → 200 {id, name, price, stock} | 없으면 404 |
| R3 | 주문 생성 | POST /api/orders {items:[{productId, quantity}]} → 201 + Location, 본문은 R4 응답과 같은 형태(status=ORDERED) | items 1개 이상, quantity ≥ 1, 같은 productId 중복 불가 — 위반 시 400. 없는 상품 404, 재고 부족 409. 모든 항목의 재고가 충분할 때만 생성하고, 재고는 전부 차감되거나 전혀 차감되지 않아야 한다 |
| R4 | 주문 조회 | GET /api/orders/{id} → 200 {id, status, totalPrice, items[{productId, quantity, unitPrice}], createdAt} | unitPrice는 주문 시점의 상품 가격, totalPrice = Σ(unitPrice × quantity). 없으면 404 |
| R5 | 주문 취소 | POST /api/orders/{id}/cancel → 200, 본문은 R4 응답과 같은 형태 | status=CANCELLED, 주문 수량만큼 재고 복원. 이미 취소된 주문 409, 없으면 404 |
| R6 | 주문 목록 | GET /api/orders?page&size → 200 {content[], page, size, totalElements} | content 원소는 R4 응답과 같은 형태. page 기본 0(≥ 0), size 기본 20(1~100), 범위 밖이면 400. createdAt 내림차순, 같으면 id 내림차순 |
| R7 | 동시성 | — | 재고 10개인 상품에 수량 1 주문 20건을 동시에 요청하면 정확히 10건 성공(201), 나머지 10건은 409, 최종 재고 0 |
| R8 | 에러 포맷 | R1~R7에서 정의한 모든 에러 응답 + 요청 본문 JSON 파싱 실패(400) | RFC 9457 Problem Details, Content-Type: application/problem+json, 최소 필드 type·title·status·detail |

## 완료 조건
- ./gradlew test 통과
- R1~R8 각각을 검증하는 테스트가 있을 것
```

> 확정(2026-10-09). 검토에서 계약 모호점 11건을 정리했다 — 성공 응답 본문, 초기 상태값, 금액 타입, 에러 우선순위, 중복 productId, 페이지 기본값·범위, 정렬 동순위, 에러 포맷 적용 범위, 공백 name, 시각 형식, 검증 불가 규칙(가격 변경 후 금액 불변) 삭제. 계획 검토에서 채점용 런타임 계약(DB 접속·포트의 환경 변수 덮어쓰기)을 공통 규약에 추가. 인수 테스트는 이 문서에 **적힌 계약만** 검증한다.

## 5. 주입 프롬프트

모든 군 동일, 한 줄:

```text
feature.md의 기능을 개발해줘. 완료 조건을 모두 충족시키고, 마지막에 테스트 명령 결과를 그대로 보여줘.
```

- 군별 차이(스킬·서브에이전트·PM)는 §2의 실행 플래그로만 만든다 → 프롬프트 문구 차이가 결과에 섞이지 않는다.
- C군은 `--agent feature-pm`이므로 같은 문구를 받아도 Phase 0~3 절차를 따른다. 스택이 `feature.md`에 있으므로 Phase 0의 `[Q.]` 정지 요인이 없다.
- 프롬프트 원문은 `playground/prompt.txt`로 고정한다.

## 6. 평가 지표·채점

비용은 품질 점수에 섞지 않고 별도 축으로 본다. 채점은 세 단계다: ① run별 원자료 수집 → ② 품질 점수(100점) 환산 → ③ 군 비교.

### 6.1 run별 원자료 (자동 수집 → `results/metrics.csv`)

| 분류 | 지표 | 측정 방법 | 객관성 |
|---|---|---|---|
| 정확도 | 인수 테스트 통과율 | 통과 케이스 / 전체 케이스(약 30개). `feature.md` 계약에서 도출해 **실행 전에 작성하고 에이전트에게 숨긴** 블랙박스 HTTP 테스트, 케이스마다 R1~R8 태그. R7(동시성)은 5회 반복해 모두 통과해야 통과 | 높음 |
| 정확도 | 요구사항 충족 수 | 해당 R의 케이스를 전부 통과한 요구사항 수 (n/8) | 높음 |
| 정확도 | 실패 원인 분류 | 실패 케이스를 상태코드 / 필드 누락 / 에러 포맷 / 원자성 / 동시성으로 분류해 건수 집계 | 높음 |
| 완료성 | 앱 빌드·자체 테스트 | 앱 빌드 = `./gradlew assemble` 성공 여부(테스트 제외). 자체 테스트 = `./gradlew test` 통과 여부·테스트 수. 실패 시 1회 재실행해 두 번 모두 실패해야 실패(일시적 실패 구분, 재실행 여부 기록) | 높음 |
| 테스트 품질 | 분기 커버리지 | JaCoCo branch % | 높음 |
| 테스트 품질 | 요구사항 커버 | R1~R8 중 자체 테스트가 검증하는 수 (LLM이 테스트 ↔ 요구사항 매핑, 근거 테스트명 기록) | 중간 |
| 코드 품질 | 정적 분석 위반 수 | PMD + SpotBugs 위반 건수 (동일 룰셋) | 높음 |
| 코드 품질 | 블라인드 리뷰 | 루브릭 6항목 × 1~5점 (§6.3) | 낮음 |
| 비용 | USD·토큰·시간·턴 | `stream-json` 최종 `result` 이벤트(`total_cost_usd`, `duration_ms`, `num_turns`, `usage`) | 높음 |
| 프로세스 | 종료 상태 | 정상 / 예산 초과 / 질문 대기로 정지 / 오류. C군은 BLOCKED·REDO 횟수, 스택 드리프트 여부도 기록 | 높음 |

- JaCoCo·PMD·SpotBugs는 에이전트가 만든 빌드 파일을 고치지 않고 **채점 측 Gradle init script**로 주입한다 → 군마다 빌드 설정이 달라도 같은 조건으로 측정. JaCoCo는 테스트가 실패해도 리포트가 나오도록 `ignoreFailures`로 실행한다.
- **앱 빌드(`assemble`)가 실패**하면 앱을 띄울 수 없으므로 인수 테스트는 0으로 처리한다. 자체 테스트 실패는 앱 빌드 실패로 보지 않는다(이중 감점 방지).
- **앱 기동**: run마다 새 PostgreSQL 컨테이너를 띄우고 `java -jar`에 `SPRING_DATASOURCE_URL`·`USERNAME`·`PASSWORD`·`SERVER_PORT` 환경 변수를 넣어 실행한다(`feature.md` 공통 규약의 런타임 계약). 포트 응답까지 최대 120초 대기, 기동 실패 시 인수 테스트 0.
- 인수 테스트는 실행 순서와 무관하게 작성한다(목록 검증은 직접 만든 데이터의 상대 순서로 판정).
- **숨긴 테스트 노출 검사**: 권한 우회 모드라 에이전트가 상위 폴더를 읽을 수 있다. `permissions.deny`로 막고(§3.2), 각 run 로그에서 `acceptance` 경로·run 디렉터리 밖 접근 여부를 확인해, 접근했으면 해당 run은 폐기 후 재실행한다.

### 6.2 품질 점수 (100점, 확정)

| 항목 | 배점 | 계산 |
|---|---|---|
| 기능 정확도 | 50 | 인수 테스트 통과율 × 50 |
| 테스트 품질 | 20 | 요구사항 커버(n/8) × 10 + 분기 커버리지(0~1) × 10 |
| 코드 품질 | 20 | 블라인드 리뷰 평균을 0~1로 환산((평균−1)/4) × 15 + 정적 분석 상대 점수 × 5 |
| 완료성 | 10 | 앱 빌드(`assemble`) 성공 5 + 자체 테스트(`test`) 통과 5 |

- 정적 분석 상대 점수 = 9개 run 중 최소 위반 수 / 해당 run 위반 수 (위반 0이면 1).
- 정확도 비중을 절반으로 둔 이유: "명세대로 동작하는가"가 결과물의 1차 가치이고 가장 객관적이다. 객관성이 낮은 블라인드 리뷰는 15점으로 제한한다.

### 6.3 블라인드 리뷰 방식

- 결과물 소스를 X1~X9로 익명화. `_workspace/`·`progress.md`·세션 로그 등 군을 드러내는 파일은 제외하고, 리뷰 순서는 무작위.
- 코드 안에 남은 군 식별 단서(설계 문서명 `01_api_design.md` 등, 하니스 에이전트 이름)는 리뷰 사본에서 가린다. 테스트 클래스명 같은 남은 단서는 한계로 보고서에 적는다.
- **블라인드 검증**: 리뷰어에게 결과물마다 "어느 방식(단일 세션/오케스트레이션)으로 만든 것 같은지" 추측도 함께 받는다. 추측 정확도가 우연 수준을 크게 넘으면 블라인드가 깨진 것으로 보고 리뷰 점수 해석을 낮춘다.
- 리뷰어는 하니스의 `code-reviewer` 에이전트가 아닌 **중립 프롬프트**(하니스 관점 배제)로 실행. 같은 결과물을 2회 리뷰해 평균.
- 루브릭 6항목, 점수마다 기준 문장을 붙인다(예시):

| 항목 | 5점 기준 | 1점 기준 |
|---|---|---|
| 레이어링 | web → service → repository 단방향, 책임 분리 명확 | 컨트롤러에 비즈니스 로직·쿼리 혼재 |
| 입력 검증 | 계약의 모든 제약이 선언적으로 검증됨 | 검증 누락 또는 수동 if 산재 |
| 예외 처리 | 도메인 예외 → 상태코드 매핑이 한곳에 일관 | 예외가 500으로 새거나 응답 포맷 불일치 |
| 트랜잭션·동시성 | 차감·저장이 한 트랜잭션, 동시성 제어가 명시적 | 트랜잭션 경계 불명확, 경쟁 조건 존재 |
| 네이밍·가독성 | 도메인 용어 일관, 메서드 짧고 의도 명확 | 의미 없는 이름, 긴 메서드 |
| 테스트 설계 | 요구사항별 시나리오 명확, 경계·에러 케이스 포함 | happy path만, 단언 약함 |

### 6.4 군 비교 (군당 3회)

1. **군별 요약** — 품질 점수·인수 테스트 통과율·비용·시간 각각 평균과 최소~최대.
2. **효과 분리** — 평균 차이로 계산.
   - B − A = 스킬 효과
   - C − B = 오케스트레이션 효과
   - C − A = 하니스 전체 효과
3. **판정 규칙** (n=3이라 통계 검정 대신)
   - **명확한 차이**: 한 군의 최솟값 > 다른 군의 최댓값 (범위 비중첩)
   - **경향**: 평균 차이 ≥ 5점이나 범위 중첩
   - **차이 없음**: 그 외
4. **비용 대비 효율**
   - 점수당 비용 = 비용($) ÷ 품질 점수
   - 추가 비용당 추가 점수 = (C 점수 − B 점수) ÷ (C 비용 − B 비용) — "오케스트레이션에 $1 더 쓰면 몇 점 오르나"
   - 9개 run을 x=비용, y=품질 점수 산점도로 표시
5. **실패 패턴 비교** — 군별 실패 원인 분류 건수 합계(어떤 종류의 실수를 하는 군인지).

### 6.5 참고 지표 — 뮤테이션 테스트 (확정, 점수 미반영)

코드를 일부러 조금씩 변형(뮤턴트)한 뒤 자체 테스트가 그 변형을 잡아내는지(실패하는지) 본다. 커버리지는 "그 줄을 실행했는가"만 보지만, 뮤테이션 점수는 "결과를 제대로 검증했는가"를 본다.

| 항목 | 값 |
|---|---|
| 도구 | PIT(pitest), 채점 측 Gradle init script로 주입 (에이전트 빌드 파일 수정 없음) |
| 대상 | **서비스 계층만** — 주문 생성·취소·조회와 재고 차감·복원 비즈니스 로직을 담은 클래스 |
| 대상 선정 | 기본 패턴 `*Service`, `*ServiceImpl`. 구조가 달라 매칭되지 않으면 채점자가 해당 로직 클래스를 수동 지정하고 `results/`에 대상 목록을 기록 |
| 테스트 | 해당 run의 자체 테스트 전체 |
| 뮤테이터 | PIT 기본 세트(DEFAULTS) |
| 시간 상한 | run당 20분. 초과 시 "측정 불가"로 기록 |
| 산출 | 뮤테이션 점수 = 죽인 뮤턴트 / 전체 뮤턴트, 살아남은 뮤턴트 목록 |
| 반영 | **100점 품질 점수에 넣지 않는다.** 보고서에 군별 표(평균·최소~최대)로만 제시하고, §6.1 테스트 품질 지표의 해석 보조로 쓴다 |

- PIT는 자체 테스트가 하나라도 실패하면 실행되지 않는다 → 자체 테스트가 실패한 run은 "측정 불가"로 기록한다.
- 비용은 API가 아닌 로컬 실행 시간뿐이다. 9 run × 최대 20분.
- 대상 클래스 선정이 군마다 달라질 수 있으므로, 대상 목록과 뮤턴트 수를 함께 보고해 비교 가능성을 판단한다.

## 7. 실행 절차

0. **준비**
   - `feature.md` 확정 — 완료 (§4.3)
   - 스타터 생성 → `playground/starter/` (§3.1)
   - 실행 스크립트(군별 옵션·`timeout`·로그 저장·run 사이 정리)와 채점 스크립트(Gradle init script 포함) 작성
   - warm-up: 스타터 빌드 1회 + PostgreSQL 이미지 pull
   - 인수 테스트 작성 → `playground/acceptance/` (run 디렉터리 밖에 두어 에이전트가 볼 수 없게)
   - 스타터에 대해 인수 테스트가 전부 **실패**하는지 확인(테스트 유효성 검증)
   - Docker 기동 확인
1. **파일럿**
   - **격리 검사(A·B)**: 짧은 프롬프트로 A·B 옵션을 각 1회 실행해 `system/init`의 agents·skills·tools 목록이 의도대로인지 확인. B에서 `spring-boot` 스킬이 실제 호출되는지도 확인.
   - **C군 축소 실행**: 축소본 `feature.md`(R1·R2만)로 1회. 확인할 것:
     - 헤드리스(`-p`)에서 백그라운드 워커가 끝날 때까지 세션이 유지되는가
     - `_workspace/features/{name}/` 산출물이 예상대로 생기는가
     - `total_cost_usd`·`--max-budget-usd`가 서브에이전트 비용을 포함하는가
     - **워커가 `spring-boot` 스킬에 접근하는가** — 접근하지 못하면 본 실행 전에 하니스 에이전트 정의를 수정(예: 워커 `tools`에 `Skill` 추가)하고, 수정 후 축소 실행을 한 번 더 해 확인
   - 채점 파이프라인도 파일럿 결과물에 한 번 돌려 끝까지 동작하는지 확인.

   문제가 있으면 PRD 수정 후 재개.
2. **본 실행** — 군마다 `starter/` + `feature.md`를 `playground/runs/{군}-{회차}/`로 복사, `git init` 후 해당 디렉터리에서 헤드리스 실행(`timeout 120m`). **순차 실행**(Docker·레이트 리밋 경합 방지), 순서는 §9.
   - 끝나면 run 사이 정리(§3) → 로그에서 격리·노출(`acceptance` 경로·상위 디렉터리 접근)·압축 횟수 확인 → `git-log.txt` 저장 후 `.git/` 삭제(§3.2).
3. **채점** — 각 run에서 `./gradlew assemble` → `./gradlew test`(init script로 JaCoCo·PMD·SpotBugs 주입, 실패 시 1회 재실행) → 새 PostgreSQL 컨테이너 + 환경 변수로 앱 기동 → 인수 테스트(R7 5회 반복) → 뮤테이션 테스트(§6.5) → 원자료를 `results/metrics.csv`에 기록 (§6.1).
4. **블라인드 리뷰** — 익명화 사본 9개를 무작위 순서로 2회씩 리뷰 (§6.3), 요구사항 커버 매핑도 이때 수행.
5. **집계·보고서** — 품질 점수 환산(§6.2), 군 비교(§6.4) 후 `playground/REPORT.md`에 지표 표, 효과 분리, 비용 대비 효율, 실패 패턴, 결론, 하니스 개선 제안 정리.

## 8. 디렉터리 구조

```
playground/
├── PRD.md                 # 이 문서
├── feature.md             # 요구사항 원본 (모든 군 공통 입력)
├── prompt.txt             # 고정 프롬프트 한 줄
├── starter/               # 공통 스켈레톤
├── acceptance/            # 숨긴 인수 테스트 + 채점 스크립트
├── runs/
│   └── {A|B|C}-{n}/       # 실행 디렉터리 그 자체: starter + feature.md 사본, 결과물, session.jsonl, git-log.txt
├── results/               # 지표 원자료(json/csv)
└── REPORT.md              # 최종 비교 보고서
```

> `playground/`는 `install.sh` 설치 대상(agents·skills·commands)이 아니므로 자산에 섞이지 않는다.
> **`runs/`는 커밋한다(확정).** 단 `build/`·`.gradle/`·`*.class` 같은 빌드 산출물은 `playground/.gitignore`로 제외하고, 소스·`_workspace/`·`session.jsonl`·채점 결과만 남긴다.

## 9. 반복·순서·예산

### 9.1 반복 (확정: 군당 3회, 총 9 run)

라운드마다 세 군을 한 번씩, 군 순서를 바꿔 시간대·환경 변화가 한 군에 몰리지 않게 한다.

| 라운드 | 순서 |
|---|---|
| 1 | B-1 → C-1 → A-1 |
| 2 | C-2 → A-2 → B-2 |
| 3 | A-3 → B-3 → C-3 |

보고서에는 군별 평균과 최소~최대를 함께 적는다. n=3이라 통계적 유의성은 주장하지 않고 "경향 + 편차"로 해석한다.

### 9.2 예산 (확정: run당 $40)

단가(Anthropic API 기준, 1M 토큰당): Opus 5.5 입력 $4 · 출력 $20 · 캐시 읽기 $0.20 / Sonnet 5.5 입력 $2 · 출력 $10 · 캐시 읽기 $0.20.

| 군 | run당 예상 | 근거 |
|---|---|---|
| A·B | $3~8 | 단일 세션, 컨텍스트 대부분 캐시 읽기 |
| C | $10~30 | PM·designer·verifier(opus) + impl·test-writer(sonnet) 각자 컨텍스트, FIX/REDO 루프 |

- **상한: run당 $40, 모든 군 동일.** 상한은 폭주 방지용 안전망이지 목표가 아니다. 정상 run이 잘리면 C군에 불리한 편향이 생기므로 C의 예상 최댓값보다 넉넉하게 잡는다.
- 파일럿에서 실측한 C 비용의 약 2배가 $40을 넘으면 상향 조정한다(전 군 동일하게). 파일럿에서 `total_cost_usd`·`--max-budget-usd`가 서브에이전트 비용까지 포함하는지도 확인한다.
- 전체 예상: 본 실행 약 $70~120 + 파일럿·채점 약 $10~20. 최악(9 run 모두 상한 도달) $360.
- 구독 요금제로 실행하면 `total_cost_usd`는 API 단가 환산값이고 실제 제약은 사용량 한도다. 9 run을 하루에 몰면 한도에 걸릴 수 있으므로 라운드 단위로 나눠 실행한다.
- 상한에 걸려 중단된 run은 그 시점 결과로 채점하고 "예산 초과"로 기록한다.

## 12. 후속 실험 (2차, 선택)

1차 결과를 본 뒤 필요하면 **입력 상세도**를 두 번째 변수로 추가한다.

|  | 일반 세션 | 오케스트레이션 |
|---|---|---|
| 짧은 프롬프트 ("주문 API 만들어줘, 재고 차감 포함") | ① | ② |
| `feature.md` (1차와 동일) | ③ | ④ |

- 가설: 요구사항이 모호할수록 오케스트레이션(요구 분해·설계 단계)의 이점이 커진다.
- 한계: 짧은 프롬프트 조건은 외부 계약이 없어 같은 인수 테스트를 돌릴 수 없다 → 요구사항 체크리스트 기반 판정(수동 + LLM)으로 채점하며, 1차보다 객관성이 낮다.
- ③·④는 1차 결과를 재사용할 수 있다.
