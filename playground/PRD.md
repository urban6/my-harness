# PRD — 개발 방식별 결과 점수화 실험 (일반 · 스킬 · 오케스트레이션)

> 상태: 확정 · 2026-10-09 · 요구사항: [`feature.md`](feature.md)
> 미결: C군 워커의 스킬 접근 수정 여부 (파일럿 후 결정)

## 1. 목적

같은 요구사항(`feature.md`)과 같은 프롬프트로 **일반(A) · 스킬(B) · 오케스트레이션(C)** 세 방식이 각각 3회씩 개발하고, 그 결과를 **같은 기준으로 점수화**한다. 어느 방식이 낫다는 가설을 판정하지 않는다 — 점수를 한 표에 나란히 놓는 것까지가 이 실험의 범위다.

최종 결과는 아래 한 표로 낸다.

| 군 | 정확도 (60) | 테스트 품질 (30) | 완료성 (10) | **총점 (100)** | 비용 ($) | 시간 (분) |
|---|---|---|---|---|---|---|
| A 일반 | | | | | | |
| B 스킬 | | | | | | |
| C 오케스트레이션 | | | | | | |

- 각 칸은 3회 평균과 (최소~최대). run별 점수 9행은 `REPORT.md`에 별도 표로 둔다.
- 비용·시간은 점수에 넣지 않는 참고 열이다.

## 2. 비교군

| 군 | 정의 | 군별 실행 옵션 |
|---|---|---|
| A Vanilla | 하니스 없음, 단일 세션 | `--disable-slash-commands --disallowedTools Agent` |
| B Skills-only | `spring-boot` 스킬만, 단일 세션 | `--disallowedTools Agent --append-system-prompt "Spring Boot 코드는 spring-boot 스킬을 따른다."` |
| C Orchestration | `feature-pm` + 워커 4종 + 스킬 | `--agent feature-pm` |

- 공통 옵션: `-p --output-format stream-json --verbose --model claude-opus-5-5 --effort high --permission-mode bypassPermissions --max-budget-usd 40 --strict-mcp-config`
- 프롬프트는 모든 군 동일 — 군 차이는 실행 옵션으로만 만든다.

```text
feature.md의 기능을 개발해줘. 완료 조건을 모두 충족시키고, 마지막에 테스트 명령 결과를 그대로 보여줘.
```

## 3. 실험 조건 (모든 군 동일)

| 항목 | 값 |
|---|---|
| 기능 | 주문 + 재고 차감, Spring Boot 3 + JPA + PostgreSQL ([`feature.md`](feature.md), 0단계 후 동결) |
| 스타터 | Spring Boot 3.5.x, Gradle(Groovy), 의존성 고정(web·validation·JPA·PostgreSQL·Flyway·Testcontainers), 코드는 메인 클래스만 |
| 반복 | 군당 3회, 총 9 run, 순차 실행. 라운드마다 군 순서 교체: `B→C→A` / `C→A→B` / `A→B→C` |
| 상한 | run당 $40, 120분. 초과 시 그 시점 결과로 채점 |
| 사람 개입 | 없음 |
| 실행 위치 | `playground/runs/{군}-{회차}/` — run마다 독립 git 저장소 + `.claude/settings.local.json`으로 상위 `CLAUDE.md` 차단(사전 확인 완료)·`acceptance/` 읽기 차단 |

## 4. 채점

### 4.1 품질 점수 (100점)

| 항목 | 배점 | 측정 |
|---|---|---|
| 기능 정확도 | 60 | 숨긴 인수 테스트 통과율 × 60 — `feature.md` 계약만 검증하는 블랙박스 HTTP 테스트 약 30케이스, R7(동시성)은 5회 반복 |
| 테스트 품질 | 30 | 요구사항 커버(R1~R8 중 n/8) × 15 + JaCoCo 분기 커버리지 × 15 |
| 완료성 | 10 | 앱 빌드(`assemble`) 성공 5 + 자체 테스트(`test`) 통과 5 |

- 앱 빌드 실패 → 인수 테스트 0. 자체 테스트 실패는 빌드 실패로 보지 않는다(이중 감점 방지). 자체 테스트 실패 시 1회 재실행.
- 앱 기동: run마다 새 PostgreSQL 컨테이너 + `SPRING_DATASOURCE_*`·`SERVER_PORT` 환경 변수 주입(`feature.md` 런타임 계약).
- JaCoCo는 채점 측 Gradle init script로 주입한다 — 에이전트 빌드 파일은 고치지 않는다. 테스트가 실패해도 리포트가 나오게 실행한다.
- 요구사항 커버: LLM이 자체 테스트를 R1~R8에 매핑하고 근거 테스트명을 남긴다(하니스가 아닌 중립 프롬프트, 군 정보 없이).
- 코드 품질(레이어링·가독성 등)은 점수에 넣지 않는다 — 검증·예외·트랜잭션·동시성은 인수 테스트와 중복되고, 남는 부분은 LLM 주관 판단이라 n=3에서 노이즈가 크다.

### 4.2 결과 표기

- 군별로 항목 점수·총점의 3회 평균과 최소~최대를 적는다(§1 표). 우열 판정은 하지 않는다.
- n=3이라 편차가 클 수 있으므로 평균만이 아니라 범위를 함께 본다.

### 4.3 보조 기록 (점수 미반영, 해석용)

- 인수 테스트 실패 원인 분류 (상태코드 / 필드 / 에러 포맷 / 원자성 / 동시성)
- 종료 상태 (정상 / 예산·시간 초과 / 질문 정지), 자동 압축 횟수, C군 REDO·BLOCKED 횟수

## 5. 실행 계획

| 단계 | 내용 | 통과 기준 / 산출물 |
|---|---|---|
| 0 준비 | 스타터, 숨긴 인수 테스트, **정답 구현**(`acceptance/reference/`), 실행·채점 스크립트 작성, warm-up | 스타터에서 인수 테스트 **전부 실패**, 정답 구현에서 **전부 통과** |
| ✋1 | 스크립트·테스트 목록 보고 후 커밋 | |
| 1 파일럿 | A·B 격리 검사(짧은 프롬프트), C 축소 실행(R1·R2), 채점 파이프라인 시험 | 격리 정상, 헤드리스에서 워커 완료까지 유지, 워커 스킬 접근 여부 |
| ✋2 | 결과 보고 → 하니스 수정·예산 조정·본 실행 진입 결정 | |
| 2 본 실행 | `run.sh {군} {회차}` × 9, 라운드마다 바로 채점(`grade.sh`) | `runs/{군}-{회차}/`, `results/{run}.json` |
| ✋3 | 라운드마다 종료 상태·비용·시간 보고 | |
| 3 요구사항 매핑 | 9개 run의 자체 테스트 ↔ R1~R8 매핑(LLM) | `results/coverage-map.json` |
| 4 보고서 | 점수 환산 → §1의 표 + run별 점수 표 + 보조 기록 | `REPORT.md` |

예상: API 비용 약 $75~140 (최악 $360), 실행 기준 1~3일.

- 정답 구현은 인수 테스트 자체의 오류를 잡는 양성 대조다. 점수 비교에 넣지 않는다. 테스트와 정답 구현이 어긋나면 `feature.md` 문구를 기준으로 판정하고, 테스트를 정답 구현에 맞춰 고치지 않는다.
- run이 숨긴 테스트 경로에 접근했거나 격리가 깨졌으면 폐기 후 재실행한다.

## 6. 디렉터리

```

├── starter/        # 공통 스타터

```

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| 헤드리스에서 백그라운드 워커 완료 전 종료 | 파일럿 확인. 문제 시 전 군을 대화형 CLI로 전환(군마다 방식 섞지 않음) |
| C군 워커에 `Skill` 도구가 없어 스킬 지시를 이행 못 함 | 파일럿 확인, 필요 시 본 실행 전 하니스 수정(별도 커밋) |
| 인수 테스트 자체 오류 | 음성·양성 대조 |
| 숨긴 테스트 노출 | `permissions.deny` + 로그 접근 검사 |
| run 무한 대기 | `timeout 120m` + run 사이 프로세스·컨테이너 정리 |

## 부록 — 설계 근거

- **같은 프롬프트, 다른 시스템 지시**: 사용자 프롬프트는 세 군이 같지만, B는 스킬 지시가, C는 `feature-pm` 정의가 세션 지시로 들어간다. "스킬을 쓴다"·"오케스트레이터를 쓴다"는 것 자체가 이 차이다.
- **B군에 스킬 명시 지시**: 컨벤션 스킬은 자동 발동이 거의 없다(과거 headless 30회 중 0회). C군도 PM이 스킬을 명시 주입하므로 B에도 줘야 공정하다.
- **C군을 `--agent feature-pm`로 실행**: `feature-pm`은 메인 세션에서 호출해야 워커를 띄울 수 있다. "feature-pm 에이전트로 ~"라고 부르면 서브에이전트가 되어 워커를 못 띄울 수 있다(`prompts/feature-development.md` A안의 잠재 이슈).
- **`feature.md`는 "무엇을"만**: 경로·상태코드·규칙은 적고 테이블·레이어·락 방식은 적지 않는다. 설계를 적으면 일반 세션도 설계를 공짜로 받아 C의 강점(요구 분해·설계)을 잴 수 없다.
- **기록만 하는 환경 변수**: 전역 자동 압축 40%(단일 세션 A·B에 더 자주 걸릴 수 있음), `AGENT_TEAMS=1`, 전역 훅(Orca, 출력 없음), C군 워커 모델 혼합(opus/sonnet).
- **후속 실험(선택)**: "짧은 프롬프트 vs `feature.md`"를 두 번째 변수로 둔 2×2 비교 — 요구사항 상세도에 따라 점수가 어떻게 달라지는지.
