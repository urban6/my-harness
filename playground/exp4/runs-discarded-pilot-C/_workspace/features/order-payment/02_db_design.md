# order-payment — DB 설계 (02_db_design.md)

스택: PostgreSQL + Flyway + Spring Data JPA(Hibernate 6.6, `ddl-auto: validate`). 마이그레이션 파일: `src/main/resources/db/migration/V1__init_schema.sql`.
응답 필드 ↔ 컬럼 대응표, 제약 ↔ 상태코드 매핑표는 **`01_api_design.md` 끝의 "정합 요약"** 이 유일한 기준이다(여기에 복제하지 않는다). 흐름 단계 번호(5·6·7·8절)도 01 문서를 참조한다.

---

## 1. 테이블 개요

| 테이블 | 역할 |
|---|---|
| `products` | 상품, `stock`/`reserved` 카운터 |
| `coupons` | 쿠폰, `used_count`(저장 컬럼) |
| `orders` | 주문(금액 스냅샷·상태·만료·PG 결제 id·게이트웨이 호출 표지) |
| `order_items` | 주문 항목(주문 시점 `unit_price` 스냅샷) |
| `idempotency_keys` | 멱등 키 + 요청 지문 + 최초 응답 |

별도 `coupon_usage`·`payments` 테이블은 두지 않는다. 근거: 쿠폰 "사용 중" 여부는 `orders.status`로 이미 표현되고(부분 유니크 인덱스로 강제), PG `paymentId`는 주문당 최대 1개라 `orders.payment_id` 한 컬럼으로 충분하다.

## 2. 타입 결정

- 금액·수량·카운터 전부 `BIGINT`(Java `long`). 시각 전부 `TIMESTAMPTZ`(Java `Instant`, 마이크로초 절삭은 01 문서 0.2절). id는 `BIGINT GENERATED BY DEFAULT AS IDENTITY`(엔티티 `GenerationType.IDENTITY`).
- 문자열은 `VARCHAR(n)`만 사용(`CHAR(n)`은 Hibernate `validate`와 불일치 — `bpchar`). 응답 본문은 `TEXT`(`jsonb`는 키 순서·공백을 바꾸므로 재생 바이트 동일성을 깨서 금지). `idempotency_keys.response_status`는 `INTEGER`(`SMALLINT`는 Java `Integer`와 validate 불일치).
- 상태·타입은 `VARCHAR` + `CHECK ... IN (...)`, 엔티티는 `@Enumerated(EnumType.STRING)`. PG 네이티브 enum 타입은 쓰지 않는다(마이그레이션·Hibernate 매핑 부담).
- 엔티티 `@Version` 없음: 카운터는 원자적 조건부 UPDATE, 주문 상태 전이는 비관적 행 락으로 보호한다.

## 3. 마이그레이션 초안 — `V1__init_schema.sql`

```sql
-- ===== products =====
CREATE TABLE products (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    price       BIGINT       NOT NULL,
    stock       BIGINT       NOT NULL,
    reserved    BIGINT       NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ  NOT NULL,
    CONSTRAINT ck_products_name     CHECK (length(btrim(name)) > 0),
    CONSTRAINT ck_products_price    CHECK (price BETWEEN 1 AND 10000000),
    CONSTRAINT ck_products_stock    CHECK (stock >= 0),
    CONSTRAINT ck_products_reserved CHECK (reserved >= 0 AND reserved <= stock)
);

-- ===== coupons =====
CREATE TABLE coupons (
    id                   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code                 VARCHAR(20)  NOT NULL,
    type                 VARCHAR(5)   NOT NULL,
    value                BIGINT       NOT NULL,
    min_order_amount     BIGINT       NOT NULL DEFAULT 0,
    max_discount_amount  BIGINT,
    total_quantity       BIGINT       NOT NULL,
    used_count           BIGINT       NOT NULL DEFAULT 0,
    valid_from           TIMESTAMPTZ  NOT NULL,
    valid_until          TIMESTAMPTZ  NOT NULL,
    created_at           TIMESTAMPTZ  NOT NULL,
    CONSTRAINT uq_coupons_code        UNIQUE (code),
    CONSTRAINT ck_coupons_code        CHECK (code ~ '^[A-Z0-9]{4,20}$'),
    CONSTRAINT ck_coupons_type        CHECK (type IN ('FIXED', 'RATE')),
    CONSTRAINT ck_coupons_value       CHECK ((type = 'FIXED' AND value >= 1)
                                          OR (type = 'RATE'  AND value BETWEEN 1 AND 100)),
    CONSTRAINT ck_coupons_min_order   CHECK (min_order_amount >= 0),
    CONSTRAINT ck_coupons_max_disc    CHECK (max_discount_amount IS NULL OR max_discount_amount >= 1),
    CONSTRAINT ck_coupons_total       CHECK (total_quantity >= 1),
    CONSTRAINT ck_coupons_used        CHECK (used_count >= 0 AND used_count <= total_quantity),
    CONSTRAINT ck_coupons_period      CHECK (valid_from < valid_until)
);

-- ===== orders =====
CREATE TABLE orders (
    id                       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id                  VARCHAR(50)  NOT NULL,
    status                   VARCHAR(20)  NOT NULL,
    coupon_id                BIGINT       REFERENCES coupons (id),
    coupon_code              VARCHAR(20),                       -- 응답용 비정규화(쿠폰은 불변), 목록 조인 제거
    subtotal                 BIGINT       NOT NULL,
    discount                 BIGINT       NOT NULL,
    total_price              BIGINT       NOT NULL,
    created_at               TIMESTAMPTZ  NOT NULL,
    expires_at               TIMESTAMPTZ  NOT NULL,
    paid_at                  TIMESTAMPTZ,
    payment_id               VARCHAR(100),                      -- PG paymentId (환불 호출용). 외부 비노출
    gateway_call_started_at  TIMESTAMPTZ,                       -- PG 결제/환불 호출 진행 표지 (NULL=없음). 외부 비노출
    CONSTRAINT ck_orders_status   CHECK (status IN ('PENDING_PAYMENT','PAID','SHIPPED','DELIVERED',
                                                    'PAYMENT_FAILED','EXPIRED','CANCELLED','REFUNDED')),
    CONSTRAINT ck_orders_amounts  CHECK (subtotal >= 0 AND discount >= 0 AND discount <= subtotal
                                         AND total_price = subtotal - discount),
    CONSTRAINT ck_orders_coupon   CHECK ((coupon_id IS NULL) = (coupon_code IS NULL)),
    CONSTRAINT ck_orders_expiry   CHECK (expires_at >= created_at),
    CONSTRAINT ck_orders_paid_at  CHECK ((status IN ('PAID','SHIPPED','DELIVERED','REFUNDED')) = (paid_at IS NOT NULL))
);

-- 같은 사용자가 같은 쿠폰을 "사용 중"(활성 상태) 주문으로 두 개 가질 수 없다. 상태가 복원 상태로 바뀌면 인덱스에서 자동 제외.
CREATE UNIQUE INDEX uq_orders_active_coupon_user
    ON orders (coupon_id, user_id)
    WHERE coupon_id IS NOT NULL
      AND status IN ('PENDING_PAYMENT', 'PAID', 'SHIPPED', 'DELIVERED');

-- 목록 (키셋) — 필터 조합별
CREATE INDEX idx_orders_created_id        ON orders (created_at DESC, id DESC);
CREATE INDEX idx_orders_user_created_id   ON orders (user_id,  created_at DESC, id DESC);
CREATE INDEX idx_orders_status_created_id ON orders (status,   created_at DESC, id DESC);

-- 만료 스위퍼 / 지연 만료 (PENDING 행만 담는 작은 인덱스)
CREATE INDEX idx_orders_pending_expires   ON orders (expires_at) WHERE status = 'PENDING_PAYMENT';

-- ===== order_items =====
CREATE TABLE order_items (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,   -- 항목 순서 = 요청 순서
    order_id    BIGINT NOT NULL REFERENCES orders (id),
    product_id  BIGINT NOT NULL REFERENCES products (id),
    quantity    BIGINT NOT NULL,
    unit_price  BIGINT NOT NULL,
    CONSTRAINT uq_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_quantity   CHECK (quantity BETWEEN 1 AND 1000),
    CONSTRAINT ck_order_items_unit_price CHECK (unit_price >= 1)
);

-- ===== idempotency_keys =====
CREATE TABLE idempotency_keys (
    id                   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    endpoint             VARCHAR(20)  NOT NULL,       -- 'ORDER_CREATE' | 'ORDER_PAY'
    idem_key             VARCHAR(64)  NOT NULL,
    request_fingerprint  VARCHAR(64)  NOT NULL,       -- SHA-256 hex (소문자 64자)
    status               VARCHAR(12)  NOT NULL,       -- 'IN_PROGRESS' | 'COMPLETED'
    attempt_id           UUID         NOT NULL,       -- 이 시도의 소유 토큰 (인수/해제/완료의 CAS 조건)
    started_at           TIMESTAMPTZ  NOT NULL,       -- IN_PROGRESS 신선도 판정 기준
    completed_at         TIMESTAMPTZ,
    response_status      INTEGER,                     -- 최초 응답 상태코드 (COMPLETED에서만)
    response_content_type VARCHAR(100),
    response_location    VARCHAR(255),
    response_body        TEXT,                        -- 최초 응답 본문 문자열 그대로 (재생용)
    CONSTRAINT uq_idem_endpoint_key  UNIQUE (endpoint, idem_key),
    CONSTRAINT ck_idem_endpoint      CHECK (endpoint IN ('ORDER_CREATE', 'ORDER_PAY')),
    CONSTRAINT ck_idem_status        CHECK (status IN ('IN_PROGRESS', 'COMPLETED')),
    CONSTRAINT ck_idem_completed     CHECK ((status = 'COMPLETED') = (response_status IS NOT NULL AND response_body IS NOT NULL))
);
```

`order_items`에 상품 FK 인덱스는 두지 않는다(상품 삭제 기능 없음, 조회는 `order_id` 기준이며 `uq_order_items_order_product`가 `order_id` 선두 인덱스 역할).
`ck_orders_paid_at`: 승인 시점에 `status=PAID`와 `paid_at`을 같은 UPDATE로 쓰므로 위반하지 않는다. 구현이 이 불변식을 깨면 500으로 드러난다(의도).

## 4. `usedCount`는 저장 컬럼 (결정)

- **결정**: `coupons.used_count` 저장 컬럼 + 불변식 `used_count == COUNT(활성 상태 주문 where coupon_id)`. 파생 COUNT 방식 불채택.
- 근거: (1) 소진 판정을 `UPDATE coupons SET used_count = used_count + 1 WHERE id=? AND used_count < total_quantity` 한 문장의 원자적 조건부 UPDATE로 처리해 R10.2를 보장한다(파생이면 어차피 쿠폰 행 락 + COUNT 스캔이 필요). (2) GET 쿠폰이 단순 읽기. (3) 주문 상태 전이와 같은 트랜잭션에서만 증감하므로 어긋남이 생기지 않는다. 방어: `ck_coupons_used`(0 ≤ used ≤ total).
- 증가: 주문 생성 트랜잭션(01 5절 6단계). 감소(`used_count - 1 WHERE used_count > 0`): CANCELLED / EXPIRED / PAYMENT_FAILED / REFUNDED 전이와 **같은 트랜잭션**.
- 테스트 불변식(권장): 임의 시나리오 종료 후 모든 쿠폰에서 `used_count`가 `SELECT count(*) FROM orders WHERE coupon_id=? AND status IN ('PENDING_PAYMENT','PAID','SHIPPED','DELIVERED')`와 같다.

## 5. 사용자별 쿠폰 중복 사용 방지 (R2.5/R2.6/R10.3)

두 겹으로 보장한다.
1. **직렬화 + 사전 조회 (1차, 결정적 오류 코드 보장)**: 주문 생성 트랜잭션이 쿠폰 행을 `SELECT ... FOR UPDATE`(PESSIMISTIC_WRITE)로 잠근 뒤 `EXISTS(SELECT 1 FROM orders WHERE coupon_id=? AND user_id=? AND status IN (활성 4개))`를 확인한다. 같은 쿠폰의 모든 주문 생성이 쿠폰 행 락으로 직렬화되므로 같은 사용자의 동시 5건은 하나씩 평가되어 정확히 1건 201, 나머지 `COUPON_NOT_APPLICABLE`(READ COMMITTED에서 락 획득 후 실행하는 문장은 앞선 커밋을 본다).
2. **부분 유니크 인덱스 `uq_orders_active_coupon_user` (2차, 최후 방어)**: 위 사전 조회가 우회되는 경로(버그·락 누락)에서도 INSERT 시점에 중복이 거부된다. 위반을 제약명으로 식별해 409 `COUPON_NOT_APPLICABLE`로 매핑.
- **복원 시 해제**: 인덱스 술어가 `status IN (활성 4개)`라서 `CANCELLED/EXPIRED/PAYMENT_FAILED/REFUNDED`로 UPDATE되는 순간 그 행이 인덱스에서 빠진다 → 같은 사용자가 같은 쿠폰으로 다시 주문 가능. 별도 해제 로직 불필요.
- 소진(`COUPON_EXHAUSTED`)은 쿠폰 행 락 아래의 조건부 UPDATE 영향 행 수(0)로 판정. 락 순서상 서로 다른 사용자 15명(R10.2)은 직렬 처리되어 정확히 5건 성공.

## 6. 락 순서와 데드락 회피 (R10.4)

전역 락 획득 순서(모든 쓰기 경로가 이 순서만 따른다):

1. `idempotency_keys` (자기 키 행 하나뿐 — 다른 락과 교차 대기 없음)
2. `orders` 행 (이미 존재하는 주문을 변경하는 경로에서만)
3. `products` 행 — **항상 `product_id` 오름차순**
4. `coupons` 행

경로별: 생성 = 3(오름차순 조건부 UPDATE) → 4(`FOR UPDATE`) → orders/order_items INSERT. 결제 승인 = 2 → 3(`stock-=q, reserved-=q`). 결제 거절·취소·만료 = 2 → 3(`reserved-=q`) → 4(`used_count-1`). 환불 = 2 → 3(`stock+=q`) → 4. 배송 = 2만.
- `[P,Q]`와 `[Q,P]` 주문이 섞여도 모두 P→Q 순으로 잠그므로 순환 대기가 없다. 요청 항목 순서(응답용 `order_items.id`)와 잠금 순서(정렬된 productId)를 분리한다.
- 생성 경로는 상품 락 → 쿠폰 락 순이고, 해제 경로도 상품 → 쿠폰 순이라 서로 교차하지 않는다. 쿠폰 락을 잡은 트랜잭션은 이미 모든 상품 락을 확보한 뒤이므로 상품 락 대기가 없다.
- 안전망: DB 락 관련 예외(`40P01` deadlock, `40001`)가 나면 PG 호출이 **없는** DB 트랜잭션 단위로 최대 3회 재시도(짧은 백오프). 5xx 누출 방지용이며 설계상 정상 경로에서는 발생하지 않는다.
- 커넥션: 요청 처리 오케스트레이터는 `@Transactional`이 아니다. 멱등 begin → (필요 시) 지연 만료 → 비즈니스 트랜잭션을 `TransactionTemplate`으로 **순차** 실행해 한 요청이 동시에 커넥션 둘을 쥐지 않게 한다(`REQUIRES_NEW` 중첩 금지: 풀 고갈 방지). PG 호출 구간은 커넥션 없음.

## 7. 재고 (R10.1) 와 주문 생성 트랜잭션 경계 (R3.4)

- 예약: `UPDATE products SET reserved = reserved + :q WHERE id = :id AND stock - reserved >= :q` (영향 행 0 → `INSUFFICIENT_STOCK` 예외 → 롤백). 상품 id 오름차순으로 항목마다 실행. 20건 동시, available 10 → 행 락으로 직렬화되어 정확히 10건 성공, 최종 `reserved=10`.
- 복원/확정은 같은 형태의 증감 UPDATE(`reserved - :q`, `stock - :q`, `stock + :q`)만 쓰고 엔티티를 읽어 계산해 저장(lost update)하지 않는다. `@Modifying(clearAutomatically = true, flushAutomatically = true)`.
- 생성 트랜잭션(하나): [상품 조건부 UPDATE ×N → 쿠폰 락·검증·`used_count+1` → `orders` INSERT → `order_items` INSERT → 멱등 레코드 COMPLETED 갱신] → 커밋. 예외는 모두 `RuntimeException`으로 던져 전체 롤백 → "전부 반영 또는 전무". 상품·쿠폰 존재 확인(404)과 `price` 스냅샷은 락 없는 SELECT(상품 불변).
- `createdAt`은 쿠폰 락 획득 후, INSERT 직전에 `Clock`에서 읽는다(01 문서 5·9절).

## 8. 결제·환불 트랜잭션 전략 (R5, R7.3, R10.5)

- **PG 호출 중 락 없음**. 흐름: TX-A(주문 행 `FOR UPDATE` → 판정 → `gateway_call_started_at = now` 표지 → 커밋) → PG 호출 → TX-B(주문 행 `FOR UPDATE` → `gateway_call_started_at`가 내가 찍은 값과 같은지 확인 → 결과 반영 → 표지 NULL → 커밋).
- 표지 신선도: `gateway_call_started_at > :now - in-flight-timeout(10s)`면 "진행 중". PG 타임아웃이 2초이므로 정상 흐름은 항상 10초 안에 끝난다. 10초보다 오래된 표지는 크래시 잔재로 보고 무시(덮어쓰기 가능, 스위퍼의 만료 대상에서도 제외하지 않음).
- 표지는 `PENDING_PAYMENT`(결제)와 `PAID`(환불)에만 의미가 있고, 승인/거절/환불 성공으로 상태가 바뀔 때 함께 NULL이 된다. 별도 상태값을 만들지 않으므로 `ck_orders_status`는 feature.md 열거만 허용한다.
- `payment_id`: 승인 TX-B에서 저장(`VARCHAR(100)`, PG가 숫자를 주면 문자열화). 환불 호출 경로 `POST /v1/payments/{payment_id}/refund`에 사용. `totalPrice=0`으로 결제된 주문은 `payment_id`가 NULL이며 환불 시 PG 호출을 생략(01 문서 7.1 6단계).
- 환불 PG 장애: TX-B' = 표지만 NULL, `status`·`stock`·쿠폰 불변.
- `totalPrice == 0` 결제: TX-A 안에서 곧바로 승인 효과 적용(PG 호출 없음).
- R10.5: 동일 주문 동시 결제는 TX-A의 `FOR UPDATE`로 직렬화되고, 표지가 찍힌 뒤 들어온 요청은 409. PG 호출은 최대 1회.

## 9. 멱등성 메커니즘 (R4) — 외부 계약은 01 문서 11절

`IdempotencyService`(트랜잭션 밖 오케스트레이션에서 호출, 각 연산은 자체 짧은 트랜잭션):

1. **begin(endpoint, key, fingerprint)** (자체 트랜잭션, 즉시 커밋)
   - `INSERT ... ON CONFLICT (endpoint, idem_key) DO NOTHING` (`status=IN_PROGRESS`, 새 `attempt_id`, `started_at=now`). 1행 삽입 → **PROCEED(attempt_id)**.
   - 0행(충돌) → 기존 행 `SELECT`:
     - 행이 사라졌으면(동시 해제) 1회 재시도.
     - `request_fingerprint` ≠ → **422**.
     - `COMPLETED` → **REPLAY**(저장된 `response_status`, `response_body`, `response_content_type`, `response_location`).
     - `IN_PROGRESS`이고 `started_at > now - idempotency.in-progress-timeout(30s)` → **409 IDEMPOTENCY_IN_PROGRESS**.
     - `IN_PROGRESS`이고 오래됨(크래시 잔재) → `UPDATE ... SET attempt_id=:new, started_at=:now WHERE id=:id AND attempt_id=:old AND status='IN_PROGRESS'` CAS 성공 시 **PROCEED(인수)**, 실패 시 409.
2. **complete(id, attempt_id, status, contentType, location, body)**: 비즈니스 트랜잭션 **안**에서 `UPDATE ... SET status='COMPLETED', response_*=..., completed_at=now WHERE id=:id AND attempt_id=:mine AND status='IN_PROGRESS'`. 생성은 주문 INSERT와 같은 트랜잭션이라 "주문은 생겼는데 응답은 저장 안 됨"이 없다. 결제는 승인 TX-B(또는 0원 TX-A)에서 수행. 0행이면(인수당함) 예외 → 비즈니스 롤백.
3. **release(id, attempt_id)**: 2xx가 아닌 모든 종료(400 이후 단계의 404/409/402/503, 예기치 않은 예외 포함)에서 `DELETE ... WHERE id=:id AND attempt_id=:mine AND status='IN_PROGRESS'`(자체 트랜잭션). COMPLETED는 절대 지우지 않는다 → R4.4: 오류 요청의 키는 같은 요청으로 재시도 가능.
- **지문**: SHA-256 hex(소문자 64자) = `v1|{X-User-Id 또는 빈 값}|POST|{/api/orders 또는 /api/orders/{long id}/pay}|{정규화 본문}` (정규화 본문은 01 문서 11절). 결제 지문에 `orderId`가 있으므로 같은 키로 다른 주문을 결제하면 422.
- **서버 크래시**: begin 후 크래시하면 `IN_PROGRESS`가 남는다. 30초 후 같은 키 요청이 인수해 재처리한다. 결제는 PG가 같은 `Idempotency-Key`에 최초 결과를 돌려주므로 재처리해도 이중 결제가 없고, 주문 게이트웨이 표지(10초)도 그 시점엔 만료되어 재시도가 가능하다. 30초 이내 재요청은 409 IN_PROGRESS.
- 재생 시 응답: 저장된 본문 문자열을 `ResponseEntity<String>`으로 그대로 반환(`Content-Type: application/json`, 저장된 Location). 최초 응답도 같은 문자열을 반환해 바이트 동일. 현재 주문 상태로 재렌더링 금지.
- 키 만료/정리는 범위 밖(제외 항목). 인덱스는 `uq_idem_endpoint_key`가 조회 경로를 모두 커버.
- 엔드포인트별 키 공간 독립: 유니크가 `(endpoint, idem_key)`.

## 10. 만료·지연 만료 SQL 형태 (R6)

- 후보 조회: `SELECT id FROM orders WHERE status='PENDING_PAYMENT' AND expires_at <= :now AND (gateway_call_started_at IS NULL OR gateway_call_started_at <= :now - :inFlightTimeout) ORDER BY expires_at LIMIT 100` — `idx_orders_pending_expires`.
- 주문별 처리(자체 트랜잭션): `SELECT ... WHERE id=:id FOR UPDATE` → 같은 조건 재확인(상태·`expires_at`·표지) → `status='EXPIRED'` → 상품 `reserved -= q`(id 오름차순) → 쿠폰 `used_count - 1`. 락 대기가 길어지는 경우(결제 TX-A/B 중)에도 행 락 하나뿐이라 안전.
- 스케줄러 스레드 1개(기본 `@Scheduled`), 읽기 경로의 지연 만료는 요청 스레드에서 동일 서비스를 호출. 같은 주문을 둘이 동시에 처리해도 행 락 + 상태 재확인으로 한 번만 반영.

## 11. 목록 키셋 쿼리 형태 (R9)

```sql
SELECT o.* FROM orders o
 WHERE [o.user_id = :userId] [AND o.status = :status]
       [AND (o.created_at, o.id) < (:cursorCreatedAt, :cursorId)]
 ORDER BY o.created_at DESC, o.id DESC
 LIMIT :size + 1;
```
- `:cursorCreatedAt`은 커서의 epoch 마이크로초를 `Instant`로 복원(마이크로초 정확). `orders.created_at`은 앱이 마이크로초로 절삭해 저장하므로 비교가 손실 없다.
- 인덱스 선택: 필터 없음 `idx_orders_created_id`, `userId`만/둘 다 `idx_orders_user_created_id`(status는 필터), `status`만 `idx_orders_status_created_id`.
- 조건은 `(:p IS NULL OR ...)` 패턴이 아니라 동적 SQL 조립(PostgreSQL 파라미터 타입 추론 오류·플랜 열화 방지).
- 항목 로딩: `Order.items`는 `@OneToMany(fetch = LAZY) @OrderBy("id ASC") @BatchSize(size = 100)`. 페이지당 쿼리 = orders 1 + items 1(IN). 쿠폰 코드는 `orders.coupon_code`.

## 12. JPA 매핑 메모 (구현 단계 참조)

- 모든 컬럼명은 snake_case(Boot 기본 물리 네이밍과 일치). `Instant` ↔ `TIMESTAMPTZ`, `String` ↔ `VARCHAR`/`TEXT`(`response_body`는 `@Column(columnDefinition = "text")`), `UUID` ↔ `uuid`. `validate`가 `TEXT`에서 마찰을 일으키면 `ddl-auto: none`으로 낮춘다(Flyway가 스키마 소유이므로 허용).
- 상태 전이용 조회: `@Lock(PESSIMISTIC_WRITE) findLockedById(id)` (Postgres `FOR UPDATE`). 일반 GET은 락 없는 조회.
- 제약 위반 식별은 Hibernate `ConstraintViolationException#getConstraintName()`(예 `uq_coupons_code`, `uq_orders_active_coupon_user`)으로 하고 메시지 파싱은 하지 않는다. 쿠폰 INSERT는 `saveAndFlush`로 제약 위반을 즉시 노출.
- 격리 수준은 PostgreSQL 기본 READ COMMITTED 유지. 조건부 UPDATE는 락 대기 후 WHERE를 재평가하므로 정확하다.

## 13. 설계 불변식 (검증용 체크리스트)

1. `products`: `0 ≤ reserved ≤ stock` (DB CHECK).
2. `coupons`: `0 ≤ used_count ≤ total_quantity`, `used_count`는 활성 상태 주문 수와 같다.
3. 활성 상태 주문은 `(coupon_id, user_id)`당 최대 1개.
4. `reserved` 합계 = `PENDING_PAYMENT` 주문들의 수량 합(상품별). 결제 승인으로 `stock`과 `reserved`가 함께 줄고, 환불로 `stock`만 복원된다.
5. COMPLETED 멱등 레코드의 `response_body`는 불변(재생 바이트 동일).
6. `orders.paid_at`은 `PAID/SHIPPED/DELIVERED/REFUNDED`에서만 non-null.
