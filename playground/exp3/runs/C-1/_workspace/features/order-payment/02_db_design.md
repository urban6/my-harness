# order-payment — DB 설계 (02_db_design.md)

스택: PostgreSQL + Flyway + Spring Data JPA/Hibernate(`ddl-auto=validate`).
필드 ↔ 컬럼 대응표, 제약 ↔ HTTP 매핑표, R↔설계 매핑은 **복제하지 않고** `01_api_design.md` "정합 요약"(A/B/C)을 기준으로 한다. 이 문서는 DDL, 인덱스, 원자 갱신 SQL 패턴, 엔티티 매핑 주의점만 다룬다.

## 1. 테이블 개요

| 테이블 | 역할 | 비고 |
|---|---|---|
| `products` | 상품·재고(stock/reserved) | 카운터는 조건부 UPDATE로만 변경 |
| `coupons` | 쿠폰 정의·사용 수량 | `used_count`는 조건부 UPDATE로만 변경 |
| `orders` | 주문 헤더, 상태, 멱등키, 결제/환불 리스 | 상태 변경은 조건부 UPDATE로만 |
| `order_items` | 주문 항목(가격 스냅샷) | |
| `payments` | 주문 1:1 PG 결제 기록(결제 멱등키·pg_payment_id) | cardToken 원문 저장 금지 |

결정 요약
- 금액: `BIGINT`(정수 원). 수량·재고: `INTEGER`. 시각: `TIMESTAMPTZ`. 불리언·enum: `VARCHAR + CHECK`(PG native enum 금지 — Hibernate validate 불일치 방지).
- 모든 UNIQUE/CHECK/FK에 **명시적 이름**을 붙인다(예외 → problem 변환 시 제약명으로 식별: `uk_coupons_code`, `uk_orders_user_idem`, `uk_payments_order`).
- `available`은 컬럼이 아니다(계산값).

## 2. Flyway 계획

위치 `src/main/resources/db/migration` (현재 `.gitkeep`만 존재). 기존 `.gitkeep`은 유지해도 무방.

| 파일 | 내용 |
|---|---|
| `V1__create_catalog_tables.sql` | `products`, `coupons` |
| `V2__create_order_tables.sql` | `orders`, `order_items`, 주문 관련 인덱스 |
| `V3__create_payments_table.sql` | `payments` |

- 이후 변경은 항상 새 버전 파일(`V4__…`)로 추가 — 적용된 파일 수정 금지(체크섬 불일치).
- 테스트: Testcontainers `postgres:16` 이상 이미지, Flyway가 기동 시 적용. `spring.jpa.hibernate.ddl-auto=validate`가 엔티티↔스키마 일치를 기동 시 검증하므로 매핑 오류는 컨텍스트 로딩 실패로 드러난다.

### V1__create_catalog_tables.sql (초안)

```sql
CREATE TABLE products (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    name        VARCHAR(255) NOT NULL,
    price       BIGINT       NOT NULL,
    stock       INTEGER      NOT NULL,
    reserved    INTEGER      NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ  NOT NULL,
    updated_at  TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_products          PRIMARY KEY (id),
    CONSTRAINT ck_products_price    CHECK (price >= 0),
    CONSTRAINT ck_products_stock    CHECK (stock >= 0),
    CONSTRAINT ck_products_reserved CHECK (reserved >= 0 AND reserved <= stock)
);

CREATE TABLE coupons (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY,
    code                VARCHAR(64)  NOT NULL,
    type                VARCHAR(10)  NOT NULL,
    value               BIGINT       NOT NULL,
    min_order_amount    BIGINT       NOT NULL DEFAULT 0,
    max_discount_amount BIGINT,
    total_quantity      INTEGER      NOT NULL,
    used_count          INTEGER      NOT NULL DEFAULT 0,
    valid_from          TIMESTAMPTZ  NOT NULL,
    valid_until         TIMESTAMPTZ  NOT NULL,
    created_at          TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_coupons            PRIMARY KEY (id),
    CONSTRAINT uk_coupons_code       UNIQUE (code),
    CONSTRAINT ck_coupons_type       CHECK (type IN ('FIXED', 'RATE')),
    CONSTRAINT ck_coupons_value      CHECK (value > 0 AND (type <> 'RATE' OR value <= 100)),
    CONSTRAINT ck_coupons_min_order  CHECK (min_order_amount >= 0),
    CONSTRAINT ck_coupons_max_disc   CHECK (max_discount_amount IS NULL OR max_discount_amount >= 0),
    CONSTRAINT ck_coupons_total      CHECK (total_quantity >= 1),
    CONSTRAINT ck_coupons_used       CHECK (used_count >= 0 AND used_count <= total_quantity),
    CONSTRAINT ck_coupons_period     CHECK (valid_from < valid_until)
);
```

### V2__create_order_tables.sql (초안)

```sql
CREATE TABLE orders (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY,
    user_id          VARCHAR(64)  NOT NULL,
    status           VARCHAR(20)  NOT NULL,
    coupon_id        BIGINT,
    coupon_code      VARCHAR(64),
    subtotal         BIGINT       NOT NULL,
    discount         BIGINT       NOT NULL DEFAULT 0,
    total_price      BIGINT       NOT NULL,
    idempotency_key  VARCHAR(128) NOT NULL,
    request_hash     VARCHAR(64)  NOT NULL,
    created_at       TIMESTAMPTZ  NOT NULL,
    expires_at       TIMESTAMPTZ  NOT NULL,
    paid_at          TIMESTAMPTZ,
    shipped_at       TIMESTAMPTZ,
    delivered_at     TIMESTAMPTZ,
    updated_at       TIMESTAMPTZ  NOT NULL,
    lease_kind       VARCHAR(10),
    lease_token      UUID,
    lease_expires_at TIMESTAMPTZ,
    version          BIGINT       NOT NULL DEFAULT 0,
    CONSTRAINT pk_orders PRIMARY KEY (id),
    CONSTRAINT fk_orders_coupon FOREIGN KEY (coupon_id) REFERENCES coupons (id),
    CONSTRAINT uk_orders_user_idem UNIQUE (user_id, idempotency_key),
    CONSTRAINT ck_orders_status CHECK (status IN
        ('PENDING_PAYMENT','PAID','PAYMENT_FAILED','EXPIRED','CANCELLED','REFUNDED','SHIPPED','DELIVERED')),
    CONSTRAINT ck_orders_amounts CHECK (
        subtotal >= 0 AND discount >= 0 AND discount <= subtotal AND total_price = subtotal - discount),
    CONSTRAINT ck_orders_coupon_pair CHECK (
        (coupon_id IS NULL AND coupon_code IS NULL AND discount = 0)
        OR (coupon_id IS NOT NULL AND coupon_code IS NOT NULL)),
    CONSTRAINT ck_orders_paid_at CHECK (
        status NOT IN ('PAID','SHIPPED','DELIVERED','REFUNDED') OR paid_at IS NOT NULL),
    CONSTRAINT ck_orders_lease CHECK (
        (lease_kind IS NULL AND lease_token IS NULL AND lease_expires_at IS NULL)
        OR (lease_kind IN ('PAY','REFUND') AND lease_token IS NOT NULL AND lease_expires_at IS NOT NULL))
);

CREATE TABLE order_items (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY,
    order_id    BIGINT  NOT NULL,
    line_no     INTEGER NOT NULL,
    product_id  BIGINT  NOT NULL,
    quantity    INTEGER NOT NULL,
    unit_price  BIGINT  NOT NULL,
    CONSTRAINT pk_order_items PRIMARY KEY (id),
    CONSTRAINT fk_order_items_order   FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT uk_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT uk_order_items_order_line    UNIQUE (order_id, line_no),
    CONSTRAINT ck_order_items_quantity   CHECK (quantity > 0),
    CONSTRAINT ck_order_items_unit_price CHECK (unit_price >= 0)
);

-- 목록 커서(id DESC) + 필터 조합별 인덱스
CREATE INDEX idx_orders_user_status_id ON orders (user_id, status, id DESC);
CREATE INDEX idx_orders_user_id        ON orders (user_id, id DESC);
CREATE INDEX idx_orders_status_id      ON orders (status, id DESC);
-- 만료 스윕: 대기 주문만 expires_at 순
CREATE INDEX idx_orders_pending_expiry ON orders (expires_at) WHERE status = 'PENDING_PAYMENT';
-- FK 보조
CREATE INDEX idx_order_items_product   ON order_items (product_id);
CREATE INDEX idx_orders_coupon         ON orders (coupon_id) WHERE coupon_id IS NOT NULL;
```

인덱스 사용 근거
- 필터 없음: PK(`id`) 역방향 스캔. `userId`만: `idx_orders_user_id`. `userId+status`: `idx_orders_user_status_id`. `status`만: `idx_orders_status_id`. 모두 `WHERE id < :cursor ORDER BY id DESC LIMIT n+1`에 정렬 없이 적중.
- `(user_id, idempotency_key)` 조회/ON CONFLICT는 `uk_orders_user_idem`이 담당.
- `ck_orders_paid_at`: 결제 이후 상태에서 `paid_at` 누락 방지(REFUNDED 포함).

### V3__create_payments_table.sql (초안)

```sql
CREATE TABLE payments (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY,
    order_id         BIGINT       NOT NULL,
    idempotency_key  VARCHAR(128) NOT NULL,
    request_hash     VARCHAR(64)  NOT NULL,   -- SHA-256 hex of cardToken (원문 저장 금지)
    amount           BIGINT       NOT NULL,
    status           VARCHAR(12)  NOT NULL,
    pg_payment_id    VARCHAR(128),
    attempt_count    INTEGER      NOT NULL DEFAULT 1,
    last_error       VARCHAR(255),
    created_at       TIMESTAMPTZ  NOT NULL,
    updated_at       TIMESTAMPTZ  NOT NULL,
    decided_at       TIMESTAMPTZ,
    refunded_at      TIMESTAMPTZ,
    CONSTRAINT pk_payments PRIMARY KEY (id),
    CONSTRAINT fk_payments_order FOREIGN KEY (order_id) REFERENCES orders (id),
    CONSTRAINT uk_payments_order UNIQUE (order_id),
    CONSTRAINT ck_payments_status CHECK (status IN ('INITIATED','APPROVED','DECLINED','REFUNDED')),
    CONSTRAINT ck_payments_amount CHECK (amount >= 0),
    CONSTRAINT ck_payments_attempt CHECK (attempt_count >= 1),
    CONSTRAINT ck_payments_pgid CHECK (status NOT IN ('APPROVED','REFUNDED') OR pg_payment_id IS NOT NULL)
);
CREATE UNIQUE INDEX uk_payments_pg_payment_id ON payments (pg_payment_id) WHERE pg_payment_id IS NOT NULL;
```

`payments.status` 의미: `INITIATED`=결제 시도 기록됨(PG 결과 미확정 포함, 진행 여부는 `orders` 리스로 판단), `APPROVED`/`DECLINED`=PG 확정, `REFUNDED`=환불 완료. 환불 진행/실패는 별도 상태 없이 `APPROVED` + 주문 리스(`REFUND`)로 표현.

## 3. 원자 갱신 SQL 패턴 (구현 지침)

`JdbcClient`(spring-jdbc, starter-data-jpa에 포함) 또는 `@Modifying @Query(nativeQuery=true)`를 사용한다. 파라미터 `:now`는 `Clock`에서 얻은 마이크로초 truncate 값.

```sql
-- (1) 재고 예약 — products를 id 오름차순으로 호출. 0행 → 409 insufficient-stock
UPDATE products SET reserved = reserved + :q, updated_at = :now
 WHERE id = :id AND stock - reserved >= :q;

-- (2) 재고 해제 — claim 성공 트랜잭션에서만. 0행이면 불변식 위반(버그) → 예외(롤백)
UPDATE products SET reserved = reserved - :q, updated_at = :now
 WHERE id = :id AND reserved >= :q;

-- (3) ship 확정 — 한 문장에서 동시 차감
UPDATE products SET stock = stock - :q, reserved = reserved - :q, updated_at = :now
 WHERE id = :id AND reserved >= :q AND stock >= :q;

-- (4) 쿠폰 사용 — 0행이면 재조회로 사유 판정(기간/소진) → 422
UPDATE coupons SET used_count = used_count + 1
 WHERE id = :id AND used_count < total_quantity AND valid_from <= :now AND valid_until >= :now;

-- (5) 쿠폰 반환
UPDATE coupons SET used_count = used_count - 1 WHERE id = :id AND used_count > 0;

-- (6) 주문 생성 선점 — 0행이면 롤백 후 재생/충돌 판정
INSERT INTO orders (user_id, status, coupon_id, coupon_code, subtotal, discount, total_price,
                    idempotency_key, request_hash, created_at, expires_at, updated_at)
VALUES (...)
ON CONFLICT (user_id, idempotency_key) DO NOTHING
RETURNING id;

-- (7) 만료 claim — 1행일 때만 products/coupon 반환 수행
UPDATE orders SET status = 'EXPIRED', updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PENDING_PAYMENT' AND expires_at <= :now
   AND (lease_token IS NULL OR lease_expires_at <= :now);

-- (8) 취소 claim (PENDING)
UPDATE orders SET status = 'CANCELLED', updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PENDING_PAYMENT' AND expires_at > :now
   AND (lease_token IS NULL OR lease_expires_at <= :now);

-- (9) 결제 리스 claim
UPDATE orders SET lease_kind = 'PAY', lease_token = :t, lease_expires_at = :leaseUntil,
                  updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PENDING_PAYMENT' AND expires_at > :now
   AND (lease_token IS NULL OR lease_expires_at <= :now);

-- (10) 결제 완료 반영 (APPROVED / DECLINED 각각 status만 달리)
UPDATE orders SET status = 'PAID', paid_at = :now,
                  lease_kind = NULL, lease_token = NULL, lease_expires_at = NULL,
                  updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PENDING_PAYMENT' AND lease_token = :t;

-- (11) 환불 리스 claim
UPDATE orders SET lease_kind = 'REFUND', lease_token = :t, lease_expires_at = :leaseUntil,
                  updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PAID' AND (lease_token IS NULL OR lease_expires_at <= :now);

-- (12) 환불 완료 반영
UPDATE orders SET status = 'REFUNDED', lease_kind = NULL, lease_token = NULL, lease_expires_at = NULL,
                  updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PAID' AND lease_token = :t;

-- (13) ship / (14) deliver
UPDATE orders SET status = 'SHIPPED', shipped_at = :now, updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'PAID' AND (lease_token IS NULL OR lease_expires_at <= :now);
UPDATE orders SET status = 'DELIVERED', delivered_at = :now, updated_at = :now, version = version + 1
 WHERE id = :id AND status = 'SHIPPED';

-- (15) 게이트웨이 오류 시 리스만 해제 (상태 불변)
UPDATE orders SET lease_kind = NULL, lease_token = NULL, lease_expires_at = NULL,
                  updated_at = :now, version = version + 1
 WHERE id = :id AND lease_token = :t;
```

규칙
- 영향 행 수 1이면 같은 트랜잭션에서 부수효과(products 오름차순 → coupons) 수행. 0이면 부수효과 없이 현재 상태 재조회 후 `01_api_design.md` §3.3 매트릭스대로 409 매핑.
- 트랜잭션 경계: 각 TX는 PG 호출을 포함하지 않는다(결제·환불은 TX-A / 호출 / TX-C 분리). PG 호출 코드는 `@Transactional` 바깥 빈에서 수행(자기호출 프록시 우회 주의: TX-A/TX-C는 별도 빈의 메서드로).
- (9)에서 payments UPSERT: `INSERT INTO payments(order_id,idempotency_key,request_hash,amount,status,attempt_count,created_at,updated_at) VALUES(...,'INITIATED',1,...) ON CONFLICT (order_id) DO UPDATE SET attempt_count = payments.attempt_count + 1, updated_at = :now` (키·해시 일치는 애플리케이션이 먼저 검증).

## 4. 엔티티 매핑 주의점 (`ddl-auto=validate`)

- ID: `@GeneratedValue(strategy = GenerationType.IDENTITY)` + `Long`. (`GENERATED BY DEFAULT AS IDENTITY` 호환)
- 타입 일치(validate가 타입 코드를 비교): `BIGINT`↔`Long/long`, `INTEGER`↔`Integer/int`, `VARCHAR(n)`↔`String`(+`@Column(length=n)` 권장), `TIMESTAMPTZ`↔`Instant`, `UUID`↔`java.util.UUID`. 해시 컬럼은 `CHAR(n)`(bpchar)이 아니라 **`VARCHAR(64)`** 로 선언한 이유가 이것이다. `TEXT` 사용 금지.
- enum: `@Enumerated(EnumType.STRING)` + `VARCHAR`. PG native enum 타입 사용 금지.
- 카운터/상태 컬럼은 **엔티티 save()로 갱신하지 않는다**: `Product.reserved`·`Product.stock`(수정은 생성 시만)·`Coupon.usedCount`·`Order.status/paid_at/lease_*`는 `@Column(updatable = false)`로 막거나 `Order` 엔티티를 `@Immutable`(읽기 모델)로 두고, 변경은 §3의 조건부 UPDATE만 사용. 이유: 더티 체킹이 오래된 값으로 UPDATE해 lost update를 만든다.
- 조건부 UPDATE 후 같은 영속성 컨텍스트에서 재조회하면 1차 캐시의 오래된 엔티티가 반환될 수 있다: `@Modifying(flushAutomatically = true, clearAutomatically = true)`를 쓰거나 후속 조회를 새 트랜잭션/`EntityManager.clear()` 후 수행. 결제/환불 TX-A→TX-C 사이는 트랜잭션이 분리되므로 자연히 새 컨텍스트.
- `available`은 `@Transient`/DTO 계산(`stock - reserved`). `orders.version`은 `@Version`을 붙이지 않는다(조건부 UPDATE가 증가시키는 감사 값, 읽기 전용 `long`).
- `Order` ↔ `OrderItem`: `@OneToMany` 컬렉션은 `@OrderBy("lineNo")` 유지, 목록 조회는 `@BatchSize` 또는 id 목록 일괄 조회로 N+1 회피. `open-in-view=false`이므로 DTO 변환은 트랜잭션 안에서.
- 쿠폰 `code` 중복: `saveAndFlush` 중 `DataIntegrityViolationException`의 원인 제약명이 `uk_coupons_code`이면 `coupon-code-duplicate`로 변환(사전 `existsByCode`는 UX용, 경쟁은 제약이 최종 방어).
- 시각: 저장 전 `Instant.truncatedTo(MICROS)`; `hibernate.jdbc.time_zone=UTC`.
- Flyway 위치 `classpath:db/migration`, `spring.flyway.enabled=true` (flyway-core + flyway-database-postgresql 이미 `build.gradle`에 존재, 신규 의존성 불필요).

## 5. 불변식 요약 (테스트/검증 기준)

- 모든 `products`: `0 ≤ reserved ≤ stock`.
- 모든 `coupons`: `0 ≤ used_count ≤ total_quantity`, 그리고 `used_count == COUNT(활성 주문: status IN (PENDING_PAYMENT, PAID, SHIPPED, DELIVERED) AND coupon_id = 해당 쿠폰)`.
- 모든 `products`: `reserved == Σ quantity (order_items of orders in (PENDING_PAYMENT, PAID))`.
- `payments.status = 'APPROVED'` 주문은 상태가 PAID/SHIPPED/DELIVERED, `REFUNDED` 결제는 주문 REFUNDED.
- 한 주문당 `payments` 최대 1행, 같은 (user, key)의 주문 최대 1건.
