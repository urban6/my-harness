# order-payment — DB 설계 (Phase 1)

PostgreSQL + Flyway. API 계약·응답 필드 ↔ 컬럼 대응표·제약 ↔ 상태코드 매핑표는 **`01_api_design.md`의 "정합 요약"을 단일 기준으로 참조**한다(여기서 복제하지 않는다). 결정 id(D-xx)도 01 §0 참조.

## 1. 개요

- Flyway 파일: `src/main/resources/db/migration/V1__init_schema.sql` (단일 마이그레이션. `.gitkeep`은 그대로 두어도 무방).
- Hibernate: `spring.jpa.hibernate.ddl-auto=validate`(스키마의 소유자는 Flyway). enum은 `@Enumerated(EnumType.STRING)` ↔ VARCHAR + CHECK. 시간은 `Instant` ↔ `TIMESTAMPTZ`, 금액은 `long` ↔ `BIGINT`, 수량은 `int` ↔ `INTEGER`. (`CHAR(n)`은 Hibernate validate와 충돌하므로 쓰지 않고 VARCHAR 사용.)
- PK는 `BIGINT GENERATED BY DEFAULT AS IDENTITY` ↔ `GenerationType.IDENTITY`.
- 테이블: `products`, `coupons`, `orders`, `order_items`, `payments`, `idempotency_keys` [REQ-16].

## 2. 테이블 개요

### 2.1 products [REQ-01, REQ-02, REQ-05]
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| name | VARCHAR(200) | NOT NULL, 공백 불가 |
| price | BIGINT | NOT NULL, ≥0 |
| stock | INTEGER | NOT NULL, ≥0 (결제 확정 후 실재고) |
| reserved | INTEGER | NOT NULL DEFAULT 0, ≥0, **≤ stock** |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

`available = stock - reserved`는 저장하지 않고 계산한다. `ck_products_reserved_le_stock`이 오버셀의 **최종 안전망**(앱 로직이 버그여도 DB가 거부).

### 2.2 coupons [REQ-03, REQ-04, REQ-06]
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| code | VARCHAR(50) | NOT NULL, **UNIQUE** (`uq_coupons_code`) |
| coupon_type | VARCHAR(10) | NOT NULL, IN ('FIXED','RATE') |
| discount_value | BIGINT | NOT NULL, >0, RATE면 1~100 |
| min_order_amount | BIGINT | NOT NULL DEFAULT 0, ≥0 |
| max_discount_amount | BIGINT | NULL, 값이 있으면 >0 |
| total_quantity | INTEGER | NOT NULL, ≥1 |
| used_count | INTEGER | NOT NULL DEFAULT 0, 0 ≤ used_count ≤ total_quantity |
| valid_from / valid_until | TIMESTAMPTZ | NOT NULL, valid_from < valid_until |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

컬럼명은 SQL 예약어 충돌을 피해 `discount_value`/`coupon_type`을 쓰고, JSON 필드명은 API대로 `value`/`type`(JPA `@Column(name=...)`로 매핑).

### 2.3 orders [REQ-05~REQ-14]
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK (커서 정렬키) |
| user_id | VARCHAR(64) | NOT NULL |
| status | VARCHAR(20) | NOT NULL, 8개 enum CHECK |
| coupon_code | VARCHAR(50) | NULL, FK → coupons(code) |
| subtotal | BIGINT | NOT NULL, ≥0 |
| discount | BIGINT | NOT NULL DEFAULT 0, 0 ≤ discount ≤ subtotal |
| total_price | BIGINT | NOT NULL, = subtotal - discount |
| created_at | TIMESTAMPTZ | NOT NULL |
| expires_at | TIMESTAMPTZ | NOT NULL, > created_at (생성 시 TTL 스냅샷) |
| paid_at | TIMESTAMPTZ | NULL (상태와 정합 CHECK) |
| updated_at | TIMESTAMPTZ | NOT NULL |

`created_at`/`expires_at`은 애플리케이션 `Clock` 값을 넣는다(DB `now()` 기본값에 의존하지 않음 — TTL 스냅샷과 같은 기준 시각 사용).

### 2.4 order_items [REQ-05]
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK (응답 items 순서 = id 오름차순 = 요청 순서) |
| order_id | BIGINT | NOT NULL FK → orders(id) |
| product_id | BIGINT | NOT NULL FK → products(id) |
| quantity | INTEGER | NOT NULL, >0 |
| unit_price | BIGINT | NOT NULL, ≥0 (주문 시점 단가 스냅샷) |
| | | UNIQUE (order_id, product_id) |

### 2.5 payments [REQ-10, REQ-11, REQ-12]
주문당 결제 시도는 최대 1건(승인되면 PAID, 거절되면 PAYMENT_FAILED로 재결제 불가). PG 장애는 롤백되어 행이 남지 않는다.
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| order_id | BIGINT | NOT NULL, **UNIQUE** (`uq_payments_order`), FK → orders(id) |
| payment_id | VARCHAR(100) | NOT NULL (PG 발급 id). **UNIQUE 걸지 않음**: PG 스텁이 동일 id를 반복 반환해도 500이 나지 않게 하기 위함 |
| status | VARCHAR(20) | NOT NULL, IN ('APPROVED','DECLINED','REFUNDED') |
| amount | BIGINT | NOT NULL, ≥0 (PG에 보낸 totalPrice) |
| created_at | TIMESTAMPTZ | NOT NULL |
| refunded_at | TIMESTAMPTZ | NULL |

`cardToken`은 저장하지 않는다.

### 2.6 idempotency_keys [REQ-07, REQ-11, REQ-17]
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT identity | PK |
| operation | VARCHAR(20) | NOT NULL, IN ('CREATE_ORDER','PAY') |
| scope_key | VARCHAR(64) | NOT NULL — CREATE_ORDER는 user_id, PAY는 `'*'` |
| idem_key | VARCHAR(128) | NOT NULL |
| request_hash | VARCHAR(64) | NOT NULL — SHA-256 hex(소문자) |
| order_id | BIGINT | NULL, FK → orders(id). 선점 직후(같은 트랜잭션 안)에만 null, 커밋 시점엔 항상 채워짐 |
| outcome | VARCHAR(20) | NULL — 'CREATED' / 'APPROVED' / 'DECLINED' (커밋 시점엔 항상 채워짐) |
| created_at | TIMESTAMPTZ | NOT NULL |
| | | UNIQUE (operation, scope_key, idem_key) = `uq_idempotency_scope` |

## 3. 동시성 전략 [REQ-05, REQ-06, REQ-17]

공통 전제: READ COMMITTED(기본), 모든 변경은 서비스 트랜잭션 하나 안에서 수행. 구현 팁: 수정 쿼리는 `@Modifying(flushAutomatically = true, clearAutomatically = true)`(또는 `JdbcClient`/네이티브)로 쓰고 영향 행 수를 반드시 검사한다.

### 3.1 재고 — 원자적 조건부 UPDATE (락 읽기 후 쓰기 금지)
```sql
-- 예약 (주문 생성)
UPDATE products SET reserved = reserved + :q WHERE id = :id AND stock - reserved >= :q;      -- 0행 → 409 insufficient-stock
-- 예약 해제 (취소/만료/거절)
UPDATE products SET reserved = reserved - :q WHERE id = :id AND reserved >= :q;               -- 0행 → 불변식 위반(500)
-- 결제 확정
UPDATE products SET stock = stock - :q, reserved = reserved - :q WHERE id = :id AND reserved >= :q AND stock >= :q;
-- 환불 복구
UPDATE products SET stock = stock + :q WHERE id = :id;
```
UPDATE가 행 락을 잡으므로 동시 주문은 해당 상품 행에서 직렬화되고, 조건식이 최신 커밋 값으로 재평가되어(READ COMMITTED의 EvalPlanQual) 초과 예약이 불가능하다. 추가로 `ck_products_reserved_le_stock`이 DB 레벨 안전망. 낙관적 락(@Version)과 재시도 루프는 쓰지 않는다(재시도 폭주·구현 복잡도 대비 이득 없음).

### 3.2 쿠폰 — 원자적 조건부 UPDATE
```sql
UPDATE coupons SET used_count = used_count + 1
 WHERE code = :code AND used_count < total_quantity AND valid_from <= :now AND valid_until > :now;   -- 0행 → 409 coupon-not-applicable
UPDATE coupons SET used_count = used_count - 1 WHERE code = :code AND used_count > 0;                 -- 복구
```
`ck_coupons_used_le_total`이 안전망. `min_order_amount`는 불변 값이라 사전 검사(조회)로 충분.

### 3.3 주문 상태 — 비관적 행 락 (`SELECT ... FOR UPDATE`)
- 결제·취소·출고·배송·만료의 모든 전이는 `orders` 행을 `PESSIMISTIC_WRITE`(`@Lock`)로 잠그고 **현재 상태를 재확인**한 뒤 수행. (락 조회는 `orders` 단독 SELECT; `order_items`는 별도 쿼리 — outer join과 FOR UPDATE 조합 회피.)
- PG 호출은 이 락을 잡은 트랜잭션 안에서(D-09). 따라서 결제 vs 취소, 결제 vs 만료, 환불 vs 출고 경합은 직렬화되어 최종 상태가 하나로 결정된다.
- 스윕 만료는 `FOR UPDATE SKIP LOCKED`(Hibernate 락 힌트 `jakarta.persistence.lock.timeout=-2`)로 진행 중인 결제를 건드리지 않는다.
- `@Version`은 사용하지 않는다(비관적 락으로 충분).

### 3.4 락 획득 순서 (교착 방지)
`orders`(기존 행) → `products`(id 오름차순) → `coupons`. 주문 생성은 새 행을 만들 뿐 기존 `orders` 락이 없고 products(오름차순) → coupons 순서이므로 모든 경로가 전순서를 따른다. 트랜잭션 내에서 이 순서를 어기는 코드를 쓰지 않는다.

### 3.5 동일 Idempotency-Key 동시 요청 (단일 주문 보장)
1. `INSERT INTO idempotency_keys (...) VALUES (...) ON CONFLICT (operation, scope_key, idem_key) DO NOTHING` — 영향 행 1이면 선점 성공.
2. 동시에 같은 키가 들어오면 PostgreSQL은 선행 트랜잭션의 커밋/롤백까지 두 번째 INSERT를 **대기**시킨다.
   - 선행 커밋 → 후행은 0행 → 기존 행 조회(READ COMMITTED에서 새 문장은 커밋된 행을 본다) → 해시 비교 후 리플레이/409.
   - 선행 롤백(재고 부족 등) → 후행의 INSERT가 성공하고 새로 처리.
3. 결제는 추가로 `orders` 행 락이 같은 주문의 동시 요청을 직렬화하고, 락 획득 직후 키 조회로 리플레이한다.
이 구조로 같은 키 N개 동시 요청에서 주문 1건, 예약 1회만 발생한다.

### 3.6 트랜잭션 경계 주의
- 만료 전이는 "예외를 던지는 요청(예: 만료 주문 pay → 409)"과 같은 호출에서 일어나므로, 전이를 **커밋한 뒤** 예외를 던지거나(`@Transactional(noRollbackFor=...)`/`TransactionTemplate`) 별도 트랜잭션(`REQUIRES_NEW`, 다른 빈)으로 수행해야 한다. 그렇지 않으면 전이가 롤백된다.
- 스케줄러는 주문별 개별 트랜잭션(자기 호출 프록시 우회 위해 별도 빈 사용).
- 커넥션 풀: Hikari 기본(10). 결제/환불 요청은 PG 응답까지 커넥션을 점유하므로 동시 결제 처리량은 풀 크기가 상한.

## 4. 멱등성 키 저장 구조 요약 [REQ-07, REQ-11]
- 위 §2.6 한 테이블에 두 연산(주문 생성/결제)을 `operation`으로 구분. 범위: 생성은 사용자별, 결제는 전역(D-12).
- 저장 시점: 주문 생성은 같은 트랜잭션 내 선점 → 주문 INSERT 후 `order_id`/`outcome=CREATED` 갱신. 결제는 PG 호출 전 선점 → 응답 후 `outcome` 갱신. 트랜잭션 롤백 시 키도 함께 사라져 재시도가 가능(D-13).
- 리플레이 판정은 `request_hash` 비교. 응답 본문은 저장하지 않고 `order_id`로 주문을 재조회해 구성(스냅샷 불일치 위험 없음).

## 5. 금액 타입 [REQ-16]
- 모든 금액(`price`, `unit_price`, `subtotal`, `discount`, `total_price`, `min_order_amount`, `max_discount_amount`, `discount_value`(FIXED), `payments.amount`)은 **BIGINT (정수 원)**, Java `long`. 부동소수점·`NUMERIC` 소수 없음.
- 상한(API 검증): price ≤ 1e9, quantity ≤ 1e5, items ≤ 50 → subtotal ≤ 5e15, RATE 중간값 `subtotal*100` ≤ 5e17 < 2^63 (long 오버플로 없음, `Math.multiplyExact` 권장).
- RATE 할인 = `subtotal * value / 100` 정수 나눗셈(내림).

## 6. 인덱스 [REQ-09, REQ-13]
| 인덱스 | 대상 | 용도 |
|---|---|---|
| `idx_orders_user_id_id` | orders (user_id, id DESC) | userId 필터 + 커서 목록 |
| `idx_orders_status_id` | orders (status, id DESC) | status 필터 + 커서 목록 |
| `idx_orders_pending_expiry` | orders (expires_at) **WHERE status='PENDING_PAYMENT'** (부분) | 만료 스윕 |
| `uq_order_items_order_product` | order_items (order_id, product_id) | 항목 조회(선두 order_id) + 중복 방지 |
| `uq_coupons_code`, `uq_payments_order`, `uq_idempotency_scope` | 유니크 | 위 참조 |
필터 없는 목록은 PK(id DESC) 스캔. `products.id` FK는 삭제 기능이 없어 `order_items.product_id` 별도 인덱스를 두지 않는다.

## 7. Flyway 마이그레이션 [REQ-16]

파일: `src/main/resources/db/migration/V1__init_schema.sql`

```sql
-- V1__init_schema.sql : order-payment 초기 스키마

CREATE TABLE products (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(200) NOT NULL,
    price       BIGINT       NOT NULL,
    stock       INTEGER      NOT NULL,
    reserved    INTEGER      NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT ck_products_name_not_blank   CHECK (length(btrim(name)) > 0),
    CONSTRAINT ck_products_price            CHECK (price >= 0),
    CONSTRAINT ck_products_stock            CHECK (stock >= 0),
    CONSTRAINT ck_products_reserved         CHECK (reserved >= 0),
    CONSTRAINT ck_products_reserved_le_stock CHECK (reserved <= stock)
);

CREATE TABLE coupons (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code                VARCHAR(50)  NOT NULL,
    coupon_type         VARCHAR(10)  NOT NULL,
    discount_value      BIGINT       NOT NULL,
    min_order_amount    BIGINT       NOT NULL DEFAULT 0,
    max_discount_amount BIGINT,
    total_quantity      INTEGER      NOT NULL,
    used_count          INTEGER      NOT NULL DEFAULT 0,
    valid_from          TIMESTAMPTZ  NOT NULL,
    valid_until         TIMESTAMPTZ  NOT NULL,
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT uq_coupons_code            UNIQUE (code),
    CONSTRAINT ck_coupons_type            CHECK (coupon_type IN ('FIXED', 'RATE')),
    CONSTRAINT ck_coupons_value           CHECK (discount_value > 0),
    CONSTRAINT ck_coupons_rate_range      CHECK (coupon_type <> 'RATE' OR discount_value BETWEEN 1 AND 100),
    CONSTRAINT ck_coupons_min_order       CHECK (min_order_amount >= 0),
    CONSTRAINT ck_coupons_max_discount    CHECK (max_discount_amount IS NULL OR max_discount_amount > 0),
    CONSTRAINT ck_coupons_total_quantity  CHECK (total_quantity >= 1),
    CONSTRAINT ck_coupons_used_le_total   CHECK (used_count >= 0 AND used_count <= total_quantity),
    CONSTRAINT ck_coupons_valid_period    CHECK (valid_from < valid_until)
);

CREATE TABLE orders (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id      VARCHAR(64)  NOT NULL,
    status       VARCHAR(20)  NOT NULL,
    coupon_code  VARCHAR(50),
    subtotal     BIGINT       NOT NULL,
    discount     BIGINT       NOT NULL DEFAULT 0,
    total_price  BIGINT       NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL,
    expires_at   TIMESTAMPTZ  NOT NULL,
    paid_at      TIMESTAMPTZ,
    updated_at   TIMESTAMPTZ  NOT NULL,
    CONSTRAINT fk_orders_coupon        FOREIGN KEY (coupon_code) REFERENCES coupons (code),
    CONSTRAINT ck_orders_status        CHECK (status IN ('PENDING_PAYMENT', 'PAID', 'PAYMENT_FAILED', 'EXPIRED',
                                                         'CANCELLED', 'REFUNDED', 'SHIPPED', 'DELIVERED')),
    CONSTRAINT ck_orders_amounts       CHECK (subtotal >= 0 AND discount >= 0 AND discount <= subtotal
                                              AND total_price = subtotal - discount),
    CONSTRAINT ck_orders_expiry        CHECK (expires_at > created_at),
    CONSTRAINT ck_orders_paid_at       CHECK (
        (status IN ('PENDING_PAYMENT', 'PAYMENT_FAILED', 'EXPIRED', 'CANCELLED') AND paid_at IS NULL)
        OR (status IN ('PAID', 'SHIPPED', 'DELIVERED', 'REFUNDED') AND paid_at IS NOT NULL))
);

CREATE INDEX idx_orders_user_id_id ON orders (user_id, id DESC);
CREATE INDEX idx_orders_status_id  ON orders (status, id DESC);
CREATE INDEX idx_orders_pending_expiry ON orders (expires_at) WHERE status = 'PENDING_PAYMENT';

CREATE TABLE order_items (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id    BIGINT  NOT NULL,
    product_id  BIGINT  NOT NULL,
    quantity    INTEGER NOT NULL,
    unit_price  BIGINT  NOT NULL,
    CONSTRAINT fk_order_items_order    FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product  FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT uq_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_quantity CHECK (quantity > 0),
    CONSTRAINT ck_order_items_price    CHECK (unit_price >= 0)
);

CREATE TABLE payments (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id     BIGINT       NOT NULL,
    payment_id   VARCHAR(100) NOT NULL,   -- PG가 발급한 결제 id (UNIQUE 아님: PG 스텁의 id 재사용 허용)
    status       VARCHAR(20)  NOT NULL,
    amount       BIGINT       NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL,
    refunded_at  TIMESTAMPTZ,
    CONSTRAINT fk_payments_order    FOREIGN KEY (order_id) REFERENCES orders (id),
    CONSTRAINT uq_payments_order    UNIQUE (order_id),
    CONSTRAINT ck_payments_status   CHECK (status IN ('APPROVED', 'DECLINED', 'REFUNDED')),
    CONSTRAINT ck_payments_amount   CHECK (amount >= 0),
    CONSTRAINT ck_payments_refunded CHECK ((status = 'REFUNDED') = (refunded_at IS NOT NULL))
);

CREATE TABLE idempotency_keys (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    operation     VARCHAR(20)  NOT NULL,
    scope_key     VARCHAR(64)  NOT NULL,   -- CREATE_ORDER: user_id, PAY: '*'
    idem_key      VARCHAR(128) NOT NULL,
    request_hash  VARCHAR(64)  NOT NULL,   -- SHA-256 hex
    order_id      BIGINT,
    outcome       VARCHAR(20),
    created_at    TIMESTAMPTZ  NOT NULL,
    CONSTRAINT uq_idempotency_scope  UNIQUE (operation, scope_key, idem_key),
    CONSTRAINT fk_idempotency_order  FOREIGN KEY (order_id) REFERENCES orders (id),
    CONSTRAINT ck_idempotency_operation CHECK (operation IN ('CREATE_ORDER', 'PAY')),
    CONSTRAINT ck_idempotency_outcome   CHECK (outcome IS NULL OR outcome IN ('CREATED', 'APPROVED', 'DECLINED'))
);
```

```yaml
  mvc:
    problemdetails:
      enabled: true
  jackson:
    deserialization:
      accept-float-as-int: false      # price 10.5 -> long 절삭 방지

server:
  port: ${SERVER_PORT:8080}

order:
  payment-ttl: ${ORDER_PAYMENT_TTL:PT15M}     # java.time.Duration, 양수
  expiry-sweep-enabled: true
  expiry-sweep-interval: PT10S

payment:
  gateway:
    url: ${PAYMENT_GATEWAY_URL:http://localhost:9090}
    connect-timeout: PT2S
    read-timeout: PT5S
```
`@ConfigurationProperties`(Duration 바인딩 `PT15M`, `@Validated`+양수 검증)로 `order.*`·`payment.gateway.*`를 주입한다. `@EnableScheduling`은 `order.expiry-sweep-enabled=true`일 때만 스케줄러 빈을 등록(`@ConditionalOnProperty`).
