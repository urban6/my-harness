# PRD — 3차 실험: 짧은 요청에서 하네스가 빠진 요구를 챙기는가

> 본 실행·채점 완료(2026-10-10) — 결과: [`REPORT.md`](REPORT.md)
> 상태: 확정 · 2026-10-10 · 2차(상세 명세, Opus): [`../exp2/REPORT.md`](../exp2/REPORT.md) · 4차(상세 명세, Sonnet 파일럿): [`../exp4/PRD.md`](../exp4/PRD.md)

## 1. 목적

1·2·4차는 상세 명세에서 모든 군이 만점이었다. 명세가 경계값·오류 순서·동시성 요구까지 대신 정해 줬기 때문으로 본다. 실무 요청은 대부분 짧다.

3차는 **같은 기능을 짧은 명세로 주고**, 명세에 없는 상식적 요구를 각 방식이 스스로 챙기는지 점수화한다. 점수에 더해, C가 놓친 항목이 **하네스의 어느 단계에서 빠졌는지** 추적해 하네스 개선 근거로 쓴다(§6).

## 4. 채점 (100점)

짧은 명세는 상태코드·`code` 값을 정하지 않았으므로 2차 인수 테스트를 그대로 쓸 수 없다. 새 숨긴 테스트를 두 층으로 만든다.

| 항목 | 배점 | 측정 |
|---|---|---|
| 계약 | 20 | 정상 경로: 생성·조회·결제 승인·취소·환불·배송·목록이 명세 필드대로 동작 |
| 견고성 | 50 | §5 S1~S25. **범주별 균등**(7범주 각 50/7), 범주 안은 항목 균등 |
| 테스트 품질 | 20 | 자체 테스트가 검증하는 S 항목 수(n/25) × 20 (블라인드 매핑, opus 3회 다수결) |
| 완료성 | 10 | `assemble` 5 + 자체 `test` 통과 5 |

- 판정 기준: **거절** = 4xx(5xx 아님), **불변** = 관련 상품 `stock`/`reserved`, 쿠폰 `usedCount`, 주문 `status`가 요청 전과 같음. 의미에 맞는 상태코드(409 vs 400)인지는 참고 열에만 기록.
- PG 장애(S17)는 의도된 503을 정답으로 인정, 그 밖의 5xx는 실패.
- 분기 커버리지는 2차에서 코드 규모에 좌우돼 변별력이 없었으므로 제외.
- 참고 열(점수 미반영): 비용, 시간, 자체 테스트 수, 상태코드 적합도, C의 FIX·REDO·BLOCKED.

## 5. 견고성 테스트 목록

- 거절 검사(S1·S3·S4·S5·S25)는 같은 엔드포인트의 정상 요청이 먼저 통과해야 센다 — 엔드포인트가 없어 나는 404를 거절로 세지 않는다.

### 입력 검증
- S1. 음수·0 가격, 음수 재고, 빈 이름 → 거절
- S2. 수량 0·음수, 빈 `items` → 거절 + 불변. 같은 상품 중복 → 거절 또는 정확히 합산
- S3. RATE 쿠폰 `value` > 100, `validFrom ≥ validUntil` → 거절
- S4. 깨진 JSON, 타입 불일치(`price: "abc"`) → 거절, Problem Details
- S5. 금액 오버플로: 가격 10,000,000 × 수량 1,000 × 상품 3개 → 5xx 아님, 금액이 음수·잘림 아님 (상한을 두고 거절해도 인정)

### 재고·쿠폰 정합성
- S6. `available` 초과 주문 → 거절 + 불변 (부분 예약 없음, 여러 상품 중 하나만 부족해도)
- S7. 할인 > 소계 → `totalPrice` 음수 아님
- S8. 기간 밖·최소 금액 미달·소진(결제 완료로 소진)·없는 쿠폰 → 거절 + 불변
- S9. 같은 사용자의 같은 쿠폰 중복 사용 → 두 번째 거절 (첫 주문 결제 완료 기준)
- S10. 주문이 취소·만료·결제 실패·환불되면 예약·쿠폰 사용 복원

### 상태 전이
- S11. 허용되지 않은 전이(`CANCELLED` 결제, `PENDING_PAYMENT` 배송, `DELIVERED` 취소 등) → 거절 + 불변
- S12. 만료 시각이 지난 주문 결제 → 거절, PG 호출 없음
- S13. TTL(`PT3S`) 경과 후 10초 안에 `EXPIRED` + 복원 반영 (주문을 조회하지 않아도 상품·쿠폰에 반영)

### 멱등성
- S14. 같은 키·같은 요청 재시도 → 주문 1건만 생성, 같은 응답
- S15. 같은 키·다른 본문 → 거절, 새 처리 없음
- S16. 같은 결제 재시도 → PG 결제 요청 1회

### 외부 PG 장애
- S17. PG 5xx·연결 끊김·5초 지연 → 500 아님(502·503·504 인정) + 상태 일관: `PENDING_PAYMENT`(예약 유지, 재시도로 결제 가능) 또는 `PAYMENT_FAILED`(예약 해제). 지연은 기다려 `PAID`도 인정
- S18. PG 거절 → `PAYMENT_FAILED` + 예약·쿠폰 복원, 또는 `PENDING_PAYMENT` 유지(다른 카드로 재시도) + 예약 유지. PG 장애 응답(502~504)으로 알리면 실패
- S19. 환불 중 PG 장애 → 500 아님 + 주문 `PAID` 유지, 재고 불변

### 동시성 (각 5회 반복)
- S20. `available` 10에 동시 주문 20건 → 성공 정확히 10, `reserved` 10
- S21. 수량 5 쿠폰에 15명 동시 주문·결제(사람마다 다른 상품) → 쿠폰 적용 결제 정확히 5, `usedCount` 5
- S22. 같은 주문 동시 결제 5건(키 다름) → 실제 청구 1회, `PAID`, 재고 1회 차감
- S23. `[P,Q]`·`[Q,P]` 교차 동시 주문 10건(재고 충분) → 5xx·교착 없음, 전부 성공, `reserved` 정확

### 목록
- S24. 커서 페이지 순회 중 새 주문 생성 → 첫 페이지 시점 주문이 중복·누락 없음
- S25. 잘못된 `size`(0·음수·문자)·`cursor`·`status` → 거절

## 6. 단계별 누락 추적 (하네스 개선 근거)

C run에서 실패한 S 항목마다 산출물을 거슬러 올라가 빠진 위치를 하나로 분류한다.

| 빠진 위치 | 판정 근거 | 개선 대상 |
|---|---|---|
| 설계 | 설계 문서(`01_api_design.md`·`02_db_design.md`)에 해당 결정이 없음 | `backend-designer` 체크리스트·`feature-pm` 요구 분해 |
| 구현 | 설계엔 있는데 코드에 없거나 다름 | `boundary-verifier` 점검 항목 |
| 테스트 | 코드엔 있는데 자체 테스트가 검증하지 않음 | `test-writer` 지시 |

- 통과한 항목도 "설계에 명시했는가"를 기록한다 — 설계에 없는데 통과한 항목은 우연(프레임워크 기본값 등)일 수 있다.
- A와 비교해 항목을 세 갈래로 나눈다: **둘 다 챙김**(모델 기본기, 하네스 기여 아님) / **C만 챙김**(하네스 기여) / **둘 다 놓침**(하네스 보강 후보).
- 분류는 사람이 아니라 판정 에이전트(opus, 블라인드)가 하고, 근거 파일·줄을 남긴다.

## 9. 리스크

| 리스크 | 대응 |
|---|---|
| 짧은 명세에서도 천장 | 그 자체가 결과("Sonnet은 이 범위를 명세 없이도 챙김"). 하네스 비용 대비 효용 판단 근거 |
| 견고성 테스트가 명세 밖 "정답"을 강요 | 상태코드를 특정하지 않고 거절·불변만 판정, 각 항목에 상식 근거를 단다 |
| n=2로 편차 판단 불가 | 점수 우열은 주장하지 않고, 항목 단위 누락 패턴(§6)을 주 결과로 삼는다 |
| C가 상한 안에 못 끝남 | 시간·비용 초과 시 그 시점 결과로 채점, 종료 상태 기록 |
