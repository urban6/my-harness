## 6. 하네스 개선 근거

1. **짧은 요청에서 C가 더 챙긴 항목은 없다.** 동시성·멱등성·만료·PG 장애처럼 "어려운" 항목은 A도 전부 챙겼다. 이 범위에서 요구 분해·설계 단계의 가치는 "더 많이 챙김"이 아니다.
2. **두 방식 모두 명세 빈칸을 임의로 채웠고, C는 그 결정을 문서로 남겼다.** 헤드리스라 어느 군도 사람에게 확인받을 수 없었고, A도 S1·S9를 똑같이 놓쳤다(A의 원인은 추적하지 않음). C의 결정 일부는 작성자의 기대와 달랐다(0원 허용, 쿠폰 무제한, 환불 시 쿠폰 미복원, 새 키 재시도 거절). 결정이 문서로 남는 점은 사람이 설계 단계에서 검토할 수 있다는 뜻이라 C 쪽의 개선 여지가 크다.
   → **후보: `feature-pm`이 설계 직후 "명세에 없어 정한 결정" 목록을 사람에게 보여 주고 확인받는 단계.** 실무는 대화형이라 비용이 거의 없다.
3. **`backend-designer` 점검 항목 후보**: 일시 장애 뒤 다른 키·다른 카드로 재시도 가능한가, 사용자당 제한이 필요한 자원(쿠폰 등), 0·경계 금액, 환불·취소 시 복원 범위의 일관성.
4. **`test-writer`는 효과가 있다** — 자체 테스트가 검증한 항목 +3개(테스트 품질 +2.4점). 다만 테스트 수 6.4배에 비해 커버 증가는 작다.
5. **대기 전용 designer 스폰 제거 후보** — REDO가 없을 때도 designer를 미리 띄워 둔다. 필요할 때 다시 스폰하면 비용을 줄일 수 있다.

## 7. 해석상 주의

- **n=2**: 총점 차이(0.3점)는 run 간 편차(A 2.3점)보다 작다. 주 결과는 점수가 아니라 항목별 누락 패턴이다. 통계 검정은 하지 않았다.
- **점수 구조**: 견고성은 7범주 균등 가중이라 S17 한 항목이 2.38점, S1이 1.43점이다. 군 차이 2.7점은 항목 1~2개에서 나온다.
- **명세 밖 기대**: S1·S9·S10은 2차 상세 명세에서 온 규칙이다(위 재계산 참고). 같은 이유로 S25(size 0 거절)도 논쟁 여지가 있다(전 run 통과라 결과에는 영향 없음).
- **실행 환경**: 전역 플러그인(superpowers 등)이 모든 군의 세션에 로드됐다(시작 훅이 지시문 주입). 호출 기록은 없지만 A도 "하네스가 전혀 없는" 상태는 아니었다.
- **effort medium 보충**은 A-1·A-2와 번갈아 돌리지 않고 나중에 실행했다.
- **논쟁적 판정**: S9(쿠폰 1인 1회)·S10(환불 시 쿠폰 복원)은 명세에 없고, C-2는 쿠폰 미복원에 근거(악용 방지)까지 적었다. 이 둘을 빼면 C-2의 견고성은 A와 비슷해진다. S1(0원 거절)도 합리적 반론이 있다.
- **동결 후 테스트 수정 1건**: K5·S17·S22가 "결제 시 재고 차감"을 강요하던 편향을 라운드 1 뒤 수정(가용 재고로 판정), 전 run 수정판으로 채점. 수정 전 결과는 `results/*-v1.json`.
- **설계 판정은 설계 문서만 본다** — 문서와 코드가 다를 때(S17) 분류가 실제 원인과 어긋날 수 있다.
