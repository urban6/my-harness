# PRD — 5차 실험: 단일 세션이 실패하는 과제에서 에이전트 팀이 이득인가

> 상태: **마감** · 2026-10-11 — 0-2 걸러 내기에서 채택 과제 없음(Sonnet·Haiku B 모두 만점), 본 실행 없이 종료. 결과: [`REPORT.md`](REPORT.md) · ✋0 결정: §10 그대로 · 0-1 준비 결과: §11 · 이전 결과 요약: [`../README.md`](../README.md) · 3차(짧은 명세): [`../exp3/REPORT.md`](../exp3/REPORT.md)

## 1. 목적

1~4차는 모든 과제에서 단일 세션(A·B)이 명세 요구를 전부 맞혔다. 그래서 에이전트 팀(C)이 **더 잘할 여지가 처음부터 없었고**, 결론은 "이 조건에서는 비용만 더 든다"에 그쳤다.

5차는 **단일 세션이 실제로 실패하는 과제를 먼저 골라 낸 뒤** 같은 질문을 다시 던진다 — 그런 과제에서 `feature-pm` 에이전트 팀이 일반·스킬 대비 비용만큼의 차이를 내는가.

설계 원칙은 **짧게, 그러나 결론이 흔들리지 않게**다.

| 목표 | 방법 |
|---|---|
| 확실하게 | 단일 세션이 실패하는 과제만 채택, 숨긴 테스트·가설·분석을 **실행 전에 동결**, 군당 5회 + 정확 순열검정, 설정 격리 |
| 짧게 | 기존 2차 자산을 재사용하는 단일 단계 과제만 먼저 준비, 라운드 안 3군 병렬 실행, 3라운드 뒤 무익 중단 규칙 |

| 이전 실험의 약점 | 5차에서 바꾸는 것 |
|---|---|
| A가 명세 요구를 전부 맞혀 C가 앞설 여지가 없음 | 0단계에서 B를 먼저 돌려 **명세 내 통과율 40~85%인 과제만** 채택 (§3) |
| 판정 기준이 결과를 본 뒤 두 번 바뀜 | 숨긴 테스트를 명세 내·명세 해석으로 **실행 전에 나누고 동결**, 사후 수정 규칙을 미리 정함 (§5) |
| 전역 플러그인이 군마다·run마다 다르게 로드 | run마다 격리된 설정 디렉터리, init 이벤트로 플러그인·스킬·에이전트 목록 검사 (§4) |
| 하네스가 live 저장소 심링크 | 특정 커밋의 사본으로 고정 |
| 1·2차는 군마다 모델이 섞임 | 전 군·전 워커 Sonnet 고정 (3차 방식) |
| 군당 2~3회, 검정 없음 | 군당 5회, 가설·주 지표·검정을 미리 정함 (§6) |

## 2. 비교군 (1~3차와 동일)

| 군 | 정의 | 군별 실행 옵션 | 설정 디렉터리에 넣는 자산 |
|---|---|---|---|
| A 일반 | 하네스 없음, 단일 세션 | `--disable-slash-commands --disallowedTools Agent Workflow` | 없음 |
| B 스킬 | `spring-boot` 스킬만, 단일 세션 | `--disallowedTools Agent Workflow --append-system-prompt "Spring Boot 코드는 spring-boot 스킬을 따른다."` | `skills/spring-boot` |
| C 에이전트 팀 | `feature-pm` + 워커 4종 + 스킬 | `--agent feature-pm` | `agents/`의 `feature-pm`·`backend-designer`·`backend-impl`·`boundary-verifier`·`test-writer` + `skills/spring-boot` |

- 모델: 전 군 `claude-sonnet-5-5`, effort high. C 워커도 `ANTHROPIC_DEFAULT_OPUS_MODEL=claude-sonnet-5-5`로 고정하고, 세션 로그에 Sonnet 외 모델이 있으면 폐기한다.
- 하네스 자산은 실행 시점 커밋의 **사본**을 쓴다. 커밋 해시를 run 메타에 기록한다.
- 프롬프트는 전 군 동일 — 군 차이는 실행 옵션과 설정 디렉터리로만 만든다.

## 3. 0단계 — 과제 걸러 내기 파일럿

후보 과제를 B로 1회씩 돌려 채점하고, 아래 기준을 만족하는 과제 하나를 본 실험에 쓴다. B로 거르는 이유: 1~3차에서 B ≥ A였으므로 B에 여지가 있으면 A에도 있다.

| 채택 기준 | 이유 |
|---|---|
| B의 명세 내 통과율 40~85% | 85% 초과는 다시 천장, 40% 미만은 바닥이라 C가 차이를 내도 노이즈에 묻힘 |
| 실패한 요구사항 3개 이상 | 우연한 한 항목으로 점수가 갈리지 않게 |
| B run 비용 $15 이하 · 60분 이하 | 본 실행 15 run이 시간·예산 안에 들어오게 |

- 둘 다 통과하면 **B 통과율이 더 낮은 과제**(여지가 큰 쪽)를 고른다.
- 채택 과제로 C를 1회 돌려 헤드리스에서 끝까지 완료되는지, 시간이 상한 안인지 확인한다(점수는 본 실험에 넣지 않음).
- 둘 다 기준을 못 넘으면 "Sonnet 단일 세션은 이 범위까지 명세 요구를 맞힌다"를 결과로 기록하고, 대기 후보(T1·T2) 준비 여부를 ✋1에서 정한다.

### 우선 후보 (빠르게 준비 가능)

둘 다 **2차 정답 구현을 시작 코드로 주는 단일 단계 과제**다. 시작 코드·회귀 테스트(2차 숨긴 테스트 92케이스)·PG 스텁을 그대로 재사용하고, 새 기능 테스트와 정답 구현 확장만 만든다. 스택은 1~4차와 같은 Spring Boot 3 + JPA + PostgreSQL + Flyway + Testcontainers.

#### T3. 기존 코드에 기능 추가 — 부분 환불 + 포인트 혼합 결제

- 시작점: 2차 정답 구현(`../exp2/acceptance/reference/`), 기존 자체 테스트 포함. 2차 `feature.md`도 기존 명세로 함께 준다.
- 요청: 사용자 포인트 적립·조회, 포인트·카드 혼합 결제(포인트 먼저 차감), 항목 단위 부분 환불(환불 시 카드 → 포인트 순 복원, 쿠폰 할인은 금액 비율로 안분).
- 단일 세션이 실패할 지점: 결제·환불·만료·멱등성·동시성 경로를 함께 바꿔야 해서 일부 경로 누락, 기존 동작 회귀, 안분 계산 오차.
- C의 강점이 쓰이는 지점: 설계 단계에서 영향 경로를 먼저 정리, `boundary-verifier`의 경계면 재검증.

#### T4. 교차 관심사 변경 — 멀티테넌시 도입

- 시작점: T3와 같은 2차 정답 구현.
- 요청: `X-Tenant-Id` 헤더로 테넌트를 나누고 상품·쿠폰·주문을 전부 격리. 쿠폰 코드는 테넌트 안에서만 유일, 목록·커서·멱등 키·재고 경합도 테넌트별.
- 단일 세션이 실패할 지점: 조회·잠금·유일 제약·멱등 저장소 중 한 곳만 빠져도 테넌트 간 노출. 숨긴 테스트는 엔드포인트마다 교차 테넌트 접근을 검사한다.
- C의 강점이 쓰이는 지점: 요구 분해로 영향 범위를 빠짐없이 나열, 경계면 검증.

### 대기 후보 (T3·T4가 둘 다 천장일 때만)

| 과제 | 내용 | 미룬 이유 |
|---|---|---|
| T1 순차 누적 | 기능 4단계를 단계마다 새 세션으로 쌓고, 마지막에 기존 규칙 변경 | C run 하나가 4단계 × 전체 파이프라인이라 run당 2~4시간 — 짧게 끝내는 목표와 충돌 |
| T2 대형 단일 요청 | 9개 영역, 규칙 약 120개를 한 번에 | 숨긴 테스트·정답 구현을 새로 만들어야 해 준비가 가장 오래 걸림 |

## 4. 실행 조건

| 항목 | 값 |
|---|---|
| 반복 | 군당 5회, 총 15 run (3라운드 뒤 무익 중단 가능, §6.3) |
| 실행 방식 | **라운드 안에서 A·B·C를 동시에 실행**, 라운드끼리는 순차. 채점은 부하가 섞이지 않게 라운드 실행이 끝난 뒤 하나씩. 병렬이 안 되면 라운드마다 군 순서를 바꿔 순차 실행(`A→B→C` / `B→C→A` / `C→A→B` 반복) |
| 상한 | run당 $40 · 180분 |
| 사람 개입 | 없음 (헤드리스) |
| 실행 위치 | `playground/exp5/runs/{군}-{회차}/` — run마다 독립 git, 상위 `CLAUDE.md`·`acceptance/`·이전 실험 읽기 차단 |

### 라운드 병렬 실행

- 같은 라운드의 세 run이 같은 시간대·같은 부하를 받으므로 군 간 조건은 오히려 고르다. 시간 지표는 "병렬 부하 아래 벽시계"로 표기한다.
- 충돌 방지: run마다 다른 `SERVER_PORT`(A 8081 · B 8082 · C 8083)를 세션 환경 변수로 준다 — 기존 명세 C4가 이미 `SERVER_PORT`를 따르게 하므로 명세는 바꾸지 않는다. DB는 Testcontainers(임의 포트)라 충돌하지 않는다. Gradle 데몬 정지·남은 컨테이너 정리는 run마다 하지 않고 라운드 끝에 한 번(`round.sh`).
- 0단계에서 확인: 세 run을 동시에 돌려 포트 충돌(`Address already in use`)·Gradle 데몬 간섭이 없는지. 본 실행 중 충돌이 로그에 나오면 그 run은 폐기하고 같은 회차를 단독으로 재실행한다.

### 설정 격리

- 전 군을 `--setting-sources project,local`로 실행해 사용자 설정(전역 플러그인 superpowers 등·전역 에이전트·전역 스킬)을 뺀다. §2 표의 자산은 run의 `.claude/`(프로젝트 범위)에 커밋 사본으로 넣는다.
- 앱 내장 플러그인(`cc-plugin-*` 3종)과 내장 스킬은 빠지지 않는다. B·C에는 같은 내장 스킬이 로드되고, A는 `--disable-slash-commands`로 스킬이 0개다(1~3차와 같은 조건).
- 실행 직후 세션 로그의 init 이벤트에서 `plugins`·`skills`·`agents` 목록을 검사하고, 군별 허용 목록과 다르면 폐기한다.
- 별도 설정 디렉터리(`CLAUDE_CONFIG_DIR`)는 로그인이 풀려 쓰지 않는다(0-1 확인).
- live 저장소의 `agents/`·`skills/` 등과 `~/.claude/{agents,skills,plugins}` 접근은 읽기 차단 + 로그 검사로 막는다(사본만 쓴다).

## 5. 채점과 사전 동결

### 5.1 숨긴 테스트를 두 층으로 나눈다

| 층 | 정의 | 점수 |
|---|---|---|
| **명세 내** | 명세 문구(기존 `feature.md` + 이번 요청)에서 직접 도출되는 기대. 케이스마다 근거 문구를 단다. 기존 동작 회귀 케이스 포함 | **주 지표** |
| **명세 해석** | 명세에 없지만 상식적인 기대. 케이스마다 상식 근거를 단다 | 별도 보고, 주 지표에 넣지 않음 |

- 근거 문구가 없는 케이스는 명세 내로 분류할 수 없다. 분류는 ✋2 동결 때 확정하고 이후 바꾸지 않는다.
- 2차 회귀 케이스 중 이번 요청과 충돌하는 것(예: 전액 환불만 가정한 케이스)은 동결 전에 목록으로 빼고 사유를 적는다.

### 5.2 지표

| 지표 | 구분 | 측정 |
|---|---|---|
| 명세 내 통과율 | **주 지표** | 요구사항별 통과율의 평균 (2차 방식). 요구사항 = 새 요구사항(T3 P1~P6 · T4 M1~M8) + 회귀 묶음 `REG` 하나 — 회귀 92케이스가 점수를 독점하지 않게 |
| 회귀 통과율 | 보조 | 기존 동작 케이스만 따로 |
| 명세 해석 통과율 | 보조 | §5.1 |
| 자체 테스트 커버 | 보조 | 자체 테스트 ↔ 요구 항목 블라인드 매핑 (opus 3회 다수결, 이전과 같음) |
| 비용·시간 | 보조 | 세션 로그 `total_cost_usd`·벽시계 |

### 5.3 동결 후 수정 규칙 (실행 전에 확정)

- 동결 후 숨긴 테스트를 고칠 수 있는 경우는 **채점기 버그**뿐이다: ① 정답 구현이 실패하거나 ② 케이스가 명세 문구와 모순될 때.
- "run 결과를 보니 기대가 명세 밖이었다"는 수정 사유가 아니다 — 케이스는 그대로 두고 보고서에 기록만 한다.
- 수정은 전 run에 적용해 재채점하고, 수정 전 결과를 `results/*-v1.json`으로 보존하고, 경위를 이 PRD에 남긴다.

### 5.4 채점기 검증

- 스타터(= 2차 정답 구현, 새 기능 없음)는 새 기능 케이스 전부 실패·회귀 케이스 전부 통과.
- 확장한 정답 구현은 전부 통과(2회 연속, 동시성 반복 포함).
- 돌연변이: 새 기능 범주마다 하나 이상(최소 4종), **실패 예상 항목을 채점 전에 기록**하고 의도한 범주에서만 실패하는지 확인.

## 6. 가설과 분석 계획 (실행 전에 확정)

### 6.1 가설

| | 비교 | 의미 |
|---|---|---|
| **H1 (주)** | C vs B | 권장 기본값(일반 + 스킬) 대비 에이전트 팀이 명세 내 정확도를 높이는가 |
| **H2 (주)** | C vs A | 하네스 없는 단일 세션 대비 에이전트 팀이 높이는가 |
| H3 (보조) | B vs A | 이 과제에서 스킬이 정확도를 바꾸는가 |

### 6.2 검정과 판정 문구

- 명세 내 통과율, 군당 5 run, **정확 순열검정 양측**. H1·H2는 Holm 보정(가장 작은 p < 0.025, 다음 p < 0.05).
- 5 대 5에서 가능한 최소 p ≈ 0.008이다. 유의하려면 사실상 C 5 run이 비교군 5 run보다 거의 모두 높아야 한다 — **우연으로 이 결과가 나올 여지가 작다**는 것이 이 설계의 "확실함"이다.
- 판정 문구:
  - 유의하고 C가 높음 → "이 과제에서 C가 명세 내 정확도를 높였다" + 평균 차이·범위 + **통과율 1%p당 추가 비용**
  - 유의하고 C가 낮음 → "C가 낮았다"
  - 그 밖 → "차이를 검출하지 못했다" (차이가 없다고 쓰지 않는다)
- 보조 지표는 검정 없이 평균·범위만 보고한다.

### 6.3 무익 중단 (시간 단축)

- 3라운드(군당 3 run)를 마친 뒤 한 번만 본다.
- **C의 명세 내 통과율 평균이 A·B 평균 둘 다 이하**이면 4·5라운드를 하지 않고 "C 우위를 검출하지 못했다"로 마감한다. 남은 2라운드로 C가 유의하게 앞설 가능성이 사실상 없기 때문이다. 한쪽에만 앞서 있으면 계속한다.
- 중단은 "C 우위" 결론을 낼 기회만 줄이므로 잘못된 우위 판정 확률은 늘지 않는다. 반대로 중간에 C가 앞서도 **조기 승리 선언은 하지 않고** 5라운드까지 간다.
