# REPORT — 5차 실험: 단일 세션이 실패하는 과제에서 에이전트 팀이 이득인가

> 2026-10-11 · 계획: [`PRD.md`](PRD.md) · 과제: [`tasks/t3`](tasks/t3/change-request.md) · [`tasks/t4`](tasks/t4/change-request.md) · **0-2 걸러 내기에서 마감** (본 실행 없음)

## 1. 결론

**단일 세션이 실패하는 과제를 찾지 못했다.** 기존 코드 수정(T3)과 교차 관심사 변경(T4) 모두에서 B(일반 + 스킬) 단일 세션이 Sonnet은 물론 **Haiku로도 명세 내 숨긴 테스트를 전부 통과**했다. 사전에 정한 채택 기준(B 통과율 40~85%)을 넘는 과제가 없어, 정지 조건에 따라 A·B·C 본 실행을 하지 않고 마감했다.

- 이 실험은 A·B·C를 비교하지 않았다. 보인 것은 "에이전트 팀이 앞설 여지가 있는 과제가 이 범위에 없었다"이다.
- 1~4차와 합치면: **명세가 상세한 백엔드 기능 작업은 모델(Opus·Sonnet·Haiku)·과제 유형(신규 기능·기존 코드 수정·교차 관심사 변경)과 관계없이 단일 세션이 천장**이다. 이 범위에서 에이전트 팀은 정확도로 이득을 낼 자리가 없고, 1~3차에서 잰 비용 2.6~6.3배만 남는다.

## 4. 해석

- **천장의 원인은 명세다.** 4차(모델 하향)에 이어 이번에 Haiku까지 내려도 천장이었다. 변경 요청이 상태 전이·계산식·오류 우선순위·PG 키 규칙·동시성 기대까지 적어 주면, 모델이 할 일은 "명세를 코드로 옮기기"가 되고 이 정도 규모(변경 파일 12~16개)는 단일 세션이 무리 없이 해낸다.
- **기존 코드가 깔끔했던 것도 쉬운 쪽으로 작용했을 수 있다.** 시작 코드가 2차 정답 구현이라 레이어·잠금 순서·멱등 처리 구조가 이미 잡혀 있었다. 실무의 낡은 코드베이스는 더 어려울 수 있다(검증하지 않음).
- **에이전트 팀이 이득을 낼 수 있는 조건은 이 실험 설계로 만들기 어렵다.** 명세를 비우면 실패가 생기지만(3차), 그 실패는 명세 밖 기대에서 나오고 모든 방식이 똑같이 놓쳤다. 남은 후보는 한 세션 컨텍스트를 넘는 대형 작업(T2)·단계별 누적(T1)인데, 이번 결과로 보면 이것도 천장일 가능성이 크고 비용·시간이 크다.

## 6. 이 실험에서 남은 것

- **격리 방식 확정**: `--setting-sources project,local` + 하네스 커밋 사본(run의 `.claude/`) + init 목록 검사. 1~4차의 "전역 플러그인이 모든 군에 로드" 한계를 해결했다(`CLAUDE_CONFIG_DIR`는 로그인이 풀려 기각).
- **사전 동결 장치**: 명세 내/해석 층 분리, 돌연변이 실패 예상 사전 기록, 정지 조건 — 이번에 실제로 정지 조건이 작동해 본 실행 비용을 쓰지 않았다.
- **재사용 가능한 자산**: 변경 요청 과제 2종, 숨긴 테스트(새 케이스 55 + 회귀 92), 정답 구현 2종, 라운드 병렬 실행 스크립트(`scripts/round.sh`, `--model`).
