# 변경 요청: 멀티테넌시 도입

## 배경
이 저장소는 `feature.md` 명세대로 동작하는 주문 결제 API다. 여러 판매사(테넌트)가 같은 서버를 쓰도록, 모든 데이터를 테넌트별로 나눈다.

- 이 문서에 적지 않은 동작은 `feature.md`를 그대로 따른다. 기존 API·동작은 아래에서 바꾸는 것 외에는 그대로 유지한다.
- 기존 데이터 이전은 고려하지 않는다(빈 DB에서 시작).

## 요구사항

### M1. 테넌트 헤더
- M1.1 `/api/`로 시작하는 모든 요청은 `X-Tenant-Id` 헤더가 필수다. 값은 영문 소문자·숫자·하이픈으로 된 1~30자.
- M1.2 헤더가 없거나 형식이 틀리면 400(`VALIDATION_ERROR`, Problem Details). 오류 우선순위(C3)에서 400 단계에 속한다.

### M2. 데이터 격리
- M2.1 상품·쿠폰·주문은 생성 요청의 테넌트에 속한다.
- M2.2 다른 테넌트의 상품·쿠폰·주문은 **존재하지 않는 것과 똑같이** 취급한다 — 조회·결제·취소·배송은 해당 404(`PRODUCT_NOT_FOUND`·`COUPON_NOT_FOUND`·`ORDER_NOT_FOUND`)이고, 대상의 상태·재고·쿠폰은 바뀌지 않는다.
- M2.3 주문 생성 시 다른 테넌트의 상품이나 쿠폰을 지정하면 404(R3.3과 같은 코드)이고, 아무것도 예약되지 않는다.
- M2.4 응답의 `Location`은 같은 테넌트 헤더로 조회할 수 있는 경로다.

### M3. 쿠폰 코드
- M3.1 쿠폰 `code`는 **테넌트 안에서만** 유일하다. 다른 테넌트가 같은 `code`를 등록할 수 있다(201). 같은 테넌트에서 중복이면 409(`DUPLICATE_COUPON_CODE`).
- M3.2 `GET /api/coupons/{code}`와 주문의 `couponCode`는 요청 테넌트의 쿠폰을 가리킨다. 같은 `code`의 쿠폰이라도 테넌트가 다르면 `usedCount`·`totalQuantity`는 서로 독립이다.

### M4. 사용자
- M4.1 `X-User-Id`는 테넌트 안에서만 의미가 있다. 같은 `X-User-Id`라도 테넌트가 다르면 다른 사용자다.
- M4.2 쿠폰의 "같은 사용자가 사용 중인 주문이 없음" 조건(R2.5)은 테넌트별로 판단한다.

### M5. 멱등성
- M5.1 `Idempotency-Key`의 키 공간은 테넌트별이다(R4.1의 엔드포인트별 독립에 더해). 같은 키라도 테넌트가 다르면 서로 다른 요청으로 각각 처리한다 — 422나 재생이 아니다.

### M6. 외부 PG
- M6.1 결제 시 PG 요청의 `Idempotency-Key`는 `{tenantId}:{Idempotency-Key}`다(R5.3을 대체). 예: 테넌트 `acme`, 클라이언트 키 `k1` → `acme:k1`.
- M6.2 그 밖의 PG 계약은 바뀌지 않는다.

### M7. 목록
- M7.1 주문 목록(R9)은 요청 테넌트의 주문만 돌려준다. `userId` 필터도 그 테넌트 안에서 적용한다.

### M8. 동시성
- M8.1 R10의 동시성 규칙은 테넌트마다 성립한다.
- M8.2 두 테넌트가 같은 `code`의 쿠폰(각 `totalQuantity` 5)을 가지고 있을 때 두 테넌트에서 동시에 15건씩 사용하면, 테넌트마다 정확히 5건 201이고 각 `usedCount`는 5다.
- M8.3 두 테넌트가 같은 `Idempotency-Key`로 동시에 주문을 생성하면 둘 다 201이고 주문은 2건이다.
