# 02 DB 설계 — order (주문 + 재고 차감)

- DB: PostgreSQL (테스트 컨테이너 `postgres:16-alpine`)
- 마이그레이션: Flyway, `src/main/resources/db/migration/`
- 스키마 관리: `spring.jpa.hibernate.ddl-auto=validate` (Hibernate는 스키마를 만들지 않고 검증만 한다. 엔티티는 아래 DDL에 맞춘다)
- API 설계: [01_api_design.md](./01_api_design.md)
- **응답 필드 ↔ 컬럼 대응, 제약 ↔ 상태코드 매핑은 [01_api_design.md §9 정합 요약](./01_api_design.md#9-정합-요약)이 유일한 기준이다.** 이 문서에는 복제하지 않는다.

---

## 1. 테이블 개요

```
products (1) ──< order_items >── (1) orders
             product_id FK      order_id FK
```

| 테이블 | 역할 |
|---|---|
| `products` | 상품과 현재 재고. 가격은 변경 API가 없지만, 주문은 가격을 스냅샷으로 따로 저장한다 |
| `orders` | 주문 헤더(상태, 생성 시각) |
| `order_items` | 주문 항목(상품, 수량, 주문 시점 단가) |

`order` 는 SQL 예약어이므로 테이블명은 `orders` 이다.

## 2. 컬럼 정의

### 2.1 `products`
| 컬럼 | 타입 | NULL | 기본값 | 제약 | 비고 |
|---|---|---|---|---|---|
| `id` | `bigint` | NO | identity | PK | `GENERATED BY DEFAULT AS IDENTITY` |
| `name` | `varchar(255)` | NO | — | `ck_products_name_not_blank`: `btrim(name) <> ''` | 받은 그대로 저장(trim 안 함) |
| `price` | `bigint` | NO | — | `ck_products_price_positive`: `price > 0` | 원 단위 정수 |
| `stock` | `integer` | NO | — | `ck_products_stock_non_negative`: `stock >= 0` | R7의 최종 방어선 |

### 2.2 `orders`
| 컬럼 | 타입 | NULL | 기본값 | 제약 | 비고 |
|---|---|---|---|---|---|
| `id` | `bigint` | NO | identity | PK | |
| `status` | `varchar(20)` | NO | — | `ck_orders_status`: `status IN ('ORDERED','CANCELLED')` | `@Enumerated(EnumType.STRING)` |
| `created_at` | `timestamptz` | NO | 없음 | — | 애플리케이션이 `Instant`(밀리초 절삭)로 채운다 |

- `total_price` 컬럼은 **두지 않는다.** 주문 항목은 생성 후 바뀌지 않으므로(`unit_price` 스냅샷, `quantity` 고정) Σ(unit_price × quantity)는 언제 계산해도 같다. 저장하면 같은 사실이 두 곳에 생기고, 테이블을 넘나드는 일관성은 CHECK로 강제할 수 없다. 응답을 만들 때 items를 어차피 로드하므로 계산 비용도 추가 쿼리가 없다.
- `created_at`에 `DEFAULT now()`를 두지 않는다. 기본값을 두면 INSERT 후 값을 다시 읽어야 응답에 실을 수 있고, 값의 출처가 애플리케이션과 DB 두 곳이 된다. 애플리케이션 단일 출처로 한다.
- 버전(`@Version`) 컬럼은 두지 않는다. 동시성은 비관적 락으로 해결한다(§4).

### 2.3 `order_items`
| 컬럼 | 타입 | NULL | 기본값 | 제약 | 비고 |
|---|---|---|---|---|---|
| `id` | `bigint` | NO | identity | PK | 요청 내 항목 순서 보존용(`ORDER BY id`) |
| `order_id` | `bigint` | NO | — | FK → `orders(id)` | |
| `product_id` | `bigint` | NO | — | FK → `products(id)` | |
| `quantity` | `integer` | NO | — | `ck_order_items_quantity_positive`: `quantity >= 1` | |
| `unit_price` | `bigint` | NO | — | `ck_order_items_unit_price_positive`: `unit_price > 0` | 주문 시점 `products.price` 스냅샷 |
| — | — | — | — | `uq_order_items_order_product`: `UNIQUE (order_id, product_id)` | 요청 400 규칙(중복 productId)의 방어선 |

### 2.4 타입 선택 근거

| 결정 | 근거 |
|---|---|
| 금액(`price`, `unit_price`) = `bigint` / Java `long` | 원문은 상한을 두지 않았다. `integer`(최대 약 21억 원)는 고가 상품에서 넘칠 수 있다. 그리고 `totalPrice`(Σ 단가×수량)는 `long`으로 계산해야 하므로 단가도 `long`으로 맞춰 승격·절삭 혼동을 없앤다. `numeric`은 "원 단위 정수" 규약에 비해 과하고 JSON에서 소수로 직렬화될 위험이 있다 |
| 수량·재고(`quantity`, `stock`) = `integer` / Java `int` | 개수 단위로 21억이면 충분하다. 요청 범위 초과는 Jackson 오버플로로 400이 된다 |
| PK = `bigint` identity | Hibernate `GenerationType.IDENTITY`와 대응한다. 시퀀스 할당 크기 설정이 필요 없다 |
| 시각 = `timestamptz` / Java `Instant` | 절대 시각이다. Hibernate 6은 `Instant`를 `timestamp(6) with time zone`에 매핑하므로 `validate`를 통과한다. `hibernate.jdbc.time_zone=UTC`로 JVM 타임존 영향을 차단한다 |
| 상태 = `varchar(20)` + CHECK | PostgreSQL 네이티브 enum은 값 추가 시 마이그레이션이 번거롭고 Hibernate 기본 매핑(varchar)과 다르다 |

## 3. 인덱스

| 이름 | 대상 | 용도 |
|---|---|---|
| PK 인덱스 ×3 | `products(id)`, `orders(id)`, `order_items(id)` | 단건 조회, `WHERE id IN (...) FOR UPDATE` |
| `ix_orders_created_at_id` | `orders (created_at DESC, id DESC)` | R6 목록 `ORDER BY created_at DESC, id DESC LIMIT/OFFSET`. 정렬 방향과 같은 순서라 정렬 없이 인덱스 순서대로 읽는다 |
| `uq_order_items_order_product` (UNIQUE) | `order_items (order_id, product_id)` | 중복 방어선. 선두 컬럼이 `order_id`라 주문별 items 로딩(`WHERE order_id IN (...)`, batch fetch)도 이 인덱스가 담당한다. `order_id` 단독 인덱스는 따로 만들지 않는다 |

`order_items.product_id`에는 인덱스를 두지 않는다. PostgreSQL에서 참조하는 쪽(FK) 인덱스는 부모 행 삭제·키 변경 때만 필요한데, 상품 삭제·수정은 범위 밖이다. 상품별 주문 조회 요구도 없다.

## 4. 동시성 전략

### 4.1 결정: 비관적 행 락 (`SELECT ... FOR UPDATE`), productId 오름차순 단일 쿼리

```sql
-- Hibernate가 @Lock(PESSIMISTIC_WRITE) JPQL에서 생성 (방언에 따라 FOR UPDATE 또는 FOR NO KEY UPDATE)
SELECT ... FROM products p WHERE p.id IN (?, ?, ...) ORDER BY p.id ASC FOR UPDATE;
```

절차는 [01 §3](./01_api_design.md#3-r3--주문-생성-post-apiorders)(생성)과 [01 §5](./01_api_design.md#5-r5--주문-취소-post-apiordersidcancel)(취소)에 있다.

### 4.2 조건부 UPDATE 대신 이 방식을 고른 근거

| 관점 | 비관적 락 (채택) | 조건부 UPDATE `SET stock = stock - :q WHERE id = :id AND stock >= :q` |
|---|---|---|
| 404 vs 409 구분 | 락 조회 한 번으로 존재 여부와 재고를 함께 얻는다. "모든 항목 존재 확인 → 모든 항목 재고 확인" 순서가 그대로 코드가 된다 | 영향 행 0이 "없음"과 "부족"을 구분하지 못한다. 404를 먼저 내려면 별도 존재 조회가 필요하고, 그러면 쿼리 경로가 둘이 된다 |
| 원자성 | 모든 판정이 **첫 쓰기 전에** 끝난다. 409면 쓴 것이 없다(롤백은 이중 안전장치) | 앞 항목을 차감한 뒤 뒤 항목에서 실패하면 **롤백에 의존**해 되돌린다 |
| unitPrice 스냅샷 | 락을 잡은 같은 행에서 가격을 읽는다 | 가격을 위한 별도 SELECT가 필요하다(지금은 가격 변경 API가 없어 무해하지만 설계 일관성은 떨어진다) |
| JPA 관용성 | `@Lock` + 더티 체킹. 영속성 컨텍스트와 DB 상태가 일치한다 | `@Modifying` 벌크/네이티브 UPDATE라 영속성 컨텍스트가 낡는다(`clearAutomatically` 필요) |
| 409 상세 | 부족한 항목 전부를 보고할 수 있다 | 처음 실패한 항목만 안다 |
| 처리량 | 같은 상품 행에서 직렬화된다 | 같다. UPDATE도 커밋 때까지 행 락을 유지한다 |

낙관적 락(`@Version` + 재시도)은 쓰지 않는다. 충돌 시 `OptimisticLockException`이 409(재고 부족)가 아닌 실패로 새어 나가거나, 재시도 횟수가 부족하면 재고가 남아도 실패해 R7의 "정확히 10/10"을 보장할 수 없다.

### 4.3 R7 시나리오 동작 (재고 10, 수량 1 주문 20건 동시)

1. 20개 트랜잭션이 같은 `products` 행에 `FOR UPDATE`를 요청한다. 하나만 획득하고 19개는 대기한다.
2. 획득한 트랜잭션은 `stock`을 보고(≥1) 차감·INSERT·커밋한다. 락이 풀린다.
3. 다음 대기자가 락을 얻는다. **READ COMMITTED에서 락 대기 후 `SELECT ... FOR UPDATE`는 그 행의 최신 커밋 버전을 반환한다.** 따라서 직전 차감이 반영된 `stock`을 본다.
4. 10번째 커밋 후 `stock = 0`. 나머지 10건은 `0 < 1`로 409를 받고 롤백한다(쓴 것이 없다).
5. 결과: 201 ×10, 409 ×10, 최종 `stock = 0`, `orders` 10행.

전제 조건(구현 시 반드시 지킬 것):
- 격리 수준은 기본 READ COMMITTED (변경 금지).
- 락 쿼리가 트랜잭션에서 해당 Product의 **첫 로드**여야 한다. 먼저 락 없이 로드하면 Hibernate 1차 캐시가 대기 전의 낡은 `stock`을 돌려준다.
- 테스트 메서드·테스트 클래스에 `@Transactional`을 붙이지 않는다(요청마다 독립 트랜잭션이어야 한다).

### 4.4 데드락 분석

락 획득 순서 규칙:
- **주문 생성**: `products` 행들을 id 오름차순으로(단일 `ORDER BY id FOR UPDATE` 쿼리) → 새 `orders`/`order_items` INSERT.
- **주문 취소**: `orders` 대상 행 1개 → `products` 행들을 id 오름차순으로(같은 쿼리).

| 경합 | 분석 |
|---|---|
| 생성 vs 생성 (상품 집합 겹침) | 양쪽 모두 같은 전역 순서(id 오름차순)로 상품 락을 잡는다. 순환 대기가 생길 수 없다. 예: A={1,2}, B={2,1} 요청이어도 둘 다 1→2 순서다 |
| 취소 vs 생성 | 생성은 기존 `orders` 행을 잠그지 않는다(새 행 INSERT뿐). 취소는 주문 행 → 상품(오름차순)이고, 생성은 상품(오름차순)만 잡는다. 상품 구간의 순서가 같으므로 순환이 없다 |
| 취소 vs 취소 (같은 주문) | 주문 행 락에서 직렬화된다. 두 번째는 상품 락까지 가지 않고 409로 끝난다 |
| 취소 vs 취소 (다른 주문) | 각자 다른 주문 행을 잡고, 상품은 같은 오름차순이다. 순환이 없다 |
| FK 검사 락 | `order_items` INSERT 시 PostgreSQL이 부모 `products`/`orders` 행에 `FOR KEY SHARE`를 건다. `products` 행은 이미 자기 트랜잭션이 배타 락을 보유 중이고, `orders` 행은 자기가 방금 INSERT한 행이다. 다른 트랜잭션을 기다리지 않는다 |

`ORDER BY` + `FOR UPDATE`에서 PostgreSQL은 정렬된 출력 순서대로 행을 잠근다(LockRows 노드가 Sort 위에 있다). 정렬 키 `id`는 갱신되지 않으므로 대기 후에도 순서가 바뀌지 않는다.

### 4.5 409 시 전체 롤백 보장

1. 판정(404·409)이 모든 UPDATE/INSERT보다 앞선다. 판정에서 실패하면 쓴 것이 없다.
2. 도메인 예외는 `RuntimeException`이므로 `@Transactional`이 트랜잭션 전체를 롤백하고 행 락을 해제한다. 서비스는 이 예외를 catch하지 않는다.
3. 버그로 음수 재고를 쓰려 하면 `ck_products_stock_non_negative`가 커밋 전에 거절한다(이 경우 500이지만 데이터는 오염되지 않는다).

### 4.6 취소 중복 복원 방지

`orders` 행 `FOR UPDATE` 후 `status` 확인. 두 번째 취소는 첫 번째 커밋까지 대기한 뒤 `CANCELLED`를 보고 409로 끝난다. 재고 복원(`stock = stock + quantity`)은 정확히 한 번 일어난다. 조건부 UPDATE(`WHERE status='ORDERED'`) 대신 행 락을 쓴 이유는 상품 쪽과 같은 패턴(락 → 판정 → 더티 체킹)으로 통일하기 위해서다.

## 5. 엔티티 매핑 지침

| 엔티티 | 매핑 |
|---|---|
| `Product` | `@Table(name="products")`. `@Id @GeneratedValue(strategy = IDENTITY) Long id`, `@Column(nullable=false, length=255) String name`, `@Column(nullable=false) long price`, `@Column(nullable=false) int stock`. 메서드 `decreaseStock(int q)`(stock < q면 `IllegalStateException`), `increaseStock(int q)` |
| `Order` | `@Table(name="orders")`. `Long id`(IDENTITY), `@Enumerated(EnumType.STRING) @Column(nullable=false, length=20) OrderStatus status`, `@Column(name="created_at", nullable=false, updatable=false) Instant createdAt`, `@OneToMany(mappedBy="order", cascade=CascadeType.ALL) @OrderBy("id ASC") List<OrderItem> items`. 메서드 `cancel()`, `getTotalPrice()`(`multiplyExact`/`addExact`) |
| `OrderItem` | `@Table(name="order_items")`. `Long id`(IDENTITY), `@ManyToOne(fetch=LAZY, optional=false) @JoinColumn(name="order_id") Order order`, `@Column(name="product_id", nullable=false) Long productId`, `@Column(nullable=false) int quantity`, `@Column(name="unit_price", nullable=false) long unitPrice` |

- `OrderItem.productId`는 `Product` 연관이 아니라 **값 컬럼**이다. 연관으로 두면 주문 로딩 때 Product가 영속성 컨텍스트에 들어갈 수 있고, 그러면 취소 트랜잭션의 상품 락 쿼리가 "첫 로드" 조건(§4.3)을 잃는다. FK 무결성은 DB가 보장한다.
- JPQL 엔티티명 `Order`가 Hibernate 파서에서 문제가 되면 `@Entity(name = "PurchaseOrder")`로 엔티티명만 바꾼다(테이블명 `orders`는 유지).
- 리포지토리 메서드(01 문서와 같다):
  - `ProductRepository.findAllByIdInForUpdate(Collection<Long> ids)` — `@Lock(PESSIMISTIC_WRITE)`, `order by p.id asc`
  - `OrderRepository.findByIdForUpdate(Long id)` — `@Lock(PESSIMISTIC_WRITE)`, items fetch join 금지
  - `OrderRepository.findAll(Pageable)` — 정렬 `createdAt DESC, id DESC`, items는 `default_batch_fetch_size`로 배치 로딩

## 6. Flyway 마이그레이션

- 파일: `src/main/resources/db/migration/V1__create_order_schema.sql` (기존 `.gitkeep`과 같은 디렉터리, Flyway 기본 location `classpath:db/migration`)
- 이후 변경은 `V2__...sql`로 추가한다. 적용된 V1은 수정하지 않는다(체크섬 불일치로 기동 실패).

```sql
-- V1__create_order_schema.sql
-- 상품, 주문, 주문 항목. 금액은 원 단위 정수(bigint), 수량/재고는 integer.

CREATE TABLE products (
    id     BIGINT       GENERATED BY DEFAULT AS IDENTITY,
    name   VARCHAR(255) NOT NULL,
    price  BIGINT       NOT NULL,
    stock  INTEGER      NOT NULL,
    CONSTRAINT pk_products PRIMARY KEY (id),
    CONSTRAINT ck_products_name_not_blank     CHECK (btrim(name) <> ''),
    CONSTRAINT ck_products_price_positive     CHECK (price > 0),
    CONSTRAINT ck_products_stock_non_negative CHECK (stock >= 0)
);

CREATE TABLE orders (
    id          BIGINT      GENERATED BY DEFAULT AS IDENTITY,
    status      VARCHAR(20) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    CONSTRAINT pk_orders PRIMARY KEY (id),
    CONSTRAINT ck_orders_status CHECK (status IN ('ORDERED', 'CANCELLED'))
);

-- R6 목록: ORDER BY created_at DESC, id DESC
CREATE INDEX ix_orders_created_at_id ON orders (created_at DESC, id DESC);

CREATE TABLE order_items (
    id          BIGINT  GENERATED BY DEFAULT AS IDENTITY,
    order_id    BIGINT  NOT NULL,
    product_id  BIGINT  NOT NULL,
    quantity    INTEGER NOT NULL,
    unit_price  BIGINT  NOT NULL,
    CONSTRAINT pk_order_items PRIMARY KEY (id),
    CONSTRAINT fk_order_items_order   FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products (id),
    -- 선두 컬럼 order_id: 주문별 항목 로딩 인덱스 역할도 겸한다
    CONSTRAINT uq_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_quantity_positive   CHECK (quantity >= 1),
    CONSTRAINT ck_order_items_unit_price_positive CHECK (unit_price > 0)
);
```

검증 포인트(`ddl-auto=validate`와의 정합):
- `BIGINT` ↔ `Long`/`long`, `INTEGER` ↔ `int`, `VARCHAR(255)` ↔ `String`, `VARCHAR(20)` ↔ `@Enumerated(STRING)`, `TIMESTAMPTZ`(= `timestamp(6) with time zone`) ↔ `Instant`.
- 테이블·컬럼명은 Spring Boot 기본 네이밍 전략(camelCase → snake_case)과 일치한다: `createdAt` → `created_at`, `unitPrice` → `unit_price`, `productId` → `product_id`.

## 7. 정합 기준

응답 필드 ↔ 컬럼 대응표, 요청 필수 여부 ↔ nullable, 제약 ↔ HTTP 상태코드 매핑은 [01_api_design.md §9 정합 요약](./01_api_design.md#9-정합-요약)을 따른다.
