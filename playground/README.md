# playground — 개발 방식별 비교 실험

이 저장소의 하네스(에이전트 팀·스킬)가 **비용과 시간을 더 들일 만큼 결과가 좋은지** 확인하는 실험 모음. 설치 대상이 아니다.

## 질문과 결론

- **예상**: 단순 프롬프트보다 하네스를 갖춘 에이전트 팀(오케스트레이션)의 결과가 명확히 좋을 것이다.
- **실험**: 일반·스킬·에이전트 팀으로 같은 백엔드 기능을 개발시켜, 에이전트가 보지 못하는 숨긴 테스트로 채점했다. 상세 명세(Opus·Sonnet)와 짧은 명세(Sonnet)를 모두 시험했다.
- **결과**: 결과물의 정확도·견고성은 유의미하게 차이 나지 않았다. 에이전트 팀은 테스트를 더 많이 썼지만 **비용 2.6~6.3배, 시간 2.8~5.1배**를 썼고, 짧은 명세에서는 설계 단계에서 혼자 내린 가정 때문에 오히려 일부 요구를 놓쳤다. 반면 **스킬은 비용 약 +7%로 코드 컨벤션 준수율을 71% → 95%로 올렸다**.
- **한계**: 사람 개입 없는 단일 기능(주문 도메인, Spring Boot) 조건이고 반복은 군당 2~3회다. 대화형 가정 확인, 여러 기능이 쌓이는 장기 프로젝트에서의 가치는 검증하지 않았다.

## 권장 사용법 (이 실험의 결론)

| 방식 | 기능 정확도 | 코드 컨벤션 | 비용·시간 | 권장 |
|---|---|---|---|---|
| 일반 | 기준 | 71% | 기준 | 스킬 없이는 비추천 |
| **일반 + 스킬** | 같음 | **95%** | 약 +7% | **기본값** |
| 에이전트 팀 | 같음 (짧은 명세에선 조금 낮음) | 86% | 2.6~6.3배 / 2.8~5.1배 | 단일 기능에는 비추천 |

- **단일 세션 + 스킬을 기본으로**, effort는 작업 크기에 맞춘다 — medium은 비용·시간 약 −40%에 견고성 −1항목·자체 테스트 절반(3차 보충).
- **방식보다 명세가 큰 변수다** — 상세 명세에선 모든 방식이 만점, 짧은 명세에서만 차이가 났다. 에이전트 팀에 쓸 비용을 명세·계획(가정 확인)에 쓰는 편이 효과가 크다.
- 에이전트 팀은 한 세션 컨텍스트에 담기지 않는 대형 작업에 한정한다 — 이 영역은 검증하지 않았다.

## 비교군

| 군 | 정의 |
|---|---|
| A 일반 | 하네스 없음, 단일 세션 (서브에이전트·스킬 차단) |
| B 스킬 | `spring-boot` 스킬만, 단일 세션 |
| C 오케스트레이션 | `feature-pm` + 워커 4종(`backend-designer`·`backend-impl`·`boundary-verifier`·`test-writer`) + 스킬 |

모든 run은 같은 프롬프트·스타터로 헤드리스(`claude -p`) 실행, 사람 개입 없음.

## 실험별로 배운 것

1. **1차** — 쉬운 기능은 모든 방식이 만점(천장 효과). C의 verifier가 숨긴 테스트 밖 결함(오버플로)을 잡았지만 점수에 반영되지 않았다.
2. **2차** — 상태 전이·멱등성·외부 PG 장애·만료·동시성을 넣어 난이도를 올려도 천장. 명세가 충분히 구체적이면 방식과 무관하다.
3. **4차** — 모델을 Sonnet으로 낮춰도 천장. 천장의 원인은 모델 성능보다 **명세의 구체성**으로 본다.
4. **3차** — 명세를 비우자 차이가 생겼지만 하네스에 유리하지 않았다. 동시성·멱등성 같은 "어려운" 항목은 A도 전부 챙겼다. C의 실패는 전부 설계 담당이 사람 확인 없이 내린 결정(0원 허용, 쿠폰 무제한, 환불 시 쿠폰 미복원, 새 키 재시도 거절)이었다.

### 방식별로 일관되게 관찰된 것

| 관찰 | 근거 |
|---|---|
| 정확도·견고성 차이 없음 | 1·2·4차 전 run 만점, 3차 총점 차 0.3점 |
| C는 자체 테스트를 2~6배 많이 쓴다 | 1차 1.7배, 2차 3.1배, 3차 6.4배 |
| C의 테스트가 요구 항목을 더 검증한다 (3차) | S 항목 커버 C 23.5 vs A 20.5 / 25 |
| C의 분기 커버리지는 오히려 낮은 편 | 1·2차 최저 군이 C |
| C는 설계 근거를 문서로 남긴다 (점수 밖) | `_workspace/` 설계 문서 — 결정마다 근거 기재 |
| B(스킬)는 정확도로는 A와 구별되지 않지만 컨벤션 준수는 확실히 높다 | 1·2차 총점 범위 겹침, 2차 보충 준수율 A 71% · B 95% · C 86% |
| effort medium은 싸고 빠르지만 조금 덜 챙긴다 | 3차 보충 비용 −37%, 견고성 47.9 → 46.4, 자체 테스트 절반 |
| C의 verifier는 거의 판정을 바꾸지 않는다 | 3차 FIX·REDO 0, 대기만 하는 designer 재호출 |

## 실험 방법 (공통)

- **숨긴 테스트**: 표준 라이브러리만 쓰는 블랙박스 HTTP 테스트. 외부 PG는 장애 주입 스텁(거절·500·지연·연결 끊김·환불 실패)으로 대체. 시간 의존 항목은 TTL을 짧게 다시 기동해 별도 단계로 채점.
- **채점기 검증**: 스타터(전부 실패)·정답 구현(전부 통과, 2회 연속)·돌연변이(정답에 결함 주입 → 의도한 항목만 실패)로 테스트 자체를 검증.
- **테스트 품질**: 자체 테스트 ↔ 요구 규칙 매핑을 블라인드 LLM 판정(run 이름 가림, 하네스 흔적 제거, 3회 다수결).
- **컨벤션 준수**: 스킬 체크리스트 20개 항목으로 같은 방식의 블라인드 판정(판정자는 기준 출처를 모름).
- **격리**: run마다 독립 디렉터리·git, 다른 run·채점 자산·이전 실험 읽기 차단, 세션 로그에서 금지 경로 접근·사용 모델을 검사해 위반 시 폐기.
- **공정성 수정 기록**: 채점 측 버그(PG 스텁의 chunked 본문 미처리, keep-alive 오염)와 테스트 편향(재고 차감 시점 강요)은 발견 즉시 고치고 전 run 재채점, 경위를 각 PRD에 남김.
