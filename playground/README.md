# playground — 개발 방식별 비교 실험

이 저장소의 하네스(에이전트 팀·스킬)가 **비용과 시간을 더 들일 만큼 결과가 좋은지** 확인하는 실험 모음. 설치 대상이 아니다.

## 질문과 결론

- **예상**: 단순 프롬프트보다 하네스를 갖춘 에이전트 팀(오케스트레이션)의 결과가 명확히 좋을 것이다.
- **실험**: 일반·스킬·에이전트 팀으로 같은 백엔드 기능을 개발시켜, 에이전트가 보지 못하는 숨긴 테스트로 채점했다. 상세 명세(Opus·Sonnet)와 짧은 명세(Sonnet)를 모두 시험했다.
- **결과**: 결과물의 정확도·견고성에서 방식 간 차이를 검출하지 못했다. 명세에 적힌 요구만 보면 모든 실험·모든 run이 만점이었고, 실패는 명세 밖 기대에서만 났으며 그 항목은 세 방식이 똑같이 놓쳤다. 에이전트 팀은 테스트를 더 많이 썼지만 **비용 2.6~6.3배, 시간 2.8~5.1배**를 썼다(서로 다른 실험 조건에서 나온 값의 범위). 짧은 명세에서는 두 방식 모두 명세 빈칸을 임의로 채웠다. **스킬 사용을 지시하면 스킬이 정한 관례 준수율이 71% → 95%**였다(비용 +7~22%, n=3). 다만 스킬과 무관한 일반 품질 기준으로는 A·B를 구별하지 못했다(79% vs 83%).
- **결론의 범위**: 단일 세션(A)이 이미 명세 요구를 전부 맞히는 작업이라 **에이전트 팀이 더 잘할 여지가 처음부터 없었다**. 따라서 이 실험이 보인 것은 "이 조건에서는 에이전트 팀이 비용만 더 든다"까지다. 또 측정한 것은 에이전트 팀 일반이 아니라 **현재 버전의 `feature-pm` 하네스를 사람 확인 없이(헤드리스) 돌린 결과**다. 단일 세션이 실패하는 작업(대형·다기능·컨텍스트 초과)과 사람이 가정을 확인하는 대화형 흐름에서 이득이 있는지는 시험하지 않았다.
- **한계**: 사람 개입 없는 단일 기능(주문 도메인, Spring Boot) 조건이고 반복은 군당 2~3회, 통계 검정은 하지 않았다. 대화형 가정 확인, 여러 기능이 쌓이는 장기 프로젝트에서의 가치는 검증하지 않았다. 그 밖의 한계는 아래 [한계와 사후 검토](#한계와-사후-검토).

## 권장 사용법 (이 실험의 결론)

| 방식 | 기능 정확도 | 스킬 관례 준수 | 일반 코드 품질 | 비용·시간 | 권장 |
|---|---|---|---|---|---|
| 일반 | 기준 | 71% | 79% | 기준 | 스킬 없이는 비추천 |
| **일반 + 스킬** | 차이 없음 (상세·짧은 명세 모두) | **95%** | 83% | +7~22% | **기본값** |
| 에이전트 팀 (`feature-pm`) | 차이 없음 | 86% | 64% | 2.6~6.3배 / 2.8~5.1배 | 단일 기능·헤드리스에는 비추천 |

스킬 관례 준수는 스킬 체크리스트 기준이라 스킬 방식에 유리한 측정이다. 일반 코드 품질은 스킬이 다루지 않는 리뷰 항목 14개로 따로 쟀다(2차 REPORT §8). 둘 다 2차 run 기준, 군당 3회라 유의하지 않다.

- **단일 세션 + 스킬을 기본으로**, effort는 작업 크기에 맞춘다 — medium은 비용·시간 약 −40%에 견고성 −1항목·자체 테스트 절반(3차 보충).
- **방식보다 명세가 큰 변수다** — 상세 명세에선 모든 방식이 만점이었고, 짧은 명세에서는 모든 방식이 명세에 없는 기대를 일부 놓쳤다. 에이전트 팀에 쓸 비용을 명세·계획(가정 확인)에 쓰는 편이 효과가 크다.
- 에이전트 팀은 한 세션 컨텍스트에 담기지 않는 대형 작업에 한정한다 — 이 영역은 검증하지 않았다.

## 실험별로 배운 것

1. **1차** — 쉬운 기능은 모든 방식이 만점(천장 효과). C의 verifier가 숨긴 테스트 밖 결함(오버플로)을 잡았지만 점수에 반영되지 않았다.
2. **2차** — 상태 전이·멱등성·외부 PG 장애·만료·동시성을 넣어 난이도를 올려도 천장. 명세가 충분히 구체적이면 방식과 무관하다.
3. **4차** — 모델을 Sonnet으로 낮춰도 천장. 천장의 원인은 모델 성능보다 **명세의 구체성**으로 본다.
4. **3차** — 명세를 비우자 실패 항목이 생겼지만 전부 명세 밖 기대(0원 거절, 쿠폰 1인 1회, 환불 시 쿠폰 복원, 장애 뒤 새 멱등 키로 재시도)였다. 이 항목을 빼면 세 방식 모두 견고성 만점이라 결국 천장이다. 동시성·멱등성 같은 "어려운" 항목은 A도 전부 챙겼다. C의 실패 6건 중 5건(판정자 기준)은 설계 문서에 명시된 결정이었다.

## 실험 방법 (공통)

- **숨긴 테스트**: 표준 라이브러리만 쓰는 블랙박스 HTTP 테스트. 외부 PG는 장애 주입 스텁(거절·500·지연·연결 끊김·환불 실패)으로 대체. 시간 의존 항목은 TTL을 짧게 다시 기동해 별도 단계로 채점.
- **채점기 검증**: 스타터(전부 실패)·정답 구현(전부 통과, 2회 연속)으로 테스트 자체를 검증. 2·3차는 돌연변이(정답에 결함 주입 → 의도한 항목만 실패, 2차는 예상 항목을 채점 전에 기록)까지 확인 — 5종 모두 통과.
- **테스트 품질**: 자체 테스트 ↔ 요구 규칙 매핑을 블라인드 LLM 판정(run 이름 가림, 하네스 흔적 제거, 3회 다수결).
- **컨벤션 준수**: 스킬 체크리스트 20개 항목으로 같은 방식의 블라인드 판정(판정자는 기준 출처를 모름). 순환 측정을 보완하려고 스킬이 다루지 않는 일반 품질 14개 항목으로도 판정.
- **격리**: run마다 독립 디렉터리·git, 다른 run·채점 자산·이전 실험 읽기 차단, 세션 로그에서 금지 경로 접근·사용 모델을 검사해 위반 시 폐기.
- **공정성 수정 기록**: 채점 측 버그(PG 스텁의 chunked 본문 미처리, keep-alive 오염)와 테스트 편향(재고 차감 시점 강요)은 발견 즉시 고치고 전 run 재채점, 경위를 각 PRD에 남김.

## 한계와 사후 검토

실험 종료 후 독립 검토로 확인한 한계. 결론의 방향("에이전트 팀은 이 조건에서 비용만큼의 차이를 보이지 않음")은 유지되지만 표현을 위처럼 낮췄다.

| 한계 | 영향 |
|---|---|
| 통계: 군당 2~3회, 검정 없음 | 1~2점 차이는 의미 없음. "차이 없음"이 아니라 "차이를 검출하지 못함" |
| A가 명세 요구를 전부 맞혀 C가 앞설 여지가 없음 | 정확도 쪽 결론은 "이득 없음"이 아니라 "이 난이도에선 이득이 생길 자리가 없음". 이득 여부는 A가 실패하는 작업에서 다시 재야 한다 |
| 3차 테스트 일부가 명세 밖 기대 — S1·S9·S10(2차 상세 명세 유래), S17(명세가 정하지 않은 멱등 키 의미) | 명세 내 기준(21항목) 재계산을 함께 보고(3차 REPORT §1) |
| 3차 판정 기준이 결과를 본 뒤 두 번 바뀜(재고 차감 시점, 명세 내 재계산) | 둘 다 C 실패를 보고 나서였지만 바꾼 뒤에도 C 우위는 없어 결론 방향은 같음. 다음 실험은 기준을 실행 전에 확정 |
| C는 현재 `feature-pm` 버전을 헤드리스로 실행 | 사람 확인 단계(`[Q.]`)가 빠졌고, 대기만 하는 designer 스폰 같은 하네스 낭비가 비용 배율에 포함됨 |
| 컨벤션 판정은 스킬 체크리스트 기준 + B에 스킬 지시 | 순환 측정. "지시받은 관례 준수"만 잰다. 보충으로 스킬 밖 일반 품질을 재 보니 A·B 차이 없음 |
| 1·2차 C는 워커 일부가 Sonnet, A·B는 전부 Opus | C의 낮은 분기 커버리지·준수율, 비용 배율이 모델 차이일 수 있음 |
| 전역 플러그인(superpowers 등)이 2~4차 모든 군에 로드, 1차는 미로드, 2차 안에서도 run마다 일부 다름 | A도 "하네스 전무"는 아님. 호출 기록은 없어 영향은 작을 것으로 봄. 이후 실험은 깨끗한 설정으로 |
| 하네스 자산 "고정"은 실제로는 live 저장소 심링크 | 그 사이 변경은 표기·rules뿐이라 영향 거의 없음 |
| 2차 정답 구현도 Claude 작성 | 숨긴 테스트가 같은 맹점을 공유할 수 있음. 보충 돌연변이 3종(동시성·멱등성·계산·PG)은 모두 잡았지만 맹점 부재의 증명은 아님 |
| 3차 스킬 군은 보충(2회, 라운드 교차 없음), effort 보충은 A만 | B는 A·C 뒤에 따로 실행. 짧은 명세의 B 관례 준수율은 재지 않음 |
